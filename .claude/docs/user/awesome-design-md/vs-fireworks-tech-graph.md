# awesome-design-md 与 fireworks-tech-graph 对照分析

## Summary

- Project name: awesome-design-md vs fireworks-tech-graph
- Project path: `D:\awesome-design-md` and `D:\fireworks-tech-graph`
- Document type: user
- Purpose: 对照前端设计约束库与技术图生成 skill 的定位差异，帮助以后在做 Agent 辅助资产时分清“设计控制层”和“技术图交付层”

## 一、先给结论：这两个项目都不是 Agent runtime，但它们补的是两种完全不同的产出层

如果只看表面，你会觉得它们很像：

- 都不是在解决 Agent loop
- 都不是在做多 Agent 编排
- 都更像“给编码 Agent 增强质量”的辅助资产
- 都把原本容易漂移的审美/表达问题，沉淀成仓库里的可复用文档或 skill

但如果再往下一层看，它们补的不是同一件事。

### `awesome-design-md` 更像什么

它更像：

> 给编码 Agent 提供“页面设计约束”的风格与界面控制层。

它主要回答的是：

- 前端页面应该长成什么气质
- 页面布局、排版、组件风格应该遵守什么规则
- 怎么把“设计要求”从聊天提示词升级成仓库资产

### `fireworks-tech-graph` 更像什么

它更像：

> 给编码 Agent 提供“技术图产出能力”的可视化交付层。

它主要回答的是：

- 技术架构图、流程图、UML 图怎么自动生成
- 图的风格、节点形状、箭头语义如何保持一致
- 怎么让图示产出可验证、可回归、可导出

所以一句话压缩就是：

- `awesome-design-md` 管“页面怎么设计”
- `fireworks-tech-graph` 管“系统怎么画清楚”

## 二、它们最本质的区别：一个控制 UI 设计，一个控制技术表达

这组对照里最重要的不是文件形式，而是目标函数。

### 1. `awesome-design-md` 的目标函数是“让前端审美稳定”

它在解决的问题通常是：

- 页面能跑，但不好看
- 风格不统一
- 不同页面像不同人做的
- 每次改版都把原来的气质冲掉

所以它的价值落点是：

- 页面设计一致性
- 视觉语言延续性
- AI 生成 UI 的质量下限

### 2. `fireworks-tech-graph` 的目标函数是“让技术结构表达稳定”

它在解决的问题通常是：

- 系统讲不清楚
- 技术文档缺统一图示
- 架构图、流程图靠手工画，慢且不一致
- AI 画图结果容易语法错、布局乱、风格漂

所以它的价值落点是：

- 技术可视化交付效率
- 技术图风格与语义一致性
- 文档/方案图示的可复用生产流程

### 3. 这意味着它们对应的是不同交付物

`awesome-design-md` 面向的是：

- landing page
- 官网
- dashboard
- docs site
- 产品页面

`fireworks-tech-graph` 面向的是：

- architecture diagram
- flowchart
- sequence diagram
- UML
- RAG / Agent / memory 架构图

也就是说，一个偏“产品界面”，一个偏“技术图示”。

## 三、知识载体也不同：一个是设计规范文档，一个是执行型 skill 包

### 1. `awesome-design-md` 的核心载体是 `DESIGN.md`

它最关键的思想是：

- 把设计要求写成一个 Agent 能读取的规范文档

这类载体的优势是：

- 轻量
- 好复制
- 好改写
- 很适合放进项目根目录长期跟随开发

它本质上更像：

- `ARCHITECTURE.md`
- `CONTRIBUTING.md`
- `PLAYBOOK.md`

的设计版本。

### 2. `fireworks-tech-graph` 的核心载体是 skill + reference + script

它不是只靠一份文档。

它把能力拆成：

- `SKILL.md`
- `references/`
- `templates/`
- `fixtures/`
- `scripts/`

这意味着它不仅在描述规则，还在提供：

- 风格规范
- 语义词汇
- 模板
- 校验工具
- 回归测试

所以它更像一个“轻量生成框架”。

### 3. 这背后的工程含义

`awesome-design-md` 更适合做：

- 长期附着在项目上的约束文档
- 多项目复用的风格起点

`fireworks-tech-graph` 更适合做：

- 独立可安装的能力模块
- 团队级统一出图工具

前者偏“规范资产”，后者偏“执行资产”。

## 四、它们都在解决“AI 产出漂移”，但漂移对象不一样

这是我认为这组对照最值得记住的一点。

### `awesome-design-md` 在压什么漂移

它主要压的是：

- UI 风格漂移
- 排版漂移
- 组件气质漂移
- 页面视觉语言漂移

### `fireworks-tech-graph` 在压什么漂移

它主要压的是：

- 图示风格漂移
- 节点语义漂移
- 箭头含义漂移
- SVG 输出质量漂移

### 所以二者虽然方向不同，但工程哲学其实很像

它们都在做一件事：

> 把原本很主观、很容易随生成过程漂移的产出质量，前置成可复用规则层。

这就是它们最值得一起看的原因。

## 五、二者最值得一起借鉴的地方：都在把“审美/表达”变成资产

很多团队做 AI 编程，只把下面这些看成资产：

- Prompt
- Tool
- Workflow
- Memory
- RAG

但实际上，真正影响交付质量的，还包括：

- 页面设计控制
- 技术图表达控制

而这两个项目刚好分别覆盖了这两层。

### `awesome-design-md` 告诉我们的

- 设计风格可以文档化
- 审美要求可以版本化
- 前端质量可以通过规范文件前置约束

### `fireworks-tech-graph` 告诉我们的

- 图示表达可以技能化
- 语义形状和箭头可以标准化
- 可视化交付可以脚本化和回归化

这两者拼起来，其实就是一套很完整的“AI 产出质量控制外壳”。

## 六、如果把它们放进同一个 Agent 工作流，各自应该待在哪一层

这是实际落地时最重要的问题。

### 1. `awesome-design-md` 应该放在页面生成链路前面

典型位置是：

- 项目根目录
- 页面改版规则文档
- 新页面生成前的默认上下文

它更像：

- UI 设计系统的轻量前置层

### 2. `fireworks-tech-graph` 应该放在技术表达链路里

典型位置是：

- 写技术方案时
- 产出 README / 博客 / 架构文档时
- 给 Agent 项目生成技术图时
- 做汇报材料时

它更像：

- 技术可视化交付工具层

### 3. 如果一个团队两者都用，会形成什么效果

那就相当于同时控制了：

- 产品界面表达
- 技术结构表达

也就是说：

- 用户看到的页面更稳定
- 团队内部和对外说明的图示也更稳定

这会显著提升整个 AI 产出链的观感与说服力。

## 七、什么时候该优先参考谁

### 优先参考 `awesome-design-md`

当你的问题是：

- AI 生成的前端为什么总是“能用但没气质”
- 如何让页面设计保持统一
- 如何给新项目准备多套可复用设计约束
- 怎样把设计要求写成 Agent 可长期读取的仓库资产

### 优先参考 `fireworks-tech-graph`

当你的问题是：

- 如何让 Agent 自动生成架构图、流程图、UML 图
- 如何标准化技术图风格和语义
- 如何把图示导出做成稳定流程
- 如何让技术文档的图示产出不再依赖手工

### 两者一起参考

当你的问题是：

- 如何给 AI 编程建立一套完整的“表达质量控制层”
- 如何同时提升页面交付和技术文档交付的稳定性
- 如何把审美与表达从提示词升级成长期资产

## 八、如果以后我们自己要补这一层能力，最值得抄哪种组合

我认为最现实的组合不是二选一，而是：

### 组合 A：`DESIGN.md` + 图示 skill

也就是：

- 页面生成时读 `DESIGN.md`
- 方案说明时调用技术图 skill

这会让一个 AI 工程系统既会“做页面”，也会“讲清楚页面和系统”。

### 组合 B：规范层 + 执行层

更抽象一点看：

- `awesome-design-md` 代表规范层
- `fireworks-tech-graph` 代表执行层

这两个层次配起来很强，因为：

- 规范层定义质量目标
- 执行层负责规模化落地

### 组合 C：产品表达 + 技术表达

再用交付视角看：

- `awesome-design-md` 管产品表达
- `fireworks-tech-graph` 管技术表达

这是一个很适合补进 Agent 工作台的双案例组合。

## 九、一句话记忆

如果只用一句话记住这组对照，我建议记成这样：

> `awesome-design-md` 是把前端设计约束沉淀成仓库资产，`fireworks-tech-graph` 是把技术图生成沉淀成可执行 skill；一个负责“页面好不好看”，一个负责“系统能不能被画清楚”。
