- Purpose: provide a fast lookup table from common code smells to likely refactoring moves and review phrasing, based on Refactoring, 2nd Edition

## 一、这份速查表怎么用

这份表不是机械规则表，而是：

- 帮你在 code review 里更快命名问题
- 帮你把“这里该优化”说成更可执行的建议
- 帮你把大而空的重构意图拆成几个小动作

推荐使用顺序：

1. 先识别更像哪种坏味道
2. 再判断它带来的维护成本
3. 再从 1 到 3 个最小动作开始
4. 最后补一句测试或风险提示

## 二、坏味道 -> 优先动作 -> 评审说法

### 1. 过长函数

- 常见表现：
  - 一个函数里混着解析、判断、格式化、存取数据、输出
- 优先考虑的动作：
  - `提炼函数`
  - `拆分阶段`
  - `以查询取代临时变量`
  - `移动语句`
- 评审时可以这样说：
  - 这个函数承担了多个不同层次的工作，后续需求一改就容易牵一发而动全身，建议先做 `提炼函数`，把计算、格式化、数据准备拆开。

### 2. 重复代码

- 常见表现：
  - 相同逻辑在多个函数、多个分支、多个类里重复出现
- 优先考虑的动作：
  - `提炼函数`
  - `搬移函数`
  - `函数组合成类`
  - `函数组合成变换`
- 评审时可以这样说：
  - 这里已经有明显重复逻辑，重复会导致以后改规则时出现漏改，建议先把公共部分抽成函数，再判断它应该归属哪个模块。

### 3. 过长参数列表

- 常见表现：
  - 调用时一长串参数，阅读者很难理解含义和顺序
- 优先考虑的动作：
  - `引入参数对象`
  - `保持对象完整`
  - `改变函数声明`
- 评审时可以这样说：
  - 这个接口的参数已经超出直观可理解范围，调用方也很容易传错，建议先 `引入参数对象` 或 `保持对象完整`，把调用协议收紧。

### 4. 数据泥团

- 常见表现：
  - 几个字段总是一起出现、一起传递、一起校验
- 优先考虑的动作：
  - `引入参数对象`
  - `封装记录`
  - `提炼类`
- 评审时可以这样说：
  - 这些字段已经形成稳定组合了，继续分散传递只会让调用点越来越乱，建议把它们提升为一个明确概念。

### 5. 依恋情结

- 常见表现：
  - 某个函数大量访问别的对象数据，对自己对象反而不怎么关心
- 优先考虑的动作：
  - `搬移函数`
  - `搬移字段`
- 评审时可以这样说：
  - 这段逻辑明显更依赖目标对象的数据而不是当前对象，放在这里会让职责边界越来越模糊，建议考虑 `搬移函数`。

### 6. 发散式变化

- 常见表现：
  - 一个模块经常因为不同原因被修改
- 优先考虑的动作：
  - `提炼类`
  - `拆分阶段`
  - `搬移函数`
- 评审时可以这样说：
  - 这个模块同时承接了多种变化来源，所以每次需求变化都容易在这里汇合，建议把不同变化原因拆到更聚焦的边界里。

### 7. 霰弹式修改

- 常见表现：
  - 改一个需求，需要在很多文件、很多函数里一起改
- 优先考虑的动作：
  - `搬移函数`
  - `搬移字段`
  - `函数上移`
  - `提炼超类`
- 评审时可以这样说：
  - 当前结构让一个小需求变更需要跨很多点同步改动，维护成本偏高，建议优先找出真正的知识归属点，把相关逻辑往一个地方收。

### 8. 基本类型偏执

- 常见表现：
  - 明明有明确业务含义的概念，却只用 string、number、boolean 裸传
- 优先考虑的动作：
  - `以对象取代基本类型`
  - `封装记录`
- 评审时可以这样说：
  - 这些原始类型已经承载业务语义了，继续裸传会让校验和规则散在各处，建议提升成显式对象。

### 9. 重复的 switch / 大量条件分支

- 常见表现：
  - 相同类型判断在多个地方重复出现
- 优先考虑的动作：
  - `以多态取代条件表达式`
  - `引入特例`
  - `以子类取代类型码`
- 评审时可以这样说：
  - 类型判断已经分散复制到多个点了，后面一扩展新类型就会到处补分支，建议考虑把分支逻辑收拢为多态或特例对象。

### 10. 嵌套条件过深

- 常见表现：
  - 多层 if/else 套娃，读者很难快速看清主路径
- 优先考虑的动作：
  - `分解条件表达式`
  - `以卫语句取代嵌套条件表达式`
  - `合并条件表达式`
- 评审时可以这样说：
  - 这里的主路径被嵌套条件淹没了，建议先用卫语句把异常路径提早返回，再判断是否能继续拆条件。

### 11. 过长消息链

- 常见表现：
  - `a.b().c().d().e()` 这类调用链很多
- 优先考虑的动作：
  - `隐藏委托关系`
  - `搬移函数`
  - `移除中间人`
- 评审时可以这样说：
  - 调用方知道了太多内部导航路径，这会增加耦合，建议把常见访问路径封成更直接的接口。

### 12. 纯数据类

- 常见表现：
  - 类里主要是字段和 getter/setter，行为都散在外面
- 优先考虑的动作：
  - `封装记录`
  - `搬移函数`
  - `提炼类`
- 评审时可以这样说：
  - 当前对象更像被动数据包，相关行为都漂在外面，后续规则会越来越难收敛，建议把最核心的业务行为往对象本身收。

### 13. 过大的类

- 常见表现：
  - 一个类有很多字段、很多方法、很多变化原因
- 优先考虑的动作：
  - `提炼类`
  - `搬移字段`
  - `搬移函数`
- 评审时可以这样说：
  - 这个类已经承接了过多职责，理解和修改成本都偏高，建议先按职责边界做 `提炼类`，不要一次性大拆。

### 14. 循环让意图不清楚

- 常见表现：
  - 一个循环里混着筛选、映射、聚合、副作用
- 优先考虑的动作：
  - `拆分循环`
  - `以管道取代循环`
  - `提炼函数`
- 评审时可以这样说：
  - 这段循环混了多个意图，读起来需要不断模拟执行，建议先 `拆分循环`，再判断能否进一步变成更清晰的数据管道。

### 15. 临时变量过多

- 常见表现：
  - 中间变量很多，且意义短暂、依赖顺序强
- 优先考虑的动作：
  - `提炼变量`
  - `内联变量`
  - `以查询取代临时变量`
- 评审时可以这样说：
  - 这里的临时变量已经开始遮挡真实业务意图，建议把稳定概念提炼出来，把只服务于一行表达式的变量内联掉。

### 16. 注释在解释“代码本来应该自己说明的事情”

- 常见表现：
  - 注释不是解释业务背景，而是在翻译难读代码
- 优先考虑的动作：
  - `提炼函数`
  - `变量改名`
  - `改变函数声明`
- 评审时可以这样说：
  - 这条注释其实暴露了代码表达力不够，建议优先通过命名和结构让代码自解释，再保留真正有背景价值的注释。

## 三、评审时的标准句式

如果你想把建议说得更稳，可以固定按这个句式来：

1. 我怀疑这里更像 `某种坏味道`
2. 它带来的主要成本是 `某种维护/扩展风险`
3. 可以先从 `1-3 个小动作` 开始
4. 在动之前最好补 `测试/快照/行为校验`

例如：

- 我怀疑这里更像 `long function`，因为解析、校验和格式化耦在一起了。这样后续改任何一步都容易影响整段逻辑。建议先从 `提炼函数` 和 `拆分阶段` 开始，动之前最好补当前输出的 characterization tests。

## 四、什么时候不要硬套这张表

### 1. 不要把坏味道当成绝对错误

坏味道更像信号，不是法院判决。

### 2. 不要看见问题就直接建议大重写

这张表更适合帮助你：

- 把大问题拆成小动作

### 3. 不要在没有安全网时给出高风险重构建议

如果缺测试，要把这件事显式说出来。

## 五、一句话记忆

如果把这份速查表压成一句话，我会这样记：

> 先用坏味道给问题命名，再用小步重构动作把建议落地，而不是只说“这里该优化”。
