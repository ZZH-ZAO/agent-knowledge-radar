- Purpose: provide a reusable design template for industrial or operational Agent systems based on lessons extracted from fault-diagnosis and related project cases

## 一、这份模板是拿来干什么的

这不是一份“写给模型看的 prompt 模板”，而是一份“设计工业 Agent 系统时的分层模板”。

它适合解决的问题是：

- 我想做一个工业领域 Agent，但不知道从哪里开始分层
- 我知道要用 LLM、RAG、工具、数据库，但不知道怎么组合才合理
- 我担心做成一个会聊天但不会交付的系统

如果你以后做的场景类似这些：

- 故障诊断
- 设备巡检
- 异常分析
- 运行监控
- 维护建议
- 工业知识问答 + 报告输出

这份模板就适合直接参考。

## 二、先不要问“用什么模型”，先问这五个问题

在工业 Agent 里，技术选型通常不是第一问题，第一问题是系统目标。

### 1. 这个 Agent 的核心任务是什么

常见有三类：

- 问答型：回答设备、故障码、工艺问题
- 诊断型：结合数据判断异常原因
- 执行型：生成报告、工单、巡检结论、处置建议

很多项目失败，是因为这三类混在一起，却没有主次。

### 2. 你的主要证据来自哪里

常见有四类：

- 实时/历史业务数据库
- 设备手册和规范文档
- 外部模型或规则引擎
- 人工经验和历史案例

这决定你后面 Tool、RAG、Memory 怎么建。

### 3. 最终输出物是什么

工业 Agent 最重要的往往不是一句答案，而是：

- 报告
- 图表
- 结论摘要
- 风险提示
- 处置建议

如果不先定义输出物，系统最后很容易只有聊天体验，没有业务价值。

### 4. 错误成本有多高

如果错误成本高，就必须加强：

- 工具透明性
- 不确定性声明
- 人在环确认
- 审计留痕

### 5. 你的系统是“主诊断引擎”还是“诊断助手”

这是非常关键的一问。

- 如果它是主诊断引擎，必须非常重视规则、验证、责任边界
- 如果它是诊断助手，可以更强调效率、辅证、报告生成

## 三、工业 Agent 推荐的六层结构

### 1. 接入层

目标：

- 让用户和 Agent 交互
- 展示流式过程
- 展示任务状态和最终产物

建议技术：

- FastAPI / Node API
- SSE 或 WebSocket
- 前端任务面板 / 报告查看器

设计建议：

- 如果只是流式回答，SSE 通常够用
- 如果需要实时监控和双向控制，考虑 WebSocket
- 不要只显示最终文本，最好展示 tool 调用和任务进度

### 2. 编排层

目标：

- 让模型能完成多步任务，而不是一次性生成

建议能力：

- model -> tool -> result -> continue reasoning
- recursion limit
- checkpointer
- middleware

设计建议：

- 工业场景通常不适合“完全自由式 Agent”
- 应该给出较明确的工作流骨架
- 先把单 Agent 工作流做稳，再考虑多 Agent

### 3. Prompt / Policy 层

目标：

- 把工业流程、约束、风险边界写清楚

推荐结构：

- 角色定义
- 任务目标
- 标准工作流程
- 工具选择规则
- 输出模板
- 不确定性声明
- 升级 / 转人工条件

设计建议：

- prompt 最重要的不是“像专家”，而是“像作业规程”
- 尽量明确哪些情况不能乱答
- 不要只写身份设定，必须写决策规则

### 4. Tool 层

目标：

- 把真实业务能力显式暴露给 Agent

工业 Agent 常见工具类别：

- 数据查询工具
- 数据提取与分析工具
- 图表生成工具
- 知识库查询工具
- 外部搜索工具
- 报告生成工具
- 子 Agent 调用工具
- 规则验证工具

设计建议：

- 工具应该沿业务证据链设计，而不是按技术模块堆砌
- 优先保证工具输入输出清楚、约束清楚
- 高风险工具要明确边界和失败处理

### 5. Knowledge / RAG 层

目标：

- 提供设备知识、标准规范、故障码语义和历史经验

推荐知识源：

- 设备手册
- 操作规程
- 维修 SOP
- 故障码说明
- 标准文件
- 历史案例报告

设计建议：

- 先分清“静态知识”和“实时数据”
- RAG 通常负责补知识，不负责替代实时诊断
- 文档多了以后要考虑 rerank、metadata filter、分层索引

### 6. Memory / Audit 层

目标：

- 让会话连续
- 让任务可追溯
- 让系统可以逐渐积累经验

建议拆成三类：

- Session memory：当前会话、上下文摘要、任务状态
- Case memory：历史诊断案例、历史报告、结论模板
- Audit memory：工具调用记录、关键判断依据、版本和时间戳

设计建议：

- 不要只做聊天历史
- 工业系统尤其应该重视 audit trail，也就是审计轨迹
- 如果以后要升级智能度，最值得补的是 case memory

## 四、一条推荐的工业 Agent 工作流

下面是一条比较通用的工业 Agent 任务流。

### 第一步：明确任务与约束

例如：

- 是问故障码，还是做完整诊断
- 是游客用户，还是专业工程师
- 是只做建议，还是要生成正式报告

### 第二步：获取核心证据

来源可能包括：

- 数据库
- 实时监控数据
- 设备台账
- 历史案例

### 第三步：调用专业分析能力

可能是：

- 规则引擎
- ML 模型
- 子 Agent
- 数据分析与图表

### 第四步：补充知识证据

从：

- RAG
- 标准文档
- 网络搜索

补充语义和规范依据。

### 第五步：形成结构化结论

建议固定输出：

- 结论
- 严重程度
- 数据依据
- 推理路径
- 处置建议
- 风险提示

### 第六步：生成产物并留痕

常见产物：

- Markdown 报告
- HTML 报告
- 图表
- 工单草案

同时保留：

- 工具调用轨迹
- 时间戳
- 关键证据

## 五、什么时候该上多 Agent，什么时候先别上

### 适合上多 Agent 的情况

- 一个任务天然分成多个专业工种
- 某一块分析明显需要独立 prompt 和工具集合
- 多个子任务可以并行
- 主流程已经比较稳定

### 不适合上多 Agent 的情况

- 单 Agent 流程还没跑稳
- 工具边界还不清楚
- 任务规模不大，拆分后协调成本更高
- 只是为了“显得高级”

工业 Agent 很适合的一种多 Agent 方式是：

- 一个主 Agent 做总控
- 一个或少量子 Agent 做专业分析

这通常比一上来做 swarm 更务实。

## 六、一个可直接套用的工业 Agent 设计清单

### A. 目标定义

- 我要解决的工业任务是什么
- 最终交付物是什么
- 用户是谁
- 错误成本多高

### B. 数据与知识

- 业务数据源有哪些
- 静态文档源有哪些
- 有没有外部模型或规则系统
- 历史案例是否可用

### C. Prompt 与规则

- 是否定义了标准工作流程
- 是否定义了工具选择规则
- 是否定义了不确定性声明
- 是否定义了转人工条件

### D. 工具设计

- 每个关键业务动作是否都有工具支撑
- 工具输入输出是否清晰
- 高风险工具是否有限制
- 是否有报告生成工具

### E. 记忆与追溯

- 是否保存对话和任务状态
- 是否有上下文压缩
- 是否保存审计轨迹
- 是否沉淀历史案例

### F. 交付与可视化

- 是否生成图表
- 是否生成正式报告
- 是否支持历史回看
- 是否让用户看到过程透明性

## 七、基于 fault-diagnosis 得到的重点改进建议

如果你参考 `fault-diagnosis` 来设计下一代工业 Agent，我最建议补的能力是：

- 把 session memory 升级成 case memory
- 把基础 RAG 升级成分层知识库
- 把 `globals()` 工具共享状态升级成 session-scoped state
- 为外部依赖补足健康检查、降级和观测
- 把报告结果结构化存档，形成历史案例学习闭环

## 八、最后一句话记忆

如果用一句话记住工业 Agent 的设计重点，我建议记成这样：

> 工业 Agent 的关键不是会不会聊天，而是能不能围绕证据、流程、风险和交付物，形成一个可信的执行系统。
