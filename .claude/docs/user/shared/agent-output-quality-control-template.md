# Agent 产出质量控制层设计模板

## Summary

- Project name: agent-output-quality-control-template
- Project path: `D:\claude-code-sourcemap\.claude\docs\user\shared`
- Document type: user
- Purpose: provide a reusable design template for adding output-quality control layers to Agent systems, especially around frontend design consistency and technical-visual documentation consistency

## 一、这份模板是拿来解决什么问题的

这不是一份“让模型回答更聪明”的模板。

它要解决的是另外一类经常被忽略、但真实项目里非常痛的问题：

- 系统能做事，但页面不好看
- 页面能用，但不同页面风格不一致
- 技术方案写出来了，但图示交付很弱
- AI 每次生成的 UI 和图示质量都在漂
- 团队只能靠人工返工把东西修到能见人

这份模板适合回答的问题是：

> 当一个 Agent 系统已经开始产出页面、文档、图示或方案时，怎样给它补一层“表达质量控制层”，让它的产出更稳定、更一致、更可复用。

它特别适合下面这类项目：

- AI coding 工作流
- 设计生成工作流
- 技术文档 / 架构文档工作流
- Agent 工作台
- 需要同时产出界面和技术说明材料的产品系统

## 二、先别急着问“页面好不好看”，先问这五个问题

### 1. 你的 Agent 到底在产出什么

常见有两类：

- 产品界面
- 技术表达材料

产品界面包括：

- landing page
- dashboard
- 文档站
- 工作台页面

技术表达材料包括：

- 架构图
- 流程图
- UML
- README 配图
- 方案说明图

如果这两类产出混在一起理解，后面设计控制层时就很容易错位。

### 2. 你现在的质量问题是“能力不够”，还是“约束不够”

很多团队会误以为：

- 生成得不好，是因为模型不够强

但实际常常是：

- 设计要求太模糊
- 图示规则太模糊
- 每次输入都不一致
- 根本没有长期资产沉淀

如果问题主要是“约束缺失”，那你应该优先补质量控制层，而不是先换模型。

### 3. 你需要控制的是“风格”，还是“语义”，还是两者都要

风格控制指的是：

- 色彩
- 排版
- 布局气质
- 组件风格
- 图示视觉风格

语义控制指的是：

- 哪种节点用哪种形状
- 哪种关系用哪种箭头
- 哪种页面结构适合哪类任务
- 哪种交付物必须包含哪些要素

成熟系统通常两者都要。

### 4. 你的质量规则是一次性 prompt，还是长期仓库资产

如果规则只存在于聊天里，问题通常会是：

- 下一轮就忘
- 下一次重做就漂
- 团队成员之间无法共享
- 复盘和迭代都很困难

如果规则是仓库资产，才更可能变成：

- 可版本化
- 可 review
- 可 diff
- 可复制
- 可长期复用

### 5. 你的质量控制层是“只负责说明”，还是“还能执行与验证”

这是很关键的分水岭。

有些资产只负责：

- 说明该怎么做

有些资产还能继续往前走到：

- 生成
- 校验
- 回归
- 导出

这决定了你做的是“规范层”，还是“规范 + 执行层”。

## 三、推荐的四层质量控制结构

我建议把 Agent 产出质量控制层，至少拆成四层来想。

### 1. 产出类型层

先明确系统到底在产出什么。

建议至少分成：

- 页面类产出
- 图示类产出
- 文档类产出

这样你才不会把一个统一 prompt 硬套给完全不同的交付物。

### 2. 规范资产层

这一层负责定义质量目标。

常见形态包括：

- `DESIGN.md`
- `BRAND.md`
- `FRONTEND_RULES.md`
- 图示风格说明
- 节点形状和箭头语义说明
- 输出模板和交付规范

这层的职责是：

- 先把“什么叫好”说清楚

没有这层，后面的执行层很容易失焦。

### 3. 执行资产层

这一层负责把规范真正落到产出上。

常见形态包括：

- skill
- template
- script
- generator
- fixture

这层的职责是：

- 让规范可以被批量执行，而不只是停留在描述里

### 4. 质量验证层

这一层负责防漂移、防退化、防 silently broken。

常见形态包括：

- regression fixtures
- lint / validate scripts
- visual diff
- export validation
- 人工 review checklist

这层的职责是：

- 让质量控制不是靠感觉，而是有稳定抓手

## 四、页面表达控制层应该怎么设计

当产出物是页面时，建议优先问下面这些问题。

### 1. 页面风格有没有固定载体

建议至少有一份：

- `DESIGN.md`

可选补充：

- `BRAND.md`
- `UI_RULES.md`

这类文档里应当尽量写清楚：

- 页面整体气质
- 色彩倾向
- 字体和排版
- 留白节奏
- 组件形态
- 动效风格
- 禁忌模式

### 2. 规则是不是足够具体到代码能执行

坏规则通常是：

- 做得高级一点
- 更有科技感
- 更现代一点

好规则通常是：

- 哪类页面应该偏什么布局
- 什么圆角、边框、阴影、背景可以用
- 什么颜色和字体组合优先
- 哪些组件风格不允许出现

也就是说：

- 规则要尽量从审美感受落到实现约束

### 3. 规则有没有随项目长期存在

最好的放置位置通常是：

- 项目根目录
- Agent 默认会读取的上下文文件

如果它只能靠人每次手动提醒，那长期效果会很差。

## 五、技术表达控制层应该怎么设计

当产出物是技术图示和技术说明时，建议优先问下面这些问题。

### 1. 图类型有没有先分类

不要把所有图都当成“帮我画张图”。

建议至少区分：

- architecture
- data flow
- flowchart
- sequence
- UML
- comparison matrix
- mind map

因为不同图类型对应的布局规则完全不同。

### 2. 节点和箭头有没有语义系统

如果每次都临时决定：

- 节点画什么形状
- 箭头用什么颜色

那图很快就会失去一致性。

建议明确：

- 哪种概念映射到哪种形状
- 哪种关系映射到哪种箭头
- 什么时候必须加 legend

这样图示就会从“视觉装饰”变成“结构表达”。

### 3. 有没有导出与验证链路

技术图最怕的不是“不好看”，而是：

- 语法坏了
- 导出坏了
- 布局断了
- 新版本风格漂了

所以这层最好补上：

- validate script
- export script
- regression fixture

## 六、什么时候只需要规范层，什么时候要做到执行层

### 只做规范层

适合：

- 团队还在早期
- 主要问题是风格没有统一
- 先想建立共同语言

典型产物：

- `DESIGN.md`
- 风格说明文档

### 做到执行层

适合：

- 团队已经频繁重复生成相似产物
- 返工成本高
- 需要稳定批量输出
- 需要脚本化导出或回归验证

典型产物：

- skill
- template
- scripts
- fixtures

### 最成熟的状态

不是二选一，而是：

- 规范层定义目标
- 执行层落地产出
- 验证层兜底质量

## 七、推荐的落地步骤

### 第一步：先按产出物分类

至少先分清：

- 页面产出
- 图示产出

### 第二步：为每类产出建立默认规范文件

页面类可以有：

- `DESIGN.md`

图示类可以有：

- `DIAGRAM_RULES.md`
- 图示 style guide

### 第三步：找出最常重复的 3 个场景

例如：

- 生成 landing page
- 生成 dashboard 页面
- 生成架构图

优先把这三类做成标准化资产。

### 第四步：再决定是否补执行脚本和 fixture

如果某类产出已经高频复用，就不要只停留在规范文档层。

应该继续补：

- template
- script
- validation
- regression sample

### 第五步：把它接进 Agent 默认工作流

如果 Agent 平时根本不读取这些资产，那它们就只是“仓库里的好心建议”。

真正生效需要明确：

- 哪类任务默认加载哪些规范
- 哪类任务加载哪些模板
- 哪类任务跑哪些验证

## 八、两类典型参考案例

### 案例 A：`awesome-design-md`

最适合参考的点：

- 如何把前端设计约束沉淀成仓库资产
- 如何用 `DESIGN.md` 控制 UI 风格一致性
- 如何把设计要求从聊天提示词升级成长期规则层

它代表的是：

- 页面表达控制层

### 案例 B：`fireworks-tech-graph`

最适合参考的点：

- 如何把技术图生成做成 skill
- 如何把图示风格、语义形状、验证和导出做成完整链路
- 如何用 fixture 和脚本控制 AI 产出稳定性

它代表的是：

- 技术表达控制层

### 两个案例组合起来说明什么

它们一起说明：

> Agent 系统的质量控制，不只发生在推理层和工具层，也发生在“最终产出长什么样、怎么被表达出来”这一层。

## 九、以后分析一个新项目时，可以固定问这几个问题

### 1. 这个系统有没有单独的产出质量控制层

如果没有，很容易随着迭代越来越漂。

### 2. 这个质量控制层是页面导向、图示导向，还是两者都有

不同产出物需要不同资产。

### 3. 这些规则是临时 prompt，还是长期仓库资产

只有后者才有长期复用价值。

### 4. 它有没有执行与验证能力

如果没有，说明还停留在“规范”阶段。

### 5. 它在 Agent 主链路里的接入点是否清楚

如果接入点不清楚，再好的质量规则也只是摆设。

## 十、一句话记忆

如果把这份模板压成一句话，我会这样记：

> Agent 产出质量控制层，本质上是在 Prompt / Tool / Workflow 之外，再补一层“让页面更稳、图示更准、交付更一致”的长期资产与执行机制。
