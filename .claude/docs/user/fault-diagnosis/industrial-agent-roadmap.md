# fault-diagnosis 工业 Agent 升级路线图

## Summary

- Project name: fault-diagnosis
- Project path: `D:\fault-diagnosis`
- Document type: user
- Purpose: turn the current project analysis into a practical upgrade roadmap, explaining what should be improved first, why that order is better, and what capability each stage unlocks

## 一、先给结论：这个项目下一步最该补什么

如果只用一句话概括，我会这样说：

> 这个项目下一步最该补的，不是再多接几个模型，也不是立刻做复杂多 Agent，而是先把“证据链稳定性、案例沉淀能力、知识层质量”补起来。

原因很简单。

现在的 `fault-diagnosis` 已经有了一个比较完整的工业 Agent 闭环：

- 能接收请求
- 能调工具
- 能查数据库
- 能调外部诊断 API
- 能查知识库
- 能生成图表
- 能输出报告

也就是说，它已经不是“能不能跑起来”的问题了，而是“跑得稳不稳、能不能积累、规模上去会不会塌”的问题。

所以路线图不应该围绕“加功能数量”展开，而应该围绕三个目标展开：

- 提高诊断可信度
- 提高系统可持续演进能力
- 提高工业场景可落地性

## 二、我建议的升级顺序

我建议把后续升级拆成三层优先级：

- `P0`：先补稳定性与工程底座
- `P1`：再补知识与记忆闭环
- `P2`：最后再扩复杂协作与平台能力

这个顺序非常重要。

很多 Agent 项目最容易犯的错误是：

- 还没把底层执行链和证据链做稳，就开始加新能力
- 还没形成数据与案例沉淀，就开始做复杂多 Agent
- 还没把知识层做强，就开始追求模型切换、智能增强

对工业 Agent 来说，这样很危险，因为你会得到一个“看起来更复杂，但实际上更不可控”的系统。

## 三、P0：稳定性与工程底座

这一层的目标不是让系统更炫，而是让它更像一个可以长期运行的工业服务。

### P0-1. 把工具共享状态从 `globals()` 升级成 session-scoped state

当前问题：

- `extract_data` 和 `fig_inter` 通过 `globals()` 共享 DataFrame

为什么这是问题：

- 这种方式在单人调试时常常“看起来能用”
- 但在多会话、多请求、并发场景下，很容易出现状态污染
- 后面如果图表工具增多，问题会越来越明显

为什么优先级最高：

- 这是工具链稳定性的基础
- 不解决它，后续增加更多数据分析工具只会放大风险

建议方向：

- 按 `thread_id` 或 session 建立隔离的运行时上下文
- 把临时 DataFrame、图表中间状态放进 session-scoped store
- 明确状态生命周期和清理策略

补完后的变化：

- 图表工具链更稳
- 并发更安全
- 未来更容易增加复杂分析步骤

### P0-2. 给外部依赖补健康检查、超时策略、降级策略

当前依赖很多：

- MySQL
- PostgreSQL
- Ollama embedding
- 外部故障预测 API

问题不在于依赖多，而在于当前更像“能连就用，连不上再报错”。

为什么重要：

- 工业系统的核心问题之一不是算法，而是依赖稳定性
- 只要其中一个外部系统波动，诊断链就会变脆

建议方向：

- 启动时做依赖健康检查
- 请求时做更清晰的 timeout / retry / fallback 策略
- 区分“数据库不可用”“知识库不可用”“外部诊断模型不可用”这三类故障
- 给前端更明确的降级提示

补完后的变化：

- 出问题时系统更可诊断
- 用户知道是“诊断失败”还是“依赖失败”
- 运维成本显著下降

### P0-3. 增强观测与审计轨迹

当前系统已经有：

- SSE 透明事件
- todo 状态
- 历史消息

但还缺：

- 更结构化的工具调用日志
- 关键判断依据留痕
- 每次诊断的外部依赖状态

为什么要先做：

- 工业场景不是只要跑出来，还要能追责、复盘、定位问题

建议方向：

- 记录每次诊断调用了哪些工具
- 记录关键工具输入输出摘要
- 记录本次诊断使用的数据源、模型版本、时间戳
- 给报告和历史记录打上 trace id

补完后的变化：

- 报告更可追溯
- 出错后更容易复盘
- 更接近真实工业系统的审计要求

## 四、P1：知识与记忆闭环

这一层是把“会执行”升级成“会积累”。

### P1-1. 从 session memory 升级到 case memory

当前已有：

- checkpoint 会话记忆
- 摘要压缩
- todo 任务状态

但当前缺的是：

- 历史诊断案例记忆
- 历史报告中的经验沉淀
- 对“类似问题”的复用能力

为什么这一步非常关键：

- 工业诊断天然适合案例积累
- 一个成熟的工业 Agent，不应该每次都像第一次见这个问题

建议方向：

- 把每次诊断结果结构化存档
- 抽取字段如：设备类型、故障类型、关键指标、结论、处置建议、报告路径
- 让后续诊断可以检索相似案例

补完后的变化：

- Agent 会从“只会当前会话”升级成“有历史经验参考”
- 诊断建议会更稳定
- 后续很容易做案例推荐和复盘系统

### P1-2. 把基础 RAG 升级成分层知识体系

当前 RAG 主要是：

- PDF 手册
- FAISS 检索

它现在能工作，但规模一大就容易出现混杂问题。

建议把知识至少分成三层：

- 手册与标准层
- 故障码与处理步骤层
- 历史案例与报告层

为什么这样更好：

- 不同知识类型的用途不同
- 手册是规范知识
- 故障码是结构化领域知识
- 案例是经验知识

如果全部混在一个索引里，检索质量会变差，模型也更难区分“规范”和“经验”。

建议方向：

- 分索引或分 collection
- 加 metadata
- 按任务类型控制召回源
- 后续可以考虑 rerank

补完后的变化：

- 检索结果更干净
- 知识证据更可信
- 更适合后续扩展多设备、多文档、多案例

### P1-3. 让报告从“文件输出”升级成“结构化资产”

当前报告已经能生成 Markdown 和 HTML，这很好，但它更像输出文件，而不是可计算资产。

为什么这是问题：

- 如果报告只是文件，后续难做统计、分析、案例检索、质量评估

建议方向：

- 在生成报告的同时，把关键字段写入结构化存储
- 例如：
  - 设备
  - 故障类型
  - 严重度
  - 数据证据
  - 结论
  - 建议
  - 图表路径
  - 报告路径

补完后的变化：

- 报告系统从“文档生成器”升级成“知识资产入口”
- 后续更容易建设工业案例库

## 五、P2：复杂协作与平台能力

这一层不是现在最急，但它决定系统未来能否从单点项目成长成平台。

### P2-1. 从单一子 Agent 扩展到职责明确的多 Agent

当前已经有一个很好的起点：

- 主 Agent 做总控
- 子 Agent 做故障分析

这已经比“无脑上 swarm”成熟很多了。

下一步如果要扩，不应该追求数量，而应该追求职责拆分，例如：

- 诊断分析 Agent
- 知识补证 Agent
- 报告整理 Agent
- 维护建议 Agent

什么时候适合做：

- 当流程已经稳定
- 当不同任务确实需要不同 prompt 和工具集合
- 当单 Agent prompt 已经开始变重

### P2-2. 引入规则引擎或校验层

工业场景里，LLM 不应成为唯一判断源。

如果未来诊断责任更重，建议补一层：

- 规则校验
- 阈值校验
- 安全边界校验

为什么要做：

- 有些判断应该来自显式规则，而不是语言模型生成
- 这能让结论更稳，也更容易解释

### P2-3. 建设统一工业 Agent 平台能力

如果这个项目未来不只是一个 demo 或单点系统，而是想支持更多设备和场景，就要逐渐平台化。

平台化通常意味着：

- 更统一的工具注册
- 更统一的知识层管理
- 更统一的案例记忆管理
- 更统一的观测和审计
- 更统一的角色和权限体系

这一步为什么不放前面：

- 因为平台化应该建立在已经被验证的真实能力上
- 太早平台化，容易过度抽象

## 六、不建议现在优先做什么

除了知道该先做什么，也要知道什么不要太早做。

### 1. 不建议优先做“更多模型切换”

原因：

- 当前瓶颈不在模型切换，而在证据链稳定性和知识沉淀

### 2. 不建议优先做“更复杂的多 Agent 编队”

原因：

- 当前的单主控 + 单子 Agent 已经够用了
- 现在更缺的是底层资产化，不是更复杂协调

### 3. 不建议优先做“花哨前端”

原因：

- 工业 Agent 的核心竞争力还是诊断质量和交付可信度

## 七、一个可执行的阶段性版本规划

### 版本 A：稳住基础

目标：

- 让系统在并发、多依赖场景里更可靠

建议包含：

- session-scoped tool state
- 健康检查
- timeout / fallback
- 结构化日志

### 版本 B：形成知识闭环

目标：

- 让系统开始积累经验，而不是每次重新来

建议包含：

- 结构化报告存储
- 案例记忆库
- 分层知识库

### 版本 C：走向平台化

目标：

- 让系统支持更多设备、更多流程、更多角色

建议包含：

- 多 Agent 职责拆分
- 规则校验层
- 统一平台能力

## 八、最后一句话记忆

如果用一句话记住这份路线图，我建议记成这样：

> `fault-diagnosis` 的正确升级顺序，不是先变复杂，而是先变稳定、再会积累、最后再平台化。
