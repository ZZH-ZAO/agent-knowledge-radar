# fault-diagnosis 项目分析

## Summary

- Project name: fault-diagnosis
- Project path: `D:\fault-diagnosis`
- Document type: user
- Purpose: explain what kind of Agent system this project really is, how its prompt/tool/workflow/memory/RAG are implemented, and what useful design lessons it offers for future industrial or vertical Agent projects

## 一、先给结论：这到底是个什么项目

`fault-diagnosis` 不是一个通用 Agent runtime，也不是一个“模型接几个工具”的轻量 Demo。

它更准确的定位是：

> 一个面向工业设备故障诊断场景的垂直 Agent 工作流系统。

它的核心价值不在于发明了新的 Agent 底层循环，而在于把一套工业诊断流程压成了一个可以稳定执行的“领域作业系统”。

换句话说，这个项目真正想解决的问题不是：

- 怎么做一个最通用的 Agent

而是：

- 怎么让 Agent 在“工业设备诊断”这个任务里，按比较可信的流程走完数据查询、诊断分析、知识补充、可视化和报告生成

这是一种很重要的工程取向。很多团队一上来就想做“万能 Agent”，但在真实业务里，更常见、更容易落地的其实是这种：

- 有明确领域
- 有明确流程
- 有明确输出物
- 有明确数据源和外部系统

从这个角度看，它和 `career-ops` 很像，都是垂直工作流型 Agent；但它比 `career-ops` 更“数据驱动”和“工具密集”，因为它直接连了数据库、向量库、外部 ML API、图表生成和报告落盘。

## 二、从系统分层看，它的真正骨架是什么

如果把这个项目拆开看，它至少有六层。

### 1. 接入层：FastAPI + SSE

对应实现：

- `app.py`
- `streaming.py`

这一层解决的是“用户怎么和 Agent 对话”的问题。

这里不是普通 HTTP 一问一答，而是用了 SSE，也就是 Server-Sent Events，服务端持续把事件流推给前端。项目里把对话过程拆成了几种事件：

- `start`
- `token`
- `tool_start`
- `tool_end`
- `complete`
- `server_error`

为什么这样设计更好：

- 用户能看到 token 级别的流式输出，而不是一直转圈等最终答案
- 工具调用是透明的，前端可以展示 Agent 正在查库、查知识库、生成报告
- 这比“只返回最后一段文本”更像一个可观察系统，而不是黑盒

这种设计特别适合工业诊断场景，因为工业场景里用户往往不只关心结论，还关心：

- 它到底查了什么
- 是不是走了标准流程
- 结果是不是有依据

它的不足也很明确：

- SSE 更适合单向流，不适合复杂双向交互
- 如果以后要做更强的实时监控、设备主动告警、后台持续推送，就可能需要 WebSocket 或事件总线

### 2. 编排层：LangChain / LangGraph Agent

对应实现：

- `app.py` 中的 `create_agent(...)`
- `middleware.py`

这一层解决的是“模型怎么在任务里不断推进”的问题。

项目不是把 LLM 当成一次性文本生成器，而是把它放进一个带中间件、带工具、带检查点的 Agent 执行回路里。主模型通过：

- 接收用户输入
- 结合 system prompt
- 决定调用哪个工具
- 拿到工具结果
- 继续推理

来走完整个诊断任务。

这背后的目标是把“问答”变成“任务执行”。

为什么这很重要：

- 故障诊断不是单跳问答，而是多步任务
- 如果没有工具循环，模型只能“编”
- 如果没有状态保存，复杂流程很容易中途丢失上下文

但这个项目并没有自己重写 LangGraph runtime，它更多是使用现成 Agent 机制，把心力放在垂直流程设计上。这也说明它的创新点主要不在 runtime 核心，而在 workflow 落地。

### 3. 工具层：把领域能力外化成可调用模块

对应实现：

- `tools/sql_tools.py`
- `tools/data_tools.py`
- `tools/kb_tools.py`
- `tools/report_tools.py`
- `tools/utility_tools.py`
- `tools/subagent/`

这是全项目最重要的一层之一。

在 Agent 工程里，工具不是附属品，工具就是系统能力边界。这个项目几乎把整个业务流程都做成了工具：

- 查 SQL
- 提取 DataFrame
- 生成 matplotlib 图
- 查知识库
- 网络搜索
- 生成 Markdown 报告
- 生成 HTML 报告
- 调用故障诊断子 Agent

为什么这样设计更好：

- 领域能力被显式暴露，模型知道自己可以“做什么”
- 每个能力单独维护，比把所有逻辑揉进 prompt 更可控
- 更容易替换某个环节，比如把知识库换掉、把报告模板换掉

但它也带来一个典型挑战：

- 当工具越来越多时，模型的工具选择成本会上升
- 如果工具说明写得不清楚，模型容易选错
- 工具之间的状态共享会变复杂

项目里已经能看到这个问题的一个典型影子：

- `extract_data` 和 `fig_inter` 通过 `globals()` 共享 DataFrame

这说明作者在努力把数据分析链拆成工具，但工具间状态还没有抽象成更稳的 session context。现在能工作，但如果以后并发更强、会话更多、工具更复杂，这会成为潜在风险。

### 4. Prompt 层：把诊断流程写成操作规程

对应实现：

- `prompts/system_prompt.py`
- `prompts/dynamic_prompt.py`
- `tools/subagent/system_prompt.py`

这个项目的 prompt 不是“写得很花”，而是“写得很像作业指导书”。

这是它最值得学的地方之一。

主 prompt 里写了很多关键内容：

- 用户身份适配
- DCMA 查询流程
- 标准故障诊断流程
- 工具使用速查表
- 工具选择决策表
- 回答格式模板
- 不确定性声明要求

这本质上是在做一件很重要的事情：

> 把领域操作规程编译进 Agent 的认知入口。

为什么这样做更好：

- 让模型不只是“知道工具存在”，而是知道“什么情况下先用哪个”
- 减少工具误用，比如明确 DCMA 查询不能走某些图表工具
- 让回答风格和输出结构更稳定

这比单纯说“你是工业专家，请认真回答”强太多，因为后者只有身份，没有过程。

这里的一个核心启发是：

- 在垂直场景中，prompt 最重要的作用不是装人设，而是编码流程、约束和决策规则

它的边界也要看清：

- prompt 写得越细，越依赖流程稳定
- 如果将来设备类型、诊断路径、数据库结构变化很大，这种写死在 prompt 里的流程会变得难维护
- 更进一步时，部分规则可能要下沉成真正的 policy engine 或 task planner，而不只是文本规范

### 5. Memory 层：会话状态与上下文压缩

对应实现：

- `AsyncPostgresSaver` / `InMemorySaver`
- `SummarizationMiddleware`
- `/ai/history/*`
- `/api/todos/{thread_id}`

这个项目的 memory 不是“长期人格记忆”，而是更偏工程化的会话记忆。

主要包括三种：

#### 第一种：检查点持久化

通过 PostgreSQL 保存 LangGraph checkpoint。

它解决的是：

- 用户下次回来还能接着看
- 前端能回放历史消息
- 任务和消息状态不会因为进程结束就丢失

#### 第二种：上下文压缩

通过 `SummarizationMiddleware` 在 token 达到阈值后做摘要。

它解决的是：

- 长对话上下文越来越大，成本越来越高
- 如果完全不压缩，复杂任务会被上下文长度拖死

#### 第三种：任务状态记忆

通过 `TodoListMiddleware` 保存任务清单和状态。

它解决的是：

- 让 Agent 在多步任务里有“当前进度感”
- 让前端能展示任务条，增加可解释性

这套 memory 设计的目标很清楚：

- 不是做人设记忆
- 不是做知识沉淀
- 而是保障长任务会话的连续性、可视化和可恢复性

这对工业场景很合理，因为工业场景通常更关心“这次诊断任务是否连贯可追溯”，而不是“Agent 记不记得你上周喜欢什么风格”。

它的不足在于：

- 没有显式的长期经验记忆抽取
- 没有把历史案例沉淀成可检索经验
- 没有把诊断结果反向沉淀到知识层

所以它有 session memory，但还没有 learning memory。

### 6. RAG 层：FAISS + PDF 手册知识检索

对应实现：

- `knowledge_base.py`
- `tools/kb_tools.py`
- `rebuild_kb.py`
- `pdfs/`

这里的 RAG 很典型，也很实用：

- 从 PDF 手册加载文档
- 切 chunk
- 用 Ollama embedding 做向量化
- 存进 FAISS
- 查询时返回前几个相关片段

这个 RAG 的目标不是回答所有问题，而是补足“故障码含义、处理步骤、设备手册知识”这一类静态知识。

为什么这样做有意义：

- 工业诊断往往同时需要实时数据和静态手册
- 只看实时数据，缺少规范和经验语义
- 只看手册，又不知道当前设备到底发生了什么

所以这个项目形成了一种很有代表性的混合诊断模式：

- 实时/历史业务数据 → 数据事实
- 外部 ML API → 模型诊断判断
- 本地知识库 → 设备知识补充
- 网络搜索 → 最新标准补充

这其实已经不是单纯的 RAG，而是多来源证据拼接。

但它当前的 RAG 还比较基础，边界也明显：

- 没有 rerank
- 没有多路召回
- 没有 metadata 过滤
- 没有案例库与手册库分层
- 结果直接拼片段，缺少更强的证据整理

这意味着当知识库规模更大、文档更杂时，命中质量可能开始下降。

## 三、这个项目的 workflow 编排，真实发生在什么层面

这个项目最值得你理解的，不只是“有哪些工具”，而是工作流真正发生在哪几层。

### 1. 单轮 query loop

这是最底层的单次任务推进：

- 用户输入
- 模型判断
- 调用工具
- 获取结果
- 再推理
- 输出最终答案

对应实现主要在：

- `app.py`
- `streaming.py`

这个层次决定的是“Agent 能不能真的把任务跑起来”。

### 2. 会话级编排

这一层处理的是“多轮对话怎么不断线”。

对应实现主要在：

- PostgreSQL checkpoint
- `SummarizationMiddleware`
- history API

这个层次的目标不是更聪明，而是更稳：

- 长会话不断
- 上下文不过载
- 历史能回看

### 3. 任务级编排

这一层其实是项目里最有业务味道的一层。

对应实现主要在：

- `TodoListMiddleware`
- system prompt 中的标准工作流
- 各工具的职责分拆

它让 Agent 不只是“自由探索”，而是尽量沿着一个固定诊断流程走：

- 先获取时间
- 再规划任务
- 再诊断
- 再补知识
- 再出报告

这就是典型的 workflow-first 设计。

### 4. 子 Agent 编排

对应实现主要在：

- `tools/subagent/agent.py`
- `tools/subagent/api_tool.py`

这里的多 Agent 不是通用 swarm，而是非常务实的专门分工：

- 主 Agent 负责总流程、知识补充、报告汇总
- 子 Agent 负责故障诊断这块专业流水线

为什么这样做更好：

- 把复杂、专业、重约束的诊断任务独立封装
- 降低主 Agent prompt 的复杂度
- 让专业分析可以单独进化

这是一种很适合行业 Agent 的多 Agent 方式：

- 不是先追求数量
- 而是先追求职责边界

## 四、它最值得学的亮点是什么

### 1. Prompt 不是装饰，而是 SOP

SOP 是 Standard Operating Procedure，也就是标准作业流程。

这个项目最值得学的地方，就是把 prompt 写成操作规程，而不是写成空泛的人设说明。

### 2. 工具能力直接对齐业务流程

它不是“为了有工具而有工具”，而是每个工具都能对应到业务流程中的一段动作。

这让 Agent 不像聊天机器人，而像一个执行系统。

### 3. 诊断结果不是只停在对话里，而是落成报告

很多 Agent 系统做到最后只剩一段聊天文本，而这个项目会生成：

- Markdown 报告
- HTML 报告
- 图表文件

这非常重要，因为工业场景真正需要的是交付物，不只是回答。

### 4. 透明化执行过程

SSE 事件流 + todos + tool_start/tool_end，让用户能看到它怎么工作的。

这对高风险业务特别重要。

## 五、它有哪些明显欠缺和未来瓶颈

### 1. 还没有真正的长期学习闭环

它能记住会话，但不能把高价值诊断案例沉淀成经验资产。

如果以后想更强，应该考虑：

- 案例记忆库
- 诊断结果结构化存档
- 从历史报告中抽取经验模式

### 2. RAG 还偏基础

适合当前规模，但不适合更复杂知识域。

如果未来文档更多、更杂，可能要补：

- rerank
- metadata filter
- 分层知识库
- 案例库与手册库分离

### 3. 工具间状态共享不够稳

`globals()` 共享 DataFrame 的方式能跑，但不够优雅，也不够安全。

如果以后并发更高、图表任务更多，这会成为问题。

### 4. 多 Agent 还属于“局部专用”，不是平台能力

现在的子 Agent 很务实，但还没有形成更通用的 coordinator-worker 机制。

这不一定是缺点，因为当前阶段也许没必要；但如果未来要支持更多设备和更多分析工种，就可能要升级。

### 5. 很依赖外部系统稳定性

这个项目强依赖：

- MySQL
- PostgreSQL
- Ollama embedding
- 外部故障预测 API

这意味着它不是一个轻部署系统，而是一个多依赖协同系统。工程上要更重视：

- 健康检查
- 降级策略
- 依赖观测
- 超时与重试

## 六、如果把它放进案例库，最适合怎么归类

我会把它归类为：

- Primary label: `vertical-workflow`
- Secondary label: `tool-runtime`
- Secondary label: `RAG-assisted`

也就是说，它首先是一个垂直工作流型 Agent，其次是一个工具驱动很强、并带有知识增强的系统。

它最适合被拿来学习的场景是：

- 你想做行业 Agent，而不是通用聊天助手
- 你想把数据库、知识库、可视化、报告输出串成闭环
- 你想理解“如何把 Agent 嵌进真实业务作业流程”

## 七、对以后做 Agent 项目的可迁移建议

如果以后你要参考这个项目给别的 Agent 项目提建议，我会提炼成下面几条。

### 1. 先确定你是在做 runtime，还是在做 vertical workflow

如果目标是行业落地，很多时候后者更重要。

### 2. Prompt 优先编码流程和约束，不要只写身份设定

垂直场景里，流程感比人设感重要得多。

### 3. 工具设计要围绕交付链路，而不是围绕技术炫技

最好的工具集合，是从“数据获取 → 分析 → 补证 → 产物输出”倒推出来的。

### 4. 会话记忆、任务记忆、知识记忆要分开设计

这个项目已经把前两者做出来了，后面如果升级，最值得补的是第三者。

### 5. 行业 Agent 的最终价值通常在“产物”上

对工业诊断来说，聊天只是入口，真正有价值的是：

- 图表
- 报告
- 可追溯结论
- 可执行建议

## 八、最后一句话怎么记住它

如果用一句话记住这个项目，我建议记成这样：

> `fault-diagnosis` 不是在发明新的 Agent 引擎，而是在把工业故障诊断流程编译成一个带数据、带知识、带报告输出的垂直 Agent 作业系统。
