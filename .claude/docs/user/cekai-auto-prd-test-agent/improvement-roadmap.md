# ByteDance--Auto_prd_test_agent 改进路线图

## Summary

- Project name: ByteDance--Auto_prd_test_agent
- Project path: `D:\测开\ByteDance--Auto_prd_test_agent`
- Document type: user
- Purpose: explain how this project can evolve from a useful prompt-and-RAG testing workbench into a more robust, scalable, and reusable testing Agent system

## 一、先给结论：这个项目最值得改的，不是“再加一个模型”，而是把产品工作流做厚、把系统边界做清

如果只从表面看，很多人第一反应会是：

- 再换个更强模型
- 再多加一点 Prompt
- 再接一个知识库

但真正从系统角度看，这个项目的主要瓶颈并不在“模型太弱”，而在下面四件事：

1. 编排逻辑过度集中在 UI 层
2. RAG 还停留在轻量检索增强阶段
3. 历史资产能回存，但还不能真正形成经验学习
4. 评审已经有了，但还没有形成质量闭环和组织级复用

所以这类项目如果想继续变强，正确方向不是“堆功能”，而是：

> 从单点生成工具，升级成测试知识与质量闭环系统。

## 二、改进目标应该分成三层，而不是混在一起

很多团队做升级时容易把目标混掉。  
这个项目更适合按三层来定目标。

### 第一层：把现在这套工作台做稳

目标是：

- 更稳
- 更可维护
- 更容易扩展

这一层重点不是追求更炫，而是把当前能跑的东西做成可靠产品。

### 第二层：把“生成测试用例”升级成“测试资产生产线”

目标是：

- 不只生成
- 还要评审、筛选、归档、复用、追踪质量

这一层重点是从一次性结果走向资产化。

### 第三层：把它升级成组织级测试知识系统

目标是：

- 让模型越来越贴近团队规范
- 让历史案例沉淀成经验
- 让不同项目组共享有效测试模式

这一层重点是知识工程和质量运营，而不是单次回答效果。

## 三、最优先的改进：把 UI 编排下沉到服务层

### 1. 当前问题是什么

现在的编排中心主要在 [ui/main.py](D:\claude-code-sourcemap\.claude\docs\user\cekai-auto-prd-test-agent\analysis.md) 对应分析中已经讲过，本质上是：

- 文件上传逻辑在 UI
- RAG 检索和过滤在 UI 串联
- 主生成流程在 UI 组装
- 评估流程也在 UI 发起
- 状态大量依赖 `st.session_state`

这在早期 Demo 阶段没问题，但后面会出现几个明显问题：

- 文件一多，页面代码会越来越重
- 调试时很难清晰区分“展示错误”和“业务逻辑错误”
- 以后如果要做 API、批处理、定时任务、多人共享会话，很难复用

### 2. 应该怎么改

建议拆成三层：

1. `ui/`
   只负责交互和展示
2. `services/`
   负责业务流程
3. `core/`
   负责底层能力，如 LLM、RAG、评估器

可以新增类似这样的结构：

```text
services/
  ingestion_service.py
  retrieval_service.py
  generation_service.py
  evaluation_service.py
  archive_service.py
```

每一层的职责很清楚：

- `ingestion_service`
  负责把上传材料转成标准输入
- `retrieval_service`
  负责知识召回、过滤、排序
- `generation_service`
  负责主生成和微调逻辑
- `evaluation_service`
  负责 QA critic 流程
- `archive_service`
  负责案例归档与回流

### 3. 为什么这样更好

因为这样做以后：

- Streamlit 只是“壳”
- 业务逻辑可测试
- 将来更容易换成 FastAPI、Web 前后端分离、异步任务队列

### 4. 适用于什么新场景

- 批量处理多个 PRD
- 通过 API 接入 Jira / 飞书 / 企业微信
- 后台跑长任务
- 一份测试方案由多人共同查看

### 5. 可能的代价

- 初期重构成本上升
- 代码文件数变多
- 对项目组织能力要求更高

但这类代价是值得的，因为这是把“能跑”升级成“能长期维护”的关键一步。

## 四、第二优先级：把 RAG 从“能查”升级成“可信地查”

### 1. 当前问题是什么

现在的 RAG 流程大致是：

1. 切片
2. 向量召回
3. 把召回片段交给 LLM 过滤

这个流程够实用，但还不够强。问题主要在于：

- 缺少 metadata 过滤
- 历史案例和规范文档虽然分集合，但检索策略还比较粗
- 没有 rerank
- 没有文档版本概念
- 没有质量标记

这意味着当知识库变大以后，会逐渐出现：

- 查到但不准
- 查到了旧规范
- 查到很多“相似但无用”的案例

### 2. 应该怎么改

我建议把知识层升级成“两库四类元数据”。

两库：

1. 规范库
2. 案例库

四类元数据：

1. 来源类型
   规范、案例、模板、实验草稿
2. 业务域
   登录、支付、订单、权限、风控等
3. 质量等级
   草稿、审核通过、黄金样本
4. 版本状态
   当前有效、历史废弃、待确认

然后在召回时分两步：

1. 先按元数据约束召回范围
2. 再做语义召回和 rerank

### 3. 为什么这样更好

因为企业知识库真正难的不是“向量化”，而是“控制哪类知识该在什么场景被召回”。

例如：

- 安全测试时，应该优先召回安全规范和高质量历史案例
- 登录模块测试时，不应该被支付模块的高相似片段污染
- 新版本规范应该压过旧版本文档

### 4. 新场景收益

- 多业务线共用一套平台
- 知识库规模持续增长
- 团队希望沉淀 golden sample
- 需要做团队级测试规范治理

### 5. 可能不足

- 元数据维护本身需要流程
- 文档接入时要多做清洗与标注
- 如果团队不维护规则，知识库会很快变乱

所以 RAG 做强，不只是技术问题，也是知识治理问题。

## 五、第三优先级：把“历史案例库”升级成“经验记忆系统”

### 1. 当前问题是什么

现在项目能把结果存回 `history_cases`，这是好事。  
但它现在更像：

- 存档
- 回查
- 参考

还不像真正的经验记忆。

因为真正的经验记忆至少应该回答：

- 哪些测试模式最常被人工保留
- 哪些输出经常被改
- 哪些 PRD 类型容易漏边界场景
- 哪些历史案例能作为高质量模板

### 2. 应该怎么改

建议把历史案例拆成三层：

1. 原始案例层
   保存 PRD、生成结果、最终结果、修改记录
2. 模板层
   抽出高复用测试模式
3. 反馈层
   记录人工采纳率、修改率、被删除率、评审分数

可以为每个案例增加字段：

- `accepted_by_human`
- `edited_after_generation`
- `evaluation_score`
- `business_domain`
- `quality_tag`
- `derived_template_id`

### 3. 为什么这样更好

因为“存下来”不等于“学会了”。

只有当你能区分：

- 哪些是高价值案例
- 哪些只是临时结果
- 哪些模式值得抽象成模板

这个系统才会越来越像“会成长的测试系统”。

### 4. 新场景收益

- 团队可以快速复用已验证模式
- 新成员更容易上手
- AI 输出可以越来越贴近团队真实习惯

### 5. 可能的问题

- 需要更多数据结构设计
- 需要人工给案例做标注或至少半自动打标签
- 如果没有运营过程，系统可能只是“多存了些字段”

所以 memory 升级的核心不是加一个向量库，而是设计反馈信号。

## 六、第四优先级：把 AI 评审从“单次打分”升级成“质量闭环”

### 1. 当前问题是什么

现在的 `evaluator.py` 已经很不错，它能做：

- 覆盖率评估
- 逻辑问题检查
- 重复项检查
- 建议输出

但它现在更像“单次审核员”，还不是“质量管理系统”。

缺的关键是：

- 评审结果没有反向驱动后续生成策略
- 没有形成长期统计
- 没有把高分结果沉淀为模板
- 没有把低分常见错误沉淀为规则

### 2. 应该怎么改

建议引入三种闭环动作：

1. 结果归因
   记录低分原因属于哪类问题
2. 规则回写
   把高频问题变成 Prompt 或代码规则
3. 模板沉淀
   把高分案例变成推荐模板

可以额外增加：

- 评审维度统计看板
- 模块级质量趋势
- 常见漏测点排行榜

### 3. 为什么这样更好

因为 AI 评审真正有价值的，不是“这次说你错了”，而是“以后更不容易再犯同样的错”。

这就是从工具走向系统的差别。

### 4. 新场景收益

- 团队可以分析哪些模块总是难测
- 测试负责人可以看到 AI 的真实价值
- 可以逐步形成“组织的测试设计经验库”

### 5. 潜在问题

- 如果评审本身不稳定，错误反馈会污染规则
- 需要人工抽检高影响规则

所以评审闭环最好是“AI 提议，人审核后再沉淀”。

## 七、第五优先级：引入更正式的工具层和任务层

### 1. 当前问题是什么

现在这个项目更像固定流水线，流程大多由代码写死。  
这在当前场景可行，但未来如果接入更多系统，会越来越僵硬。

例如以后可能会接：

- Jira / 禅道 / TAPD
- TestRail / 用例管理系统
- Git 仓库
- 接口定义平台
- 自动化测试脚本生成器

到那时，仅靠当前这种 UI 串联方式会开始吃力。

### 2. 应该怎么改

建议分两步升级，不要一步到位搞太重。

第一步：

- 做轻量 tool registry
- 把各类能力统一成工具接口

例如：

- `retrieve_specs`
- `retrieve_history_cases`
- `generate_test_cases`
- `evaluate_test_cases`
- `archive_case`
- `export_case`

第二步：

- 再考虑让模型在部分场景里决定工具调用顺序

也就是从：

- code-orchestrated pipeline

逐步升级到：

- semi-agentic workflow

### 3. 为什么这样更好

因为这能保留当前项目的稳定性，同时逐步引入更高自治能力，而不是突然重写成一个复杂 Agent runtime。

### 4. 新场景收益

- 更容易接入外部平台
- 更容易做批处理
- 更容易复用同一能力到别的界面

### 5. 潜在不足

- 工具描述写不好，会让后续 Agent 化效果变差
- 如果业务流程本来很固定，过早做重型 agent 化会徒增复杂度

所以这一步要强调“渐进式升级”，不是“全部推倒重来”。

## 八、第六优先级：把输出从“测试用例文本”升级成“测试工程资产”

### 1. 当前问题是什么

现在已经支持导出：

- CSV
- JSON
- YAML
- Markdown

这很好，但还主要是“文档资产”。  
如果往更实战方向走，应该继续往“工程资产”推进。

### 2. 可以怎么改

后续可以增加：

1. 自动化脚本草稿生成
   例如 Pytest、Playwright、接口测试模板
2. 测试点追踪矩阵
   PRD 条目 -> 测试点 -> 用例 -> 执行状态
3. 缺陷回写建议
   低覆盖区域自动提示重点补测
4. 用例版本对比
   新一轮生成与历史版本差异对比

### 3. 为什么这样更好

因为测试团队真正需要的，往往不是“几条好看的 JSON”，而是：

- 能继续执行
- 能继续追踪
- 能进系统流转

也就是说，最终价值在交付链路，不在文本本身。

## 九、如果只让我排一个改进优先级，我会这样排

### P0：先做架构稳固

1. UI 编排下沉到 service 层
2. 状态管理更清晰
3. 把生成、检索、评估拆成可测试模块

这是“先打地基”。

### P1：再做知识和质量闭环

1. RAG 加 metadata、版本、质量标签
2. 历史案例加反馈字段
3. 评审结果形成闭环回写

这是“让系统开始积累组织能力”。

### P2：最后做更强 Agent 化

1. 统一工具接口
2. 引入部分半自治工具调用
3. 接入外部测试平台和项目管理平台

这是“把它从工作台升级成平台”。

## 十、如果把它往工业级或组织级产品方向推，最终会长成什么样

我认为这类项目最好的终局，不是变成一个“很会聊天的测试机器人”，而是变成：

> 一个围绕 PRD、规范、历史案例、人工反馈、AI 评审、自动化脚本和质量统计共同运转的测试知识生产系统。

换句话说，它未来最值得长出来的能力不是：

- 更会说

而是：

- 更会沉淀
- 更会复用
- 更会约束
- 更会持续改进

## 十一、一句话记住它最该怎么改

> `ByteDance--Auto_prd_test_agent` 下一步最该做的，不是继续堆 Prompt，而是把“生成工具”升级成“测试知识与质量闭环系统”。
