# ByteDance--Auto_prd_test_agent 项目分析

## Summary

- Project name: ByteDance--Auto_prd_test_agent
- Project path: `D:\测开\ByteDance--Auto_prd_test_agent`
- Document type: user
- Purpose: explain what kind of Agent system this project really is, how its prompt/tool/workflow/RAG/memory/evaluation layers work, and what reusable design lessons it offers for future vertical Agent projects

## 一、先给结论：这到底是不是一个 Agent 项目

如果只看名字，你可能会以为它是一个“自动测试 Agent”。  
但真正读完代码以后，更准确的判断是：

> 它首先是一个面向“PRD 转测试用例”的垂直 AI 工作流系统，其次才是一个带有 Agent 味道的应用。

也就是说，它不是 `claude-code-sourcemap`、`deer-flow` 那种“通用 Agent runtime”，不是那种重点解决“模型如何稳定推理、如何标准化 tool calling、如何组织多 Agent 控制面”的系统。

它真正解决的问题是：

1. 用户上传 PRD、PDF、图片、规范文档。
2. 系统从知识库和历史案例里找参考。
3. LLM 按测试工程方法生成结构化测试用例。
4. 用户继续对话式微调。
5. AI 再扮演 QA 审核员，给这些用例打分和指出遗漏。
6. 用户确认后，把这次结果回流到历史案例库。

所以它最准确的标签应该是：

- Primary label: `vertical-workflow`
- Secondary label: `RAG-first`
- Secondary label: `human-in-the-loop`

这类项目的价值，不在于“让模型自由行动”，而在于“把一条业务交付链压缩成一套可重复执行的 AI 流程”。

## 二、项目真正的系统骨架是什么

从代码结构上看，这个系统大致可以拆成六层：

1. 产品交互层：`ui/main.py`、`ui/sidebar.py`、`ui/components.py`
2. Prompt 规程层：`config/prompts.py`
3. LLM 访问层：`core/llm_client.py`
4. RAG / 知识层：`core/rag_engine.py`
5. 评审与反馈层：`core/evaluator.py`
6. 配置与部署层：`config/settings.py`、`requirements.txt`、Docker 配置

这里最重要的一个认识是：

> 这个项目的“编排中枢”不在后端服务，也不在独立 Agent runtime，而是在 Streamlit UI 层。

这会直接影响我们对它的评价。

优点是：

- 开发快，演示效果直接
- 产品交互和推理流程绑得很紧，适合快速做出“可用工具”
- 很多状态都可以直接借 Streamlit `session_state` 管起来

代价是：

- 编排逻辑容易堆在 `ui/main.py`
- 前后端边界不清
- 后期如果要做 API 化、任务队列化、多人协作化，会比较难拆

所以这个项目更像“工作台式 AI 产品”，而不是“平台级 Agent 内核”。

## 三、Prompt 设计：它不是写人设，而是在写测试作业规程

这个项目最值得学的一点，不是某一句 prompt 写得多华丽，而是它把 Prompt 当成“标准作业程序”。

对应文件：

- `config/prompts.py`

里面至少有五类核心 Prompt：

1. `CORE_SYSTEM_PROMPT`
   负责主生成流程
2. `SUMMARY_PROMPT`
   负责给知识条目或案例生成摘要标题
3. `MULTIMODAL_PARSE_PROMPT`
   负责把图片 / PDF 转成可检索文本
4. `EVALUATOR_SYSTEM_PROMPT`
   负责 AI 评审员角色
5. `RAG_FILTER_PROMPT`
   负责对召回内容做二次过滤

### 1. 这一层的目标是什么

目标不是简单告诉模型“你是资深测试专家”，而是让模型在执行时遵守一套测试设计方法。

例如在 `CORE_SYSTEM_PROMPT` 里，项目明确写了：

- 先区分闲聊问答和测试生成场景
- 测试生成时要遵守 pairwise、边界值分析等策略
- 输出必须是完整 JSON 数组
- 解释和结构化数据要分离

这意味着 Prompt 在这里承担了三种职责：

- 角色职责定义
- 过程约束定义
- 输出契约定义

### 2. 为什么这样做更好

因为在垂直场景里，模型最容易出问题的地方，不是“不够聪明”，而是“不够守规矩”。

举个直观的理解：

- 如果你只说“你是测试专家”，模型会倾向于自由发挥
- 如果你说“你必须做 Pairwise、边界值、按 JSON 合同输出”，模型就更像在执行流程

这对于测试生成尤其关键，因为测试工作不是单纯写文字，而是要兼顾：

- 覆盖率
- 可执行性
- 格式稳定性
- 与历史规范的一致性

### 3. 它启发了什么新的场景

这种 Prompt 设计特别适合下面这些场景：

- 有明确 SOP 的行业流程
- 输出必须结构化
- 人工需要继续接管和修改
- 结果需要进知识库复用

比如：

- 法务合同审查
- 招聘 JD 审核与面试题生成
- 工业巡检报告生成
- 客服 SOP 响应建议

这些场景里，Prompt 不应该只是“人设”，而应该是“程序化规程”。

### 4. 它会在哪些场景变得不够

也要看到它的边界：

- 规则越来越多时，Prompt 会变长、变脆
- 一旦业务规则经常变更，纯文本维护成本会上升
- 当流程分支非常复杂时，仅靠 Prompt 很难替代真正的 planner / policy engine

所以这个项目代表的是一个很实用但也很典型的阶段：

> 先用 Prompt 编码规则，把垂直工作流做出来；等复杂度继续上升，再考虑把一部分规则下沉到代码和策略引擎。

## 四、Function Calling / Tool Calling：它其实没有“正式工具调用协议”

这是一个很关键、也很容易被误判的点。

很多人看到“有 RAG、有评估、有多模块”，就会下意识觉得它是一个工具调用 Agent。  
但认真看代码会发现：

> 这个项目基本不是“模型输出 tool call，再由 runtime 调度”的体系。

它更像是：

- Python 代码显式串联各个模块
- LLM 被嵌入在多个流程节点里
- 工具调用由 UI 和函数逻辑决定，而不是由模型通过 formal function call 决定

对应实现：

- `ui/main.py`
- `core/rag_engine.py`
- `core/evaluator.py`
- `core/llm_client.py`

### 1. 为什么说它不是正式 Tool Calling

因为这里没有看到典型的：

- tool schema 注册
- 模型返回结构化 tool call
- runtime 执行并把 tool result 回填给模型
- 多轮 tool loop

它的实际运行方式更像：

1. Python 先做文件解析、召回、上下文准备
2. 再把整理好的内容交给模型
3. 模型产出 JSON
4. Python 再解析 JSON 和做展示
5. 需要评估时，Python 再调用另一个评估 prompt

所以这更接近“LLM-enhanced pipeline”，不是“tool-calling agent runtime”。

### 2. 这种做法为什么仍然有价值

因为对很多业务产品来说，最重要的不是让模型自由调工具，而是让流程稳定。

这样做的好处是：

- 可控
- 易调试
- 每一步更容易定位错误
- 对初期产品和 Demo 很友好

对于 PRD 转测试用例这种任务，工具路线其实比较固定：

- 上传文档
- 检索
- 生成
- 修订
- 评估
- 归档

既然路线相对固定，未必需要一个高度自治的工具调度框架。

### 3. 哪些新场景会需要升级成正式 Tool Calling

如果未来出现以下场景，这套做法就可能不够：

- 模型要自己决定何时查知识库、何时查历史案例
- 模型要根据中间结果继续调用更多分析工具
- 同一轮里要动态组合多个工具
- 要引入更多外部系统，比如 Jira、TestRail、代码仓库、接口测试平台

这时候就更适合升级到：

- function calling
- tool registry
- tool result feedback loop
- planner/executor 分层

所以这个项目适合拿来学“固定工作流中的 LLM 嵌入”，不适合当作“通用 Tool Calling 架构”的代表案例。

## 五、Workflow 编排：真正发生在 UI 层，而且至少有四段流程

这部分是最需要讲透的。

如果你只说“这个项目有 workflow”，其实等于没说。真正要理解的是：

> 这个项目的 workflow 不是抽象存在的，它具体发生在几个节点、由谁驱动、每一段的目标是什么。

### 1. 文档接入与上下文准备流

对应位置：

- `ui/main.py`
- `core/rag_engine.py`

流程大致是：

1. 用户上传文件
2. 系统判断文件类型
3. 图片 / PDF 通过 Gemini 多模态能力转文本
4. 拼出 PRD 预览文本
5. 用这份文本去查知识库和历史案例
6. 把召回结果交给 LLM 再过滤一次
7. 把清洗后的上下文放进 `session_state`

这一段解决的是：

- 用户材料怎么变成机器可用语境
- 知识库怎么和本轮任务结合
- 召回噪声怎么控制

这里最值得学的是“两段式检索”：

- 第一段：向量粗召回
- 第二段：LLM 语义过滤

虽然它没有现代 RAG 里很规范的 rerank 设计，但它已经体现出一个很实用的思想：

> 对业务场景来说，检索不是“召回来就行”，而是“要把能污染生成的噪声先压掉”。

### 2. 主生成流

对应位置：

- `ui/main.py`
- `config/prompts.py`
- `core/llm_client.py`

流程大致是：

1. 组装 `get_initial_prompt`
2. 把 PRD、本轮参考上下文、上传内容一起发给模型
3. 使用 `CORE_SYSTEM_PROMPT`
4. 得到包含解释和 JSON 的回复
5. 从回复里抽取 JSON
6. 把结构化结果放入右侧预览

这段的目标很清楚：

- 不是聊天
- 是生成一个可继续编辑的结构化测试资产

所以它有一个很强的产品意识：

> LLM 不是最终界面，结构化结果才是最终资产。

### 3. 人工微调流

对应位置：

- `ui/main.py`
- `PromptManager.get_refinement_prompt`

流程是：

1. 用户在聊天框输入修改要求
2. 系统把当前上下文和修改指令交给模型
3. 模型重新输出“解释 + 完整 JSON”
4. UI 再次抽取 JSON 并刷新结果

这一段非常重要，因为它反映了这个项目不是“一次性生成器”，而是一个“共创工作台”。

为什么这样好：

- 测试设计天然需要人参与
- 纯自动生成很难一次到位
- 用户更愿意改一个八成对的结构化结果，而不是从零开始写

这就是典型的 Human-in-the-Loop。

### 4. AI 评审流

对应位置：

- `core/evaluator.py`
- `PromptManager.get_evaluation_prompt`
- `ui/main.py`

流程是：

1. 把当前生成结果、PRD、RAG 上下文拼起来
2. 可选加上 golden cases
3. 调用独立评审 Prompt
4. 输出结构化评审报告
5. 在 UI 中展示得分、覆盖缺口、逻辑问题、重复项、建议

这一段比很多类似项目成熟。

因为它不是让“生成模型自己说自己好不好”，而是做了一层角色切分：

- 生成者
- 审核者

这虽然不是真正的多 Agent runtime，但已经有了“角色分工”的思想。

### 5. 资产回流流

对应位置：

- `core/rag_engine.py`
- `ui/main.py`

用户确认后的案例会回流到 `history_cases` 集合，成为后续检索的参考。

这段流程代表一个非常重要的产品思路：

> 好的垂直 Agent 不应该只会“回答”，还应该能把高价值结果沉淀成以后复用的资产。

## 六、RAG 检索增强：它是“本地可落地”的 RAG，不是“先进 RAG 架构”

项目 README 里把自己写成了 “Advanced RAG”，但从实现上看，需要更冷静地判断。

对应文件：

- `core/rag_engine.py`

核心实现包括：

- `chromadb.PersistentClient`
- 两个集合：
  - `history_cases`
  - `company_knowledge`
- `TextSplitter.recursive_split`
- Gemini embedding：`models/text-embedding-004`
- 图片 / PDF 解析成文本再入库
- 查询时同时搜知识库和历史案例库

### 1. 这层真正解决的目标是什么

不是做开放域问答，而是给测试生成提供“约束性参考”。

具体来说，它希望补足三类信息：

- 公司内部规范
- 历史测试案例
- PRD 相关的补充知识

所以它的定位不是“替代模型”，而是“压缩幻觉空间”。

### 2. 它为什么适合这个项目

因为 PRD 转测试用例最怕两件事：

- 模型只根据常识生成，忽略企业内部规范
- 模型不知道历史上同类模块是怎么测的

引入 RAG 后，模型可以少一些“空想式生成”，多一些“贴着已有规范生成”。

特别是它把知识库分成：

- `company_knowledge`
- `history_cases`

这其实已经隐含了两类不同知识：

- 静态规则知识
- 经验案例知识

这点很值得学。

### 3. 为什么它还不能算很强的现代 RAG

因为它目前更像是“可用版本地检索增强”，还不是“工业级检索系统”。

明显欠缺包括：

- 没有 reranker 模型
- 没有 metadata filter
- 没有 query decomposition
- 没有多路召回策略
- 没有 chunk 级置信排序解释
- 没有按知识类型定制检索策略

它用 LLM 过滤召回内容，这是一个实用补丁，但不等于完整 RAG 架构升级。

更准确的说法应该是：

> 它是“向量检索 + LLM 过滤”的轻量 RAG 管线。

### 4. 哪些新场景下这套 RAG 会很好用

- 小中型知识库
- 文档格式比较简单
- 重点是辅助生成，不是精确问答
- 对部署轻量化、本地化有要求

### 5. 哪些场景下会不够

- 知识库规模上万文档
- 不同文档质量差异很大
- 需要可审计证据链
- 需要跨文档融合推理
- 需要权限隔离

这时候就要升级成更强的知识架构，比如：

- 分层索引
- metadata 筛选
- rerank
- hybrid retrieval
- citation grounding

## 七、会话记忆：它有状态，但严格说还不是“真正的记忆系统”

这部分很值得区分。

很多 LLM 应用会把任何持久化都叫 memory，但这里更准确的拆法应该是三类：

1. 会话状态
2. 资产归档
3. 学习型记忆

这个项目主要做到了前两类，没有真正做成第三类。

对应实现：

- Streamlit `st.session_state`
- ChromaDB 中的 `history_cases`

### 1. 它现在有什么

#### 第一类：会话状态

放在 `st.session_state` 里的有：

- `messages`
- `gemini_history`
- `res_data`
- `prd_context`
- `rag_context`
- `processed_files`
- `eval_report`

这些状态保证了：

- 页面可以持续交互
- 用户可以继续微调
- 当前生成结果能被反复编辑和评审

#### 第二类：资产归档

在 `history_cases` 里保存：

- PRD 文本
- 最终 JSON
- 摘要信息

这让过往案例可以被后续任务再次召回。

### 2. 为什么说它不是完整记忆系统

因为“记忆”至少还可以更进一步：

- 从历史案例中抽经验模式
- 识别哪些案例是高质量模板
- 提取领域偏好和团队规范
- 建立可复用的测试设计模式库

当前项目只是把结果存进向量库，方便以后检索。  
这更像“可回查资产”，还不是“可成长经验记忆”。

### 3. 这种设计为什么仍然合理

因为对这个阶段的产品来说，最需要的是：

- 本轮可继续工作
- 已完成结果不丢
- 历史案例能被参考

如果一开始就做复杂 memory architecture，反而容易把系统做重。

### 4. 未来哪些场景会推动它升级

- 同一个团队长期积累大量测试资产
- 不同产品线希望共享测试经验
- 希望把“专家习惯”固化成可学到的规则
- 希望做质量反馈闭环，比如“哪些 AI 生成结果最终被人工保留”

这时候可以把 memory 升成：

- case memory
- pattern memory
- preference memory
- quality feedback memory

## 八、工业知识库构建：这里已经有雏形，但还停留在“文档入库层”

用户之前很关心“工业知识库怎么建”，这个项目虽然不是工业场景，但它在知识资产建设上已经有一个很清楚的基础模型。

### 1. 它当前做的其实是两类知识库

#### 规范知识库

来源：

- PDF
- 图片
- 文本

落点：

- `company_knowledge`

用途：

- 作为生成测试用例时的规范参考

#### 案例知识库

来源：

- 历史 PRD 与最终测试用例

落点：

- `history_cases`

用途：

- 作为类似任务的经验参考

### 2. 这种拆分为什么重要

因为企业知识从来都不是一种东西。

至少可以分成：

- 规则知识
- 案例知识
- 过程知识
- 反馈知识

这个项目已经完成了前两种雏形，所以它对工业知识库设计的启发在于：

> 不要把所有知识都扔进一个大桶里，至少先区分“规范”和“案例”。

### 3. 如果往工业 Agent 场景继续演进，应该怎么补

可以继续拆成四层：

1. 文档层
   原始 PDF、截图、说明书、规范文档
2. 片段层
   chunk、摘要、标签、来源、版本
3. 规则层
   明确的制度、阈值、流程节点、适用范围
4. 案例层
   问题背景、处理动作、结果、复盘结论

如果做到这一步，知识库就不只是“RAG 原料仓”，而会开始变成“业务知识操作系统”。

### 4. 它目前的不足

- 缺少版本管理
- 缺少知识生命周期管理
- 缺少质量标记
- 缺少结构化元数据
- 缺少案例优劣分层

所以它更像“知识入门版基础设施”，还不是成熟知识工程系统。

## 九、这个项目最值得学的亮点

### 1. 它清楚知道自己不是通用 Agent，而是垂直工作流产品

这很重要。很多项目最大的问题不是技术差，而是定位乱。  
这个项目虽然不复杂，但产品目标非常聚焦。

### 2. Prompt 不是装饰，而是流程规程

这是做垂直 Agent 时非常重要的能力。

### 3. RAG 不是独立展示功能，而是嵌进生成链路

它没有把知识库做成一个单独“问答功能”，而是用来约束生成质量。

### 4. HITL 做得比很多 Demo 更真实

左侧解释、右侧结构化结果、继续微调、再评估，这套链路已经很像实际生产工具，而不是一次性聊天玩具。

### 5. 引入了“生成者-审核者”角色分离

虽然不是重型多 Agent 框架，但已经有了角色治理意识。

## 十、这个项目最明显的欠缺和演进方向

### 1. 编排过于集中在 UI 层

后期如果要：

- 做 API 服务
- 做批量任务
- 做异步执行
- 做多人协同

就需要把工作流下沉到 service / workflow 层。

### 2. 没有正式 tool calling 机制

如果未来接入更多系统，靠 UI 手工编排会越来越吃力。

### 3. RAG 仍然偏轻

适合小规模知识库，不适合更复杂的企业知识系统。

### 4. memory 还不是 learning memory

能存结果，但还不会从结果中学习。

### 5. 评审虽然很好，但还没有形成真正闭环

现在 AI 会指出问题，但还没有：

- 自动回写优化策略
- 把高质量结果标为模板
- 对生成质量做长期统计

如果补上这些，它会更像一个“会进化的测试知识系统”。

## 十一、如果把它放进我们的 Agent 学习地图里，应该怎么记

我会这样记住它：

> `ByteDance--Auto_prd_test_agent` 不是通用 Agent 内核，而是一个以 Prompt 规程、轻量 RAG、人工共创和 AI 评审为核心的 PRD 测试生成工作台。

它最适合拿来学习的不是“Agent 如何自主思考”，而是下面这些问题：

- 如何把一个明确业务流程压成 AI 产品
- 如何让 Prompt 承担规程编码角色
- 如何把 RAG 放进生成闭环而不是做成孤立功能
- 如何把人工微调和 AI 评审纳入工作台
- 如何从“回答”走向“资产沉淀”

## 十二、给以后做同类项目的可迁移建议

### 1. 先问自己是在做 runtime 还是在做 workflow

如果目标是业务交付，很多时候 workflow 比 runtime 更重要。

### 2. Prompt 设计优先写“怎么做”，不是只写“你是谁”

角色重要，但规程更重要。

### 3. 工具和知识都要围绕最终交付物设计

这个项目的最终交付物不是聊天记录，而是测试用例资产。  
这是它做对的一点。

### 4. 会话状态、历史资产、可学习记忆要分层

不要把它们混为一个“memory”概念。

### 5. 当 UI 编排越来越重时，要及时往后端工作流迁移

这是它未来最值得补的一步。
