# 搜索与 Markdown 工程化模式（资料源）

> 来源背景：基于 Pagefind、QMD、remark / unified 等项目的公开资料，提炼适合知识平台的搜索与 Markdown 工程思路。

## 1. 一句话结论

搜索和 Markdown 渲染都不应该停留在“前端临时字符串处理”，它们应该成为构建期和结构化层面的正式能力。

## 2. 它解释了什么行业问题

很多知识平台早期都能“看起来能用”，但内容一多就会出现：

- 搜索只能按标题或整页匹配，命中质量很差。
- Markdown 只能展示文本，不能支持稳定锚点、扩展块和导出。
- 后续想做引用、反馈、搜索跳转时，只能不断补临时代码。

## 3. 优秀做法

- 在构建期生成全文索引，而不是把检索压力都丢给前端运行时。
- 把搜索结果设计成“命中对象 + 命中原因 + 命中片段”。
- 使用 Markdown AST 渲染，而不是自己写一套脆弱的文本解析器。
- 为标题、列表项、段落和表格单元保留结构化扩展空间。

## 4. 为什么这些做法重要

因为知识平台不是静态页面集合，而是会持续增长的知识系统。

越早把搜索和渲染做成“结构化能力”，后面越容易支持：

- 精准命中
- 区块引用
- 页面导出
- 内容审计
- AI 基于当前页上下文的二次处理

## 行业痛点研究版补充

### 1. 它对应的行业普遍痛点

知识平台前期常用字符串匹配和简单预览快速起步，但一旦内容增长，就会在检索精度、引用能力和扩展性上遇到系统性瓶颈。

### 2. 可作为证据的来源类型

- 搜索工具文档
- Markdown 工程体系文档
- 文档平台实现方案

### 3. 优秀做法的共性

- 搜索结果尽量结构化，而不是只返回一段截断文本。
- 渲染层尽量建立在 AST 上，而不是临时文本规则。
- 为未来的 block 引用、导出和 AI 二次处理预留稳定结构。

### 4. 数据支撑与判断信号

- 搜索命中精度
- 重复查询率
- 区块引用数量
- 渲染异常和 Markdown 兼容问题数量

### 5. 自动进化规则

后续每次索引结构或 Markdown 阅读器升级后，都要同步检查是否提升了搜索命中质量、阅读定位效率和后续导出能力。
