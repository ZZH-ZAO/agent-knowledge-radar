# GitHub 知识平台样本调研（2026-05-04）

> 研究目标：寻找和当前 Agent 知识平台定位相近，或者在搜索、阅读、记录、工程化上值得直接借鉴的开源项目。

## 1. 这次调研到底在看什么

这里考察的不是“有没有长得像文档站”，而是当前平台从 Markdown 展示器升级成真正知识工作台时，哪些能力必须先产品化。

真正有价值的问题有四个：

1. 搜索能不能从“找页面”升级成“找命中的段落和证据”。
2. 阅读能不能从“看 Markdown”升级成“可跳转、可导出、可反馈、可引用”。
3. 记录能不能从“写一篇文档”升级成“维护项目、痛点、方案、行动项之间的关系”。
4. 平台能不能具备持续进化能力，而不只是静态展示。

## 2. 样本池

| 项目 | 类型 | 最值得借鉴的点 |
| --- | --- | --- |
| OpenKB | AI 知识平台 | 把原始文档编译成结构化 wiki、概念页和交叉引用 |
| QMD | 本地搜索引擎 | BM25、向量、混合检索、rerank、collection context |
| Pagefind | 静态搜索 | 构建期搜索索引，低成本支持全站全文检索 |
| Docusaurus | 文档站工程化 | TOC、锚点、版本化、稳定侧栏、Markdown 基础设施 |
| Starlight | 文档阅读体验 | 默认阅读结构成熟，搜索、目录、布局、i18n 都比较稳 |
| Docmost | 协作文档平台 | 评论、权限、历史、附件、空间治理 |
| Trilium | 个人知识库 | 层级、属性、关系、全文搜索和大规模笔记治理 |
| SiYuan | 块级知识库 | 块引用、双链、导出、结构化查询 |
| remark / unified | Markdown 工程体系 | 把 Markdown 当 AST 处理，而不是字符串拼接 |

## 3. 核心研究结论

优秀知识平台的共性不是更花哨，而是把这条链路做成系统：

```text
稳定导航
  + 全局搜索
  + 页内目录
  + 可引用区块
  + 命中高亮
  + 反馈闭环
  + 可导出内容
  + 可度量的内容质量
```

对我们这个平台来说，真正该学的不是营销首页，而是下面这些“阅读基础设施”。

## 4. 最值得迁移的 10 个点

### 4.1 搜索从前端过滤升级成构建期索引

当前平台已经有 `searchIndex`，但后面应该继续强化：

- 命中理由
- 命中片段
- 文档类型上下文
- 推荐阅读角度

下一步可以从 Pagefind 或 MiniSearch 继续升级到本地全文检索。

### 4.2 搜索结果要带上下文，而不是只给标题

QMD 的启发很明确：结果不是“哪篇文档相关”，而是“为什么相关、属于哪个知识域、该从哪个视角去读”。

对当前平台建议至少保留：

- 路由类型
- 来源类型
- 命中片段
- 关联痛点或方案

### 4.3 Markdown 渲染必须基于 AST

这是工程基础，不是可选增强。

用 AST 渲染的价值在于：

- 可以稳定生成 heading id
- 可以安全加目录、导出、块级引用
- 可以扩展证据块、行动块、提示块

### 4.4 段落级 block id 是长期能力

块级 ID 不是为了炫技，而是为了后面这些能力：

- 痛点页引用某个项目里的某一段证据
- 面试官直接围绕某个证据块追问
- 搜索结果跳到具体命中段落
- 阅读反馈绑定到具体区块

### 4.5 资料源要有 intake 流程

OpenKB 的思路很适合现在的平台：外部资料不是直接进知识库，而是先经过 intake。

建议后续流程固定成：

```text
raw source
  -> source card
  -> pain point mapping
  -> pattern extraction
  -> action extraction
  -> index rebuild
```

### 4.6 文档要有健康检查

知识库最怕“内容越来越多，但没人知道哪部分已经失效”。

后续 lint 至少要盯这些问题：

- 没有关联 pain-point 的项目
- 没有关联项目的 pattern
- 没有来源证据的痛点
- 没有行动项的文档
- 长期没人引用的沉淀

### 4.7 内容需要更新时间和变化线索

版本不是为了好看，而是为了知道：

- 这个痛点为什么变了
- 哪条证据是最近新增的
- 哪些方案是最近补强的

### 4.8 阅读模式要内建，而不是临时样式

优秀文档站默认都解决了：

- 页内目录
- 标题跳转
- 搜索命中高亮
- 可导出
- 宽度和专注模式

这类能力对平台不是加分项，而是底座。

### 4.9 记录系统要有属性和关系

Docmost、Trilium、SiYuan 的共性都说明了一件事：文档不是孤立文件，而是带属性和关系的对象。

当前平台最小可行的一组属性已经很清楚：

- `sourceType`
- `evidenceStrength`
- `relatedPainPoints`
- `relatedPatterns`
- `nextActions`
- `status`
- `updatedAt`

### 4.10 工程化必须跟内容一起长

如果平台内容变厚，但 bundle、构建、验证和回归测试不跟上，最后会反过来拖慢沉淀效率。

当前就值得持续跟的工程项包括：

- 路由级懒加载
- 更轻的索引结构
- schema 校验
- Playwright 截图回归

## 5. 口语版回答

如果面试官问“你为什么要研究这些知识平台样本”，可以这样答：

> 我研究的不是别人的页面长什么样，而是知识平台在规模增长之后，搜索、阅读、记录和迭代到底会遇到什么结构性问题。像 Pagefind、Docusaurus、Starlight、Docmost 这些项目分别把搜索、阅读结构、协作和知识治理做得比较成熟。我把这些做法抽出来，不是为了照搬样式，而是为了补我们平台的阅读基础设施和自动进化能力。

## 6. 常见误区

- 只学视觉，不学信息结构。
- 只学搜索框，不学索引和命中上下文。
- 只学 Markdown 展示，不学锚点、区块引用和导出。
- 只堆页面功能，不做内容质量检查。

## 8. 它应该回写到哪里

这份资料源不应该停在“研究记录”，它应该至少反哺三层：

- `资料源` 页：作为外部知识平台样本证据。
- `方案` 页：补强搜索、阅读器、知识治理类 pattern。
- `痛点` 页：补强“知识平台内容增长后如何避免失控”的行业痛点。

## 行业痛点研究版补充

### 1. 它对应的行业普遍痛点

知识平台最容易失控的地方，不是没有内容，而是内容一多之后，搜索、阅读、引用、反馈和更新之间断开，最终变成“资料很多但学不动”。

### 2. 可作为证据的来源类型

- GitHub 开源项目
- 官方文档站
- 静态搜索工具文档
- 协作文档平台和知识库产品资料

### 3. 优秀项目的共性做法

- 把文档视为结构化对象，而不是纯文本页。
- 让搜索命中能回到段落和上下文，而不只是文档标题。
- 让阅读行为可导出、可反馈、可引用、可统计。
- 让内容沉淀和工程化能力一起增长。

### 4. 数据支撑与判断信号

后续建议重点跟：

- 资料源转成方案和痛点的比例
- 搜索结果点击率与零结果率
- 文档反馈中“需补强”的比例
- 被面试官页和痛点页引用的来源数量

### 5. 自动进化规则

后续每次新增一份平台类资料源，都要判断它补强的是搜索、阅读、记录、证据治理还是工程化，并把结果回写到 `资料源 / 方案 / 痛点 / backlog` 四层。
