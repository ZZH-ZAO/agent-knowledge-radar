# 资料源吸收与自动进化手册

> 目标：让 GitHub、技术博客、论文和你提供的文档，进入同一条“发现 -> 判断 -> 提炼 -> 回写”的学习流水线。

## 1. 阅读目标

读一份资料时，不只问“它讲了什么”，而要问：

- 它暴露了什么行业痛点？
- 它的解决做法是什么？
- 这个做法和已有优秀项目有没有共性？
- 它应该更新哪个 `pain-point`？
- 它应该补强哪个 `pattern`？
- 它能给当前项目带来什么行动项？

## 2. 这件事真正考验什么

这里考验的不是“会不会记笔记”，而是资料筛选和知识转化能力。

优质资料不是越多越好。真正重要的是，能不能把外部信息转成自己的工程判断：

- 行业痛点
- 证据来源
- 成熟做法
- 数据信号
- 可迁移框架
- 当前项目行动项

## 3. 口语版回答

我会把资料源当成平台自动进化的输入层。GitHub 项目、博客、论文和用户文档先进入资料源池，再判断它们解释了什么行业问题、有没有证据、能不能补强已有痛点和方案。只有通过这层筛选的资料，才进入深度沉淀。

## 4. 工程视角拆解

- 来源层：GitHub、博客、论文、用户文档。
- 筛选层：相关性、证据强度、工程质量、学习价值、稀缺性。
- 抽象层：行业痛点、成熟做法、共性模式、边界与 trade-off。
- 落地层：更新项目沉淀、patterns、pain-points、面试题和当前项目行动项。

## 5. 自动进化规则

每新增一个资料源，至少产出：

- 一个行业痛点判断
- 一个优秀做法或反例
- 一个可关联项目或 pattern
- 一个当前项目行动项

如果这些都产不出来，这个来源先只记录，不进入深度沉淀。

## 6. 常见误区

- 把 GitHub star 当成质量。
- 只摘抄观点，不提炼工程结构。
- 只看论文结论，不判断能否落到项目。
- 只收藏链接，不更新痛点、方案和行动项。

## 7. 当前项目行动项

- [ ] 把 Project Radar 的候选项目和资料源池打通。
- [ ] 给每个痛点记录来源类型：GitHub、博客、论文、旧文档、当前项目。
- [ ] 每次沉淀后重建 `knowledge-index.json`，让平台自动刷新资料源页面。
- [ ] 给资料源页补“证据强度 / 推荐用途 / 关联痛点 / 关联方案”这四类摘要信息。

## 8. 行业痛点研究版补充

### 8.1 它对应的行业普遍问题

知识平台最常见的问题不是“资料不够”，而是资料进入之后不能转成稳定知识资产。最终表现为：

- 链接越来越多，但痛点没有变清楚。
- 项目越来越多，但方案没有变稳定。
- 面经越来越多，但回答能力没有变强。

### 8.2 可作为证据的来源类型

- GitHub 项目与源码
- 官方文档与 changelog
- 高质量博客与工程复盘
- 论文与 benchmark
- 用户提供的真实项目资料、面经和知识库

### 8.3 优秀平台的共性做法

- 把资料视为结构化输入，而不是自由文本。
- 进入知识库前先过筛选和分类。
- 每份资料必须关联痛点、方案或行动项。
- 每次新资料进入后，都要推动已有知识资产更新。

### 8.4 数据支撑与判断信号

后续建议重点追踪：

- 每份资料关联的 pain-point 数量
- 每份资料触发的 pattern 更新数量
- 资料源转成项目沉淀的比例
- 资料源最终产出的行动项数量

### 8.5 给当前项目的启发

资料源页不应该只是“我看过什么”，而应该回答：

- 这份资料为什么值得信？
- 它补了平台哪一块空白？
- 它最后改变了什么设计或行动？
