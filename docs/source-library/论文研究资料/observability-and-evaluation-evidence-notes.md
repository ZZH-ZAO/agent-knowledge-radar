# 可观测性与评估证据笔记（论文/研究资料型资料源）

> 来源背景：结合平台内已有的 `observability-patterns.md`、项目沉淀和面试表达需求，抽取一份偏研究证据视角的资料源，用于补强“为什么 Agent 平台必须做可观测性与评估”。

## 1. 一句话结论

Agent 平台一旦进入真实执行环境，没有可观测性和评估体系，就几乎无法稳定迭代，只能靠人工猜问题。

## 2. 它解释了什么行业问题

行业里很多 Agent 原型在 demo 阶段看起来很顺，但一进入真实任务链路就暴露三个问题：

- 不知道模型为什么这样决策。
- 不知道工具在哪一步出错。
- 不知道这次改动到底让系统更好还是更坏。

本质上，这不是“日志不够”，而是缺少完整观测和评估闭环。

## 3. 优秀做法

- 记录 session、tool、permission、error、model event 等关键事件。
- 保留结构化 traces，而不只保存最后回答。
- 让评估成为持续流程，而不是上线前一次性检查。
- 把 bad case 当成正式资产，持续回灌回归集。

## 4. 为什么它对平台重要

这个平台后面会不断做：

- 项目沉淀
- 方案抽象
- 痛点研究
- 面试官追问

如果没有观测和评估视角，平台本身也会退化成“只会展示总结”，而无法解释为什么某些内容值得保留、某些改造值得继续推进。

## 6. 行业痛点研究版补充

### 1. 它对应的行业普遍痛点

Agent 项目在从 demo 走向可维护系统时，最常见的问题之一就是没有稳定证据链，导致问题定位、方案验证和经验复用都很困难。

### 2. 可作为证据的来源类型

- 评估框架文档
- 可观测性模式文档
- bad case 分析与回归记录
- 成熟 Agent 平台的 release / telemetry / audit 设计

### 3. 优秀做法的共性

- 观测和评估不是附属功能，而是运行时的一部分。
- 好系统会保留行为痕迹、错误分类和回归证据。
- 好平台会让“证据 -> 判断 -> 行动”成为闭环。

### 4. 数据支撑与判断信号

- bad case 回归次数
- 错误分类覆盖率
- 搜索与阅读反馈中“需补强”项的变化
- 文档和页面被引用到方案/痛点/面试官的次数

### 5. 自动进化规则

后续每次平台新增评估、反馈或观测能力后，都要检查它是否真正提升了“问题定位能力、方案验证能力和知识复用能力”。
