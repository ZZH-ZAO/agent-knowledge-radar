# 当前项目演化观察（用户提供文档资料源）

> 来源背景：基于 `current-project-distillation.md`、平台总规划以及最近一轮产品化改造，抽取“这个项目是如何从源码仓库演化成知识平台”的观察结果。

## 1. 一句话结论

`claude-code-sourcemap` 最值得学习的不是它还原了源码，而是它如何从“源码研究仓库”逐步演化成“项目雷达 + 深度沉淀 + 通用问题抽象 + 可视化平台”。

## 2. 它解释了什么行业问题

很多研究型项目都会卡在中间态：

- 前期有大量阅读和分析。
- 中期有很多笔记和零散文档。
- 后期却很难形成稳定产品和可复用方法论。

这个资料源关注的就是：研究资产如何产品化，知识沉淀如何平台化。

## 3. 优秀做法

- 不把“看过源码”当成果，而是把它转成项目、方案、痛点和工程逻辑。
- 不把“找到优质项目”当终点，而是把它接进 Project Radar 和深度沉淀流程。
- 不把“文档越来越多”视为进展，而是逼迫每份文档输出行动项和回写位置。

## 4. 为什么它适合作为资料源

因为它不是外部样本，而是你自己平台目标的真实演化记录。

外部项目给的是“别人怎么做”，这份资料给的是“我们自己已经做到了哪一步、还差哪一步”。

## 5. 当前项目行动项

- [ ] 继续把旧体系文档吸收进新结构，而不是让它们继续散落。
- [ ] 给更多资料源补“应该回写到哪里”的明确出口。
- [ ] 让平台首页或工程逻辑页更清楚地展示这条演化链。
- [ ] 后续把“平台改造前后”的差异继续沉淀成可复用方法。

## 6. 行业痛点研究版补充

### 1. 它对应的行业普遍痛点

研究型项目普遍容易停在“有积累但不可复用”的状态，尤其在 Agent、知识平台和源码分析这类内容复杂、变化快的领域更明显。

### 2. 可作为证据的来源类型

- 当前项目沉淀
- 平台规划文档
- 旧体系迁移记录
- 新平台工程逻辑文档

### 3. 优秀做法的共性

- 每一轮改造都要从“结构问题”出发，而不是只修表层页面。
- 每一类知识资产都要有归宿：项目、方案、痛点、资料源、面试。
- 平台结构和文档结构要一起演化。

### 4. 数据支撑与判断信号

- 新体系接入的旧文档数量
- 每轮改造后索引项数量变化
- 被平台页面真正消费的文档比例

### 5. 自动进化规则

后续每次平台结构升级后，都要同步更新这份资料，记录“这次升级解决了什么结构问题、带来了什么新的学习能力”。
