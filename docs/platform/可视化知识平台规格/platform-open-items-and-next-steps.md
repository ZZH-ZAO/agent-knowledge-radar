现在这个平台已经不再是“看 Markdown 的页面”，而是一个已经成型的中文知识工作台：

- 能沉淀单项目

## 2026-05-07 沉淀台拆成三步动作

### 分类

Workflow / 前端展示 / 工具链路

### 这次要做什么

把沉淀台从一个“统一提交表单”拆成三步动作：`仓库理解`、`分析项目`、`正式沉淀`。

### 动机是什么

如果所有事情都放在一个按钮里，用户其实不知道自己到底在做哪一层工作。  
有的时候只是想先看仓库结构，有的时候是想让平台先给判断，有的时候才是要正式落库。  
把这三层分开以后，平台的行为会更像一个真正的分析工作流，而不是临时脚本入口。

### 对项目有什么实际作用

- 降低沉淀台的理解成本
- 让用户先选动作，再看结果
- 让“仓库理解”可以单独复用
- 让“分析项目”输出结构化结果，方便继续回写方案、痛点和面试内容
- 让“正式沉淀”更像最终落库动作，而不是混杂在前面两层里

### 具体场景是什么

- 我先点 `仓库理解`，确认这个项目值不值得继续深挖
- 我再点 `分析项目`，让平台先给项目一句话、核心场景和可迁移原则
- 我最后点 `正式沉淀`，把已经判断好的样本真正写进知识库

### 我应该怎么去使用

在前端沉淀台里，先看动作卡片，再决定这次要走哪一层。  
如果只是看结构，直接跑理解；如果要看结构化判断，跑分析；如果要正式生成草稿和索引，就跑沉淀。

### 对用户意味着什么

用户不再面对一个“什么都能做但不清楚先做什么”的入口，而是面对一个更清晰的学习工作流。

### 对开发者意味着什么

后面如果要继续接 MCP、做 Agent 自动调用，接口语义会更稳定，也更容易在前端和后端之间保持一致。

### 当前结论

这次改动的核心不是按钮变多了，而是平台终于把“理解”和“落库”分开了。  
这会直接影响后面所有自动进化能力的设计。

### 下一步建议

- 给分析结果加独立阅读器
- 把分析结果继续回写到 patterns / pain-points / interviews
- 让沉淀台动作和桥接接口继续保持一一对应

## 6. 行业痛点研究版补充

从行业视角看，这个平台想解决的不是“文档展示”问题，而是 Agent / 大模型工程里一个更普遍的断层：

- 优质项目很多，但很难稳定转成自己的工程判断
- 好博客、论文、源码和用户资料分散，缺少统一证据链
- 学习容易停在功能枚举，不能反推出设计原因
- 文档和真实项目决策脱节，做项目时仍然要从头摸索
- 面经、项目沉淀和工程逻辑没有打通，表达能力和工程理解彼此割裂

这个平台未来最值钱的地方，不是再多几个页面，而是持续把这些行业普遍断层补成一套可复用的方法论和工作流。

### 7.1 建议的实际执行顺序

为了让平台尽快从“可用”变成“会自己长脑子”，后面建议按这个顺序推进：

2. 再把痛点页做成真正的行业判断层，继续补证据项目、数据线索和成熟做法。
3. 然后继续厚化你自己的项目样本，尤其是面试表达、trade-off、追问链和优化路线。
4. 最后再做前端性能、阅读宽度、包体拆分和更强的导出能力。

### 7.2 写作质量这一轮最该补什么

这两天继续做下去，最该警惕的不是“内容不够多”，而是内容重新滑回“侃侃而谈、像总结、没有文章感”。

基于这轮补充的外部样本，我认为后续所有重点文档都要统一补四层：

1. 先补“为什么现在值得读”，把阅读收益讲清楚。
2. 再补“最容易误读什么”，提前拆掉错误理解。
3. 再补“口语版回答 / 三分钟工程讲法”，让内容能真的讲出去。
4. 最后补“证据、trade-off、行动项”，防止文章只停在态度层。

其中最该持续学习的两类写法已经比较清楚：

- 大公司工程文章：学它们怎么写约束、取舍、证据和验证信号。
- 黄同学h 这类高信号内容：学它们怎么抓真实压力、立判断句、组织追问链和服务表达。

如果后续某篇文档没有这几层，就算信息是对的，也还不算平台想要的“能学、能说、能迁移”的成品。

## 2026-05-08 自动回写闭环产品化（第一期落地）

### 分类

Workflow / 数据接入 / 前端展示 / 证据链路

### 这次要做什么

把“项目沉淀 -> 自动抽取判断 -> 回写方案 / 痛点 / 面试资产 -> 重建索引 -> 平台立即可见”这条链从半手动状态推进成平台默认能力。

### 动机是什么

如果项目沉淀只停在单篇文档，平台就还是一个会存文章的地方，不是一个会持续长判断的系统。真正值钱的是每新沉淀一个项目，平台里的方案页、痛点页和面试资产都能一起变厚。

### 对我们的项目有什么实际作用

- 项目分析不再只是生成一份草稿，而是同时生成 `writeback package`
- 回写结果可审计、可复跑、可去重，不会把文档越写越乱
- 痛点页开始拥有“最近被哪些项目补强”的数据视角
- 项目页能直接看到这次沉淀反哺了什么，不需要靠人工记忆

### 具体场景又是什么

- 我沉淀一个 GitHub 项目后，希望它立刻补强 `patterns / pain-points / interviews`
- 我重复分析同一个项目时，希望它更新同一份回写包，而不是不断堆重复内容
- 我打开项目详情页时，希望一眼看到这次沉淀影响到了哪些知识资产

### 我应该怎么去使用

默认在沉淀台保留“自动回写闭环”为开启状态。这样走 `analyze-project` 时，会自动生成回写包并重建索引；如果只是想先看分析、不想改知识库，再显式关闭 `autoWriteback`。

### 对用户意味着什么

用户不需要再记住“先分析、再点一键回写、再手动重建索引”这种多段流程，平台开始更像一个会自己长内容的工作台。

### 对开发者意味着什么

后续继续做痛点判断层、项目驱动面试链路和多源发现时，已经有了统一的中间层对象，不需要每条链都重新发明一套回写结构。

### 当前结论

这一步不是把平台做花，而是把平台的主链做厚。只要回写包、索引字段和项目详情页这三层稳定下来，后面的内容进化才会越来越顺。

### 下一步建议

- 继续把 pain-point rollup 前端展示补完整，尤其是证据项目数、最近补强项目和共性做法
- 把 interview 资产按项目聚合到项目详情页和 AI 面试官页
- 开始补“自动发现 -> 自动评分 -> 自动沉淀 -> 自动回写”的全自动触发链
