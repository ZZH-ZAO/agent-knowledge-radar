# 平台定位校准与交付路线图

> 适用对象：`D:\claude-code-sourcemap` 可视化知识平台  
> 作用：作为“平台现在做到哪里了、是否符合目标、接下来优先做什么”的统一执行文档。

## 1. 这份文档回答什么

这份文档不再重复“平台愿景”，而是直接回答四个执行问题：

1. 现在这套平台，是否已经符合你的目标和定位。
2. 现阶段最有价值的能力，哪些已经成型，哪些还只是骨架。
3. 后续每一轮迭代，应该优先补内容、补工程、还是补自动进化。
4. 以后说“继续做”，默认应该沿着什么顺序推进，而不是每次重新定义目标。

## 2. 平台最终要成为什么

你的目标不是做一个 Markdown 展示站，也不是做一个 GitHub 项目收藏夹。

你要的是一个中文优先、持续进化的 Agent 工程知识平台。它的核心任务是：

- 自动发现值得学习的外部项目、博客、论文和用户资料。
- 自动筛选出真正有工程价值的样本，而不是只看 star。
- 自动沉淀成可学习、可复用、可转化为项目决策的深度文档。
- 通过“项目 / 方案 / 痛点 / 工程逻辑 / 面经 / AI 面试官”这些路由，把外部知识最终收束成你自己的工程方法论。

换句话说，它最终服务的是三件事：

- 学习：帮你看懂优秀项目到底为什么值得学。
- 迁移：帮你把别人的做法转成自己的设计资产。
- 决策：帮你以后做真实项目时，不再从零摸索工程逻辑。

## 3. 当前平台是否符合这个定位

结论先说：**方向已经对了，基础平台已经成型，但还没有进入“高质量自动进化”的稳定阶段。**

更准确地说，当前状态是：

- `项目沉淀平台`：已成型
- `学习工作台`：已成型
- `工程逻辑平台`：正在成型
- `自动发现 + 自动筛选 + 自动沉淀平台`：已有链路，但还不够强

这意味着现在不需要推翻重做，重点应该是沿着现有结构继续加厚内容、补强自动化、增强阅读和证据闭环。

## 4. 当前已经具备的能力

### 4.1 内容层

当前已经具备以下内容结构：

- `docs/external-projects/`：单项目深度沉淀
- `docs/patterns/`：通用问题、优秀技术和工程框架
- `docs/project-radar/`：候选池、评分、发现与沉淀链路
- `docs/source-library/`：GitHub、博客、论文、用户资料等外部输入
- `docs/interviews/`：面经、问答、追问链路、AI 面试官素材
- `docs/platform/`：平台产品规格、工程逻辑、路线规划

这意味着平台已经不是“文档散落”，而是有了明确分层：

```text
外部资料
  -> 项目沉淀
  -> 方案抽象
  -> 痛点研究
  -> 工程逻辑
  -> 面试表达
```

### 4.2 工程层

当前已经具备以下工程能力：

- `scripts/build_knowledge_index.py`：把多目录文档构建为统一索引
- `scripts/knowledge_lint.py`：检查知识库内容结构和引用完整性
- `apps/knowledge-platform/`：中文可视化平台
- 平台支持统一搜索、长文阅读、目录跳转、局部定位、导出、反馈沉淀

这说明平台不只是“有文档”，而是已经开始具备“知识工作台”的形态。

### 4.3 路由层

当前路由已经基本覆盖你的目标：

- `项目`
- `方案`
- `痛点`
- `工程逻辑`
- `资料源`
- `面经`
- `面试官`
- `雷达`
- `反馈`
- `视觉生成`

这套路由已经不是按文件夹展示，而是按“学习与决策任务”组织。

## 5. 还没做到位的地方

虽然平台方向对了，但距离“真正有长期学习价值的工作台”还差四层能力。

### 5.1 文档深度不均衡

问题不在于文档数量，而在于厚度不稳定。

当前已有一些文档已经接近“可学习、可复用”的深度，但也有一些文档仍偏骨架化，容易停留在：

- 功能枚举
- 概念列点
- 只有结论，没有证据链
- 只有方法名，没有 trade-off

后续核心任务不是继续堆目录，而是持续把高价值文档补成“能读、能学、能直接拿来用”的版本。

### 5.2 痛点页还要持续变厚

痛点页的目标不是罗列“平台里有哪些 bug”，而是沉淀：

- Agent 行业内的普遍痛点
- 大模型工程里的共性难题
- 优质项目分别怎么解决
- 共性模式是什么
- 数据和证据从哪里来
- 这些结论对你当前项目的启发是什么

当前痛点结构已经对了，但后续要持续依赖项目页、方案页、资料源页反向补证据，才能真正变成“行业问题研究库”。

### 5.3 自动进化还偏弱

现在平台已经有：

- `Project Radar`
- 候选池
- 评分
- 自动构建索引
- 自动校验

但还没有稳定做到：

- 自动吸收 GitHub / 博客 / 论文新输入
- 自动识别应该补哪个痛点、哪个方案
- 自动回写“当前项目行动项”
- 自动判断哪些文档需要重写或补强

也就是说，现在已经有“半自动学习链路”，但还没进入“稳定自进化”阶段。

### 5.4 工程逻辑页还需要更强的决策性

工程逻辑页不应该只是说明流程，而应该最终帮助你回答：

- 这个项目先做哪一层。
- 当前风险最大的边界在哪里。
- 哪些成熟做法值得直接借鉴。
- 哪些内容适合现在做，哪些应该放后。
- 如何验证这轮设计有没有真的进步。

所以它最终应该成为整个平台的“主收束页”，而不只是一个概念页。

## 6. 每个路由真正应该承担什么职责

### 6.1 项目页

职责不是介绍项目，而是把单个优质项目拆开，让你看见：

- 它解决什么问题
- 为什么值得学
- 它背后的通用问题是什么
- 有哪些可迁移设计原则
- 对你当前平台能立刻产生哪些动作

项目页是“样本层”。

### 6.2 方案页

职责不是列框架名词，而是把多个项目共性收束成工程框架。

它应该回答：

- 这个通用问题到底是什么
- 为什么重要
- 成熟系统通常怎么做
- 常见错误做法是什么
- 我们接下来应该补哪些动作

方案页是“抽象层”。

### 6.3 痛点页

职责不是说“哪里不好”，而是沉淀行业问题。

它应该回答：

- 业内普遍痛点是什么
- 为什么反复发生
- 优质项目是怎么处理的
- 具体提升在哪里
- 我们能观察哪些信号或数据
- 对当前平台和未来项目的启发是什么

痛点页是“问题研究层”。

### 6.4 工程逻辑页

职责是把平台里分散的知识真正收束成项目方法论。

它最终应该回答：

- 我以后做一个 Agent 项目时，应该按什么顺序设计
- 每个阶段看什么证据
- 依赖哪些项目样本
- 怎样把方案和痛点转成行动项

工程逻辑页是“决策层”。

### 6.5 资料源页

职责不是展示外链，而是维护证据输入池。

它应该帮助你判断：

- 这份资料属于哪一类来源
- 证据强度如何
- 更适合补项目、方案还是痛点
- 是否值得升级成深度沉淀

资料源页是“证据入口层”。

### 6.6 面经 / 面试官页

职责不是背题，而是把沉淀成果转成表达能力。

它们应该把：

- 项目事实
- 行业痛点
- 方案框架
- trade-off 判断

转成可复盘、可训练、可追问的问答体系。

这是“输出层”。

## 7. 平台的正确内容流水线

后续默认沿这条链路推进：

```text
外部项目 / 博客 / 论文 / 用户资料
  -> Source Library 收录
  -> Project Radar 候选与评分
  -> 单项目沉淀
  -> 方案抽象
  -> 痛点补证据
  -> 工程逻辑回收
  -> 面试问答与追问训练
  -> 用户反馈回流
  -> 下一轮文档补强
```

这条链路的关键，不是“多一层目录”，而是保证每次新输入都能至少回写三类资产：

- 一个项目事实样本
- 一个可迁移方案
- 一个可执行行动项

如果不能回写这三类资产，这个新输入就只是“看过了”，还不算真正沉淀。

## 8. 后续优先级应该怎么排

### 优先级 A：把现有高价值文档继续做厚

先补最有价值的内容层，因为这是平台存在的根本。

重点包括：

- 高分项目页继续补证据链和可迁移原则
- 方案页继续补成熟做法、误区和行动项
- 痛点页继续补项目证据、数据线索和启发
- 旧文档继续迁移和统一风格

验收标准：

- 文档能被连续阅读
- 不只是枚举功能
- 能支持学习和直接使用

### 优先级 B：把工程逻辑页做成平台主收束页

这是让平台从“知识库”变成“项目决策工作台”的关键一步。

重点包括：

- 建立阶段化阅读顺序
- 让每个阶段引用项目 / 方案 / 痛点 / 资料源
- 提供更强的“当前项目行动项”收束能力

验收标准：

- 你以后做项目时，可以先看工程逻辑页再展开阅读，而不是重新问一次“现在先做什么”

### 优先级 C：增强自动发现与自动回写

这一步决定平台有没有“持续进化能力”。

重点包括：

- 扩展 Radar 的发现来源
- 更稳定地做候选池评分
- 新来源自动关联到痛点和方案
- 新沉淀自动更新索引和知识关系

验收标准：

- 每次新增高质量样本后，平台不是只多一篇文档，而是多个路由一起变厚

### 优先级 D：继续优化前端阅读体验

这一步是“好用性增强”，优先级低于内容和工程逻辑，但仍然重要。

重点包括：

- 更宽松的长文阅读布局
- 更强的目录跳转与块引用
- 更自然的导出和反馈回流
- 进一步减少页面中的“卡片堆砌感”

验收标准：

- 平台读起来更像文档工作台，而不是组件列表

## 9. 行业痛点研究版补充

这个平台之所以要继续平台化，不是因为“文档多了不好找”，而是因为 Agent / 大模型工程领域本身存在几个很普遍的结构性问题：

- 优质项目很多，但很难被稳定转化为自己的工程知识。
- 博客、论文、源码、面经和用户经验分散在不同来源里，缺少统一证据链。
- 学习容易停留在“功能知道了”，却很难抽象成可迁移的工程框架。
- 做项目时仍然容易回到从零试错，知识沉淀没有真正反哺决策。
- 表达层和工程层断开，导致知道一些内容，却不容易在面试、汇报和设计讨论里说清楚。

所以这个平台真正对应的是一个行业级知识转化问题：

```text
好样本很多
  -> 但知识转化效率很低
  -> 于是项目决策仍然高度依赖个人临场经验
  -> 结果是重复试错、重复踩坑、重复重学
```

平台的价值就在于把这条断裂链补起来，让“发现 -> 沉淀 -> 抽象 -> 决策 -> 表达”形成闭环。

## 10. 以后说“沉淀”默认放哪里

后续默认继续写入新体系：

- 单项目沉淀：`docs/external-projects/`
- 通用问题 / 技术框架：`docs/patterns/`
- 自动发现 / 候选池 / 评分：`docs/project-radar/`
- 外部博客 / 论文 / 用户资料：`docs/source-library/`
- 平台规划 / 工程逻辑 / 产品规格：`docs/platform/`
- 面经 / 问答 / AI 面试官素材：`docs/interviews/`

`.claude/docs` 继续保留历史资料价值，但不再作为新的默认沉淀入口。

## 11. 以后继续执行时的默认顺序

如果你后面只说一句“继续”，默认按下面顺序推进：

1. 先看当前平台里最薄弱的高价值文档。
2. 优先补能同时增强“项目 / 方案 / 痛点”三层的内容。
3. 有新外部资料时，先进入 `source-library` 或 `project-radar`，不要直接污染主知识库。
4. 高分项目进入单项目沉淀，再反哺 `patterns` 和 `pain points`。
5. 每轮迭代后重建索引并校验，保证平台始终可读、可搜、可用。

## 12. 当前结论

当前平台已经明显进入正确轨道。

它已经不是一个零散仓库，而是一个初步成型的：

- 项目沉淀平台
- 学习工作台
- 工程方法平台

下一阶段真正要做的，不是再发散更多目录，而是稳步增强三件事：

- 文档深度
- 工程逻辑收束
- 自动进化能力
