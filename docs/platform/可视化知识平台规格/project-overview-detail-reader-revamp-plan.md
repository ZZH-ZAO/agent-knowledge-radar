# 项目概述页与详情阅读器改版规划

> 适用对象：`D:\claude-code-sourcemap`
>
> 更新时间：2026-05-06
>
> 目的：解决当前平台“项目概述和详情混在一起、重点不够明显、文档不够口语化不够具体、阅读器不够像真正工作台”的问题。

## 1. 先说结论

这次改版不能只理解成“把页面排版调漂亮一点”。

它本质上要同时解决三件事：

1. 项目页的信息结构不对。
2. 文档本身的写法不对。
3. 阅读器虽然已经能看，但还不像真正高频使用的知识工作台。

如果只改样式，不改结构，最后还是会回到现在这个状态：

```text
列表像目录
  + 详情像一锅炖
  + 文档像功能枚举
  = 看着很多，学完带不走东西
```

所以这次应该明确改成两层：

```text
项目概述页
  -> 负责快速判断“值不值得现在读”

项目详情页
  -> 负责真正沉浸式阅读、跳转、导出、引用、学习和复盘
```

## 2. 当前平台的问题，不绕弯子

结合现在的前端结构和文档内容，我认为最核心的问题有六个。

### 2.1 项目概述和项目详情混在同一屏

现在项目路由本质上还是“左边列表 + 右边详情”的一体页。

这样的问题是：

- 用户还没判断这个项目值不值得读，就已经被长内容淹没。
- 概述区和阅读区都想承担“解释项目”的职责，结果谁都没有做透。
- 一页里同时塞导读、指标、行动项、长文，会让主次失焦。

你提的“先概述，再跳详情页”是对的，这不是小优化，而是信息架构升级。

### 2.2 概述卡片不够一眼看懂

现在项目卡片大多还是：

- 项目名
- 摘要
- tag

这对“收藏夹”够了，但对“知识工作台”不够。

因为你真正要快速判断的是：

- 这项目主分类是什么
- 它打的是哪类业务场景
- 它最大的亮点是什么
- 它更偏样本、框架、产品、基础设施还是工程工具

如果这些信息不直接露出来，用户就还是要逐个点开猜。

### 2.3 文档写法还是偏“总结”，不够“带人理解”

你说“侃侃而谈、不深入、不具体、不够口语化”，这个判断是准的。

当前不少文档虽然结构已经比以前强了，但依然容易停留在下面这类写法：

- 它有 A、B、C 功能
- 它解决了 X、Y、Z 问题
- 它给了我们一些启发

问题是这种句子看起来像在说话，实际上没有把判断落下来。

真正有学习价值的文档，应该更像：

- 这个项目真正牛的地方不是表面这个功能，而是它把哪条行业难题工程化了。
- 普通项目为什么容易做烂，这个项目为什么没有烂在这里。
- 哪部分值得抄，哪部分不要抄，边界是什么。
- 如果面试官继续追问，最容易被问爆的是哪一段，应该怎么回答。

也就是说，文档不能只是“总结项目”，而要“替读的人做第一层思考”。

### 2.4 阅读器能看，但还不像飞书这类工作台

你提飞书很有代表性，因为飞书文档的强项不是“视觉炫”，而是：

- 阅读密度高
- 层级清楚
- 标题跳转顺手
- 一边读一边定位信息很快
- 页面动作很近，不需要找半天

现在我们的阅读器已经有目录、跳转、导出、反馈，这是对的。
但还差几个关键气质：

- 页面头部太像普通详情卡，不像正式文档头
- 章节导览还不够稳，不像“持续陪你读”
- 证据、行动项、重点结论还没形成清晰的文档边栏结构
- 页面宽度、层次、留白和信息密度还没有达到“专业知识工作台”的平衡

### 2.5 写作风格没有统一标准

当前问题不只是“有些文档写得浅”，而是平台缺少一套统一的写作约束。

比如还没有明确规定：

- 项目文档必须先回答什么
- 方案文档和项目文档的语气差异是什么
- 什么叫“具体”
- 什么叫“口语化但不水”
- 什么叫“有判断”

没有这个标准，后续自动沉淀越多，内容风格会越飘。

### 2.6 平台目前还偏“文档集合”，不够“阅读决策台”

你真正想要的平台，不是把文档摆出来，而是帮助你完成三步：

```text
先判断值不值得看
  -> 再进入深读
  -> 最后把结论转成自己的项目动作
```

所以平台要把“决策”放在概述页，把“学习”放在详情页，把“行动”放在文档底部和侧栏。

## 3. 外部案例里，哪些东西最值得学

下面这些案例不是让我们照着抄皮肤，而是借它们已经验证过的结构判断。

### 3.1 飞书文档 / 知识库：学“工作台式阅读”

适合借鉴的不是视觉，而是交互心智：

- 文档是主角，不是卡片是主角。
- 标题层级必须稳定，目录必须像锚点系统。
- 页面顶部动作靠近标题，不要让复制、反馈、导出藏太深。
- 正文之外的“边栏信息”要服务阅读，而不是装饰。

我们平台应该借它这几个点：

- 项目详情页改成“文档头 + 右侧目录 + 正文 + 页面动作”
- 把“导读、证据、行动项、面试追问”做成文档边栏区或文档前置区
- 让用户进入详情后，明显感知自己已经从“看列表”切换到“读文档”

### 3.2 Vercel Docs：学“页面动作 + On this page + 反馈闭环”

我查到的 Vercel Docs 当前页面已经把这几个动作明确放在文档页里：`On this page`、`Copy as Markdown`、`Give feedback`、`Ask AI about this page`。同时它把知识库、文档、更新流放在同一套体系里。  
来源：Vercel Docs 与官方 changelog（截至 2026-05-06 检索）  
- https://vercel.com/docs  
- https://vercel.com/changelog/unified-documentation-search-across-vercel-next-js-and-turborepo

对我们最有价值的启发是：

- 文档页动作不该是附属功能，而是阅读器的一部分。
- 搜索不是只把你带到页面，而是要把你带到“这页的某一段”。
- 平台内容要能持续回收到反馈闭环里。

### 3.3 Stripe Docs：学“概念文档和参考文档分开”

Stripe Docs 很强的一点，是它不会把“为什么这么做”和“接口字段长什么样”混在一起。  
来源：Stripe API Reference（截至 2026-05-06 检索）  
- https://docs.stripe.com/api

映射到我们平台，就是：

- 项目概述页负责“这项目是什么、适合谁、亮点是什么”
- 项目详情页负责“深入讲原理、证据、边界、行动项”

不能一进页面就既想做介绍、又想做阅读器、又想做知识图谱入口。

### 3.4 Outline：学“知识库产品的文档对象感”

Outline 现在在 GitHub 上是一个很成熟的知识库产品样本，检索时显示约 `38.2k stars`，最近 release 到 `2026-03-18`。  
来源：GitHub 仓库页（截至 2026-05-06 检索）  
- https://github.com/outline/outline

它值得学的不是“团队协作”本身，而是：

- 文档对象感很强，用户知道自己是在进入一篇文档，而不是点开一张卡片。
- 知识库产品会天然把“目录、页面、历史、搜索命中、导出”当成一等公民。

我们平台可以借它的心法：

- 项目详情页要更像“文档对象”
- 项目概述页要更像“知识首页 / 样本总览”

### 3.5 Docmost：学“文档管理能力要天然服务深读”

Docmost 现在在 GitHub 上检索显示约 `19.8k stars`，最近 release 到 `2026-04-14`。  
来源：GitHub 仓库页（截至 2026-05-06 检索）  
- https://github.com/docmost/docmost

它比较值得学的是：

- 页面历史
- 搜索
- 附件 / 文档对象统一管理
- 协作文档的结构稳定性

对我们来说，这意味着：

- 后面平台不只是“展示 md”，而是要越来越像“可引用的知识对象系统”

### 3.6 Docusaurus / Starlight / Mintlify：学“文档基础设施”

这三类项目更像“能力底座”，不是终态产品，但非常适合拿来校准阅读器和文档结构。

- Docusaurus：GitHub 检索显示约 `64.6k stars`，最近 release 到 `2026-04-07`  
  https://github.com/facebook/docusaurus
- Starlight：GitHub 检索显示约 `8.4k stars`，最近 release 到 `2026-05-05`  
  https://github.com/withastro/starlight
- Mintlify Starter：GitHub 检索显示约 `1.8k stars`  
  https://github.com/mintlify/starter

它们最值得学的是：

- 稳定的目录与文档路由
- 文档页布局模板
- 搜索、标题锚点、MDX 组件化
- 文档和站点信息架构的分离

换句话说：

- Outline / Docmost 更像“我们想成为的产品形态”
- Docusaurus / Starlight / Mintlify 更像“我们该怎样搭基础设施”

## 4. 我建议的平台结构怎么改

### 4.1 路由层改成“概述页 -> 详情页”

项目路由应该拆成两层：

```text
/projects
  -> 项目概述页（总览、分类、筛选、项目卡片）

/projects/:projectId
  -> 项目详情页（文档阅读器）
```

不要继续把这两个场景塞在同一个双栏页里。

### 4.2 项目概述页只做四件事

每张项目卡片必须一眼回答四个问题：

1. 主分类是什么
2. 针对的业务场景是什么
3. 最大的亮点是什么
4. 值不值得现在看

建议卡片字段固定成：

- 项目名
- 主分类
- 业务场景
- 最大亮点
- 推荐级别 / 评分
- 沉淀状态

你要求的“一目了然”，本质上就是卡片字段不能再散。

### 4.3 项目详情页只做“深读”

详情页进入后，页面结构应该明显切换成阅读模式：

```text
文档头
  -> 标题 / 一句话判断 / 主分类 / 业务场景 / 最大亮点 / 来源

前置导读区
  -> 为什么值得读 / 适合谁 / 不适合谁 / 面试最容易追问哪

正文阅读区
  -> Markdown Reader

右侧目录
  -> 标题导航 / 当前阅读位置 / 关键章节

页面动作
  -> 复制链接 / 导出 Markdown / 反馈 / 复制摘要
```

### 4.4 方案页和痛点页也要同步这个心智

既然项目页要分离概述和详情，后面方案页、痛点页其实也应该逐步跟上：

- 列表页负责“筛选和判断”
- 详情页负责“阅读和学习”

否则只有项目页分离，其他页还是一锅炖，用户心智仍然会乱。

## 5. 概述页要怎么设计

### 5.1 页面目标

项目概述页不是项目目录，它的目标是：

```text
让我 30 秒内知道
  哪些项目属于哪一类
  这些项目分别适合看什么
  我下一篇最该点开哪一个
```

### 5.2 页面结构

建议概述页分四层：

#### 第一层：页头

- 页面标题
- 一句定位
- 搜索
- 当前筛选条件

#### 第二层：分类条

按照你最关心的知识结构来分，而不是随便按 tag 堆：

- Agent Runtime
- Tool Runtime / MCP
- Memory / Context
- Observability / Eval
- Frontend / Workbench
- Productization
- 自研项目

#### 第三层：项目概览卡片区

每张卡片固定模板：

- `项目名`
- `主分类`
- `业务场景`
- `最大亮点`
- `推荐理由`
- `进入详情`

#### 第四层：专题导流

比如：

- 适合先看：入门样本
- 适合深挖：源码级样本
- 适合面试：自研项目与问答样本
- 适合产品化：平台型样本

### 5.3 卡片文案怎么写

这里最容易写废。

不要写：

- 很优秀
- 值得学习
- 架构清晰
- 很有启发

这种句子没有信息量。

卡片文案应该像这样：

- 主分类：`Agent Runtime`
- 业务场景：`本地代码仓库里的多步任务执行与恢复`
- 最大亮点：`把 checkpoint / resume 做成可信恢复协议，而不是重放聊天记录`

这种写法才会让人一眼知道为什么该点。

## 6. 详情阅读器要怎么升级

### 6.1 页面头要像文档头，不像详情卡

现在详情区更像“资料详情”。

后面应该更像正式文档头：

- 标题
- 一句话判断
- 主分类
- 业务场景
- 最大亮点
- 阅读时长
- 来源文档
- 最近更新时间

### 6.2 文档前置区要替用户先做一层理解

正文前面建议固定放四块：

1. 这项目先看什么
2. 真正亮点是什么
3. 最容易误读什么
4. 如果拿去面试最容易被追问什么

这四块会显著提升“学习价值”和“口语感”。

### 6.3 右侧目录要更像真正的阅读辅助

不是“有一个 TOC 就算完”，而是要做到：

- 当前章节高亮稳定
- 可回到顶部
- 支持跳到关键段落
- 支持展示“推荐先读章节”

### 6.4 页面动作要收敛成标准动作组

建议统一成：

- 复制链接
- 复制摘要
- 导出 Markdown
- 标记“这页有帮助”
- 标记“这里还不够深”

后面如果真要加 AI，也应该是：

- 基于当前页继续追问

而不是一个空泛的聊天按钮。

### 6.5 版式要更像飞书，而不是卡片后台

建议几个具体方向：

- 正文区适度变宽，但不要横向过散
- 文档头和正文之间层次更清晰
- 弱化无意义的盒子感
- 重点信息块要像“批注”或“结论块”，而不是普通卡片
- 减少“整页都是一堆边框框”的后台味

## 7. 文档内容要怎么改写，才会更像你要的风格

### 7.1 项目文档的固定模板要升级

以后项目文档不要再只按“功能 -> 优点 -> 启发”去写。

建议固定成：

1. 这个项目到底是干嘛的
2. 它打的是哪类业务场景
3. 它真正厉害的地方是什么
4. 行业内这个问题为什么普遍容易做烂
5. 它具体是怎么处理的
6. 哪些地方值得学，哪些不要盲抄
7. 如果拿去面试，最容易被追问什么
8. 对我自己的项目，下一步该怎么做

### 7.2 写法要求要更口语化，但不能水

“口语化”不是多用感叹句，也不是写成闲聊。

这里的口语化，是指：

- 少说空词，多说判断
- 少说“架构清晰”，多说“它把哪件脏活单独收口了”
- 少说“值得学习”，多说“这部分最值得抄，因为它解决了什么”

比如不要写：

> 它的 memory 设计比较完善，值得我们学习。

而要写：

> 这个项目的重点不是“有 memory”，而是它没有把 memory 当聊天记录堆栈，而是当成上下文治理系统。很多项目就死在这里，看起来会记，其实只是在不断把旧内容塞回 prompt。

这才是你要的那种“能学到东西”的写法。

### 7.3 每篇文档都要带“判断句”

每篇文档至少要有几句能单独带走的话：

- 它真正解决的不是 A，而是 B。
- 它最值钱的不是功能，而是边界处理。
- 这部分不要照抄，原因是……
- 如果你的项目现在还小，先学这半段，别学那半段。

这种句子会显著提升文档密度。

## 8. 数据结构要怎么配合改

为了支持“概述页 -> 详情页”，项目索引字段建议补成这样：

```json
{
  "id": "zzh-pico",
  "name": "pico",
  "primaryCategory": "Agent Runtime",
  "businessScenario": "本地代码仓库里的多步任务执行与恢复",
  "biggestHighlight": "把 checkpoint / resume 做成可信恢复协议",
  "oneLineVerdict": "不是聊天壳，而是本地 Agent Harness",
  "whyReadNow": "适合补 runtime、memory、tool governance、eval 这几条主线",
  "notFor": "如果你只是想看简单 demo，这篇会偏重",
  "interviewValue": "高",
  "readingDepth": "deep",
  "sourceFile": "...",
  "content": "..."
}
```

这样概述页和详情页才能各用各的字段，不会什么都挤在 `summary` 里。

## 9. 实施顺序建议

### P0：先定结构，不先卷样式

先做：

- 项目路由拆成概述页和详情页
- 项目索引字段补齐
- 文档模板升级

不要一上来先改 CSS。

### P1：把概述页做成真正的“判断页”

目标：

- 分类清晰
- 卡片字段固定
- 一眼知道“主分类 / 业务场景 / 最大亮点”

### P2：把详情页做成真正的“深读页”

目标：

- 文档头重构
- 右侧目录增强
- 前置导读区上线
- 页面动作标准化

### P3：统一写作风格并批量回写旧文档

目标：

- 新文档全部按新模板写
- 老文档逐步补齐判断句、业务场景、亮点、误区、面试追问

## 10. 这轮改版后，平台会变成什么样

改完之后，项目页应该形成很清晰的分工：

```text
概述页
  -> 帮你判断

详情页
  -> 帮你学习

文档内容
  -> 帮你带走判断和行动
```

这样平台就会从“能展示文档”，升级成“能带你读、带你想、带你往自己项目上落”的知识工作台。

## 11. 建议下一步直接做什么

下一步不要散改，我建议直接按下面顺序推进：

1. 先改索引结构，给项目补 `primaryCategory / businessScenario / biggestHighlight / oneLineVerdict`。
2. 再把项目路由拆成概述页和详情页。
3. 然后重做项目概述卡片。
4. 再升级详情阅读器的文档头、导读区、目录和页面动作。
5. 最后开始批量回写旧项目文档的写法。

## 6. 行业痛点研究版补充

从行业视角看，这次改版要解决的不是“页面观感一般”这么浅的问题，而是知识平台非常常见的三类失败：

- 内容越来越多，但用户越来越难判断“先看哪个”
- 文档看起来很全，但真正能带走的判断很少
- 平台有搜索、有路由、有 Markdown，却没有形成稳定的阅读决策链

把它翻成你这个平台的语境，其实就是：

- 概述层没有把“值不值得点开”说透
- 详情层没有把“为什么值得学、该学哪段、别学哪段”说透
- 文档层没有把“项目事实 -> 行业问题 -> 方法框架 -> 我的行动”收束成强判断

所以这轮改版的真正目标，不是更像某个文档产品，而是补齐知识平台在“判断层、阅读层、行动层”三个环节上的断层。
