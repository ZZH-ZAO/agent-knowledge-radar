# 文档重构规范

> 版本：2026-05-08  
> 作用：约束后续所有项目沉淀、方案沉淀、痛点沉淀都必须写成“强判断、强做法、强启发”的中文长文，而不是功能枚举或清单式摘要。

## 1. 总目标

知识平台里的文档，不是为了证明“看过这个项目”，而是为了让你读完之后能做到三件事：

- 讲清这个项目或方案到底解决什么问题
- 讲清它具体怎么做、为什么这样做、代价是什么
- 把它转成你自己的工程动作、面试表达和后续设计判断

如果一篇文档做不到这三件事，它就还不够格进入平台核心展示层。

## 2. 统一写作协议

每篇核心文档都必须回答下面五件事：

1. 它到底在解决什么
2. 这个项目或方案具体怎么做
3. 为什么这样做
4. 代价和边界是什么
5. 对当前项目有什么动作

## 3. 明确禁止的写法

### 3.1 只有问题，没有做法

错误例子：

- Agent 如何统一接入外部工具生态？
- 高风险工具如何做权限控制？

如果只有问题，没有项目里的真实做法、步骤、边界和证据，这种内容不能进展示层。

### 3.2 只有功能名，没有工程判断

错误例子：

- 有 MCP
- 有 Memory
- 有 Sandbox

这只是记录，不是沉淀。

### 3.3 只有“值得学”，没有“值在哪里”

错误例子：

- 这个项目很强
- 这个方案很成熟

必须继续往下写清楚：

- 强在哪
- 证据是什么
- 为什么成立
- 能迁移什么

## 4. 三类正文骨架

## 4.1 项目类文档

固定顺序：

1. 项目一句话
2. 为什么值得现在读
3. 核心场景
4. 它解决的通用问题
5. 这个项目具体怎么做
6. 优秀技术和框架
7. Trade-off 与边界
8. 可迁移设计原则
9. 对我当前项目的行动项
10. 证据链接

要求：

- “它解决的通用问题”必须解释为什么这是行业问题
- “这个项目具体怎么做”必须写步骤和机制
- “Trade-off 与边界”必须明确说明不适用场景

## 4.2 方案类文档

固定顺序：

1. 问题定义
2. 为什么普通做法不够
3. 典型方案结构
4. 成熟系统通常怎么做
5. 常见错误做法
6. 证据项目
7. Trade-off 与边界
8. 我的项目行动项

要求：

- 不允许写成术语罗列
- 必须说清成熟项目为什么这样拆
- 必须把方案结构讲成一条可执行逻辑

## 4.3 痛点类文档

固定顺序：

1. 行业里为什么反复出这个问题
2. 哪些项目或资料给了证据
3. 优秀项目具体怎么处理
4. 共性做法能抽成什么框架
5. 用什么信号判断是否改善
6. 当前平台先补哪一步

要求：

- 痛点页不能停留在“这个问题很难”
- 必须有证据项目
- 必须有数据或判断信号

## 5. 平台展示要求

文档改深之后，平台不能再把它压回一句摘要。展示层必须同时保留两层：

- 短判断：主分类、业务场景、最大亮点、为什么值得读
- 深正文：问题、做法、步骤、边界、行动项

这意味着项目页、方案页、痛点页都要遵守“双层展示”：

- 列表页负责一目了然
- 详情页和阅读器负责真正可学习

## 6. 证据要求

后续如果文档涉及具体项目做法，默认要尽量补证据：

- README
- 官方文档
- 源码模块
- CHANGELOG
- 本地项目源码
- 用户提供的文档材料

尤其是项目类文档，不能长期停在“待补源码”。

## 7. 重构优先级

平台直接展示层优先：

1. `docs/external-projects/`
2. `docs/patterns/`
3. `docs/pain-points/`
4. `docs/interviews/`
5. `docs/source-research/` 核心正文

辅助层后补：

1. `docs/source-library/`
2. `docs/platform/`
3. `docs/legacy-migration/`
4. `docs/templates/`
5. 各目录 `README.md`

## 8. 验收标准

一篇文档在进入平台核心展示前，至少要通过下面检查：

- 有明确问题定义
- 有“这个项目 / 方案具体怎么做”
- 有“为什么这样做”
- 有“Trade-off / 边界”
- 有“当前行动项”

如果缺任意一项，就还不算完成。
