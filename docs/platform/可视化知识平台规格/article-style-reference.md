# 平台文章风格参考

> 更新时间：2026-05-07
>
> 作用：约束知识平台里的项目页、方案页、痛点页不要只停留在功能枚举，而要写成真正有学习价值、有判断力、有工程含量的中文文章。

## 1. 这次参考了哪些外部写法

### 1.1 Stripe Engineering

参考方向：

- 先讲为什么这个问题值得解决。
- 再讲具体是怎么做的。
- 中间会不断补工程约束、取舍和数据。
- 文章不是“炫技”，而是让读者理解设计判断。

这类文章适合我们平台里的：

- 痛点页。
- 方案页。
- 工程逻辑页。

### 1.2 Linear Blog

参考方向：

- 文风克制，但判断很强。
- 很少堆概念，更多是在讲“这个决定为什么成立”。
- 擅长把抽象产品或设计问题写成清楚的工作方法。

这类文章适合我们平台里的：

- 项目页导读。
- 前端设计控制。
- 产品化与工程取舍。

### 1.3 Anthropic Context / Prompt Engineering

参考方向：

- 不是泛泛讲原则，而是会把方法拆成步骤。
- 会说明为什么这些步骤有效。
- 会强调边界、失效方式和验证方法。

这类文章适合我们平台里的：

- Agent Runtime。
- Tool Runtime。
- Memory / Context。
- Prompt / Multi-Agent。

## 2. 平台文章以后统一怎么写

### 2.1 先给结论，但不要只给结论

坏写法：

```text
它解决了 Agent 工具接入问题。
```

好写法：

```text
它真正解决的不是“接一个工具”，而是让 Agent 在接入外部工具后，仍然保持权限边界、结果可追踪、失败可恢复和上下文可控。
```

要求：

- 第一段要能回答“这件事到底值不值得学”。
- 不能只报功能名。
- 要把问题的真正难点说出来。

### 2.2 必须写“这个项目具体怎么做”

不能只写：

- 通用问题是什么。
- 技术框架是什么。

还必须写：

- 这个项目具体用了哪些做法。
- 它的步骤顺序是什么。
- 它的边界控制在哪里。
- 它为什么这样拆。

理想结构：

```text
问题
  -> 项目做法
  -> 做法拆解
  -> 为什么这样做
  -> 代价和边界
  -> 对我的启发
```

### 2.3 少写“术语堆叠”，多写“工程判断”

坏写法：

```text
它采用 Tool Registry + Permission Mapping + Observability。
```

好写法：

```text
它先把工具统一登记到 Tool Registry，再补权限等级和副作用描述。这样做的好处是，模型在决定调用之前，就已经有了“这个工具危险不危险、是否要确认、结果该怎么返回”的明确边界，而不是等调用出问题再补救。
```

要求：

- 术语出现时，要解释它在这个项目里到底扮演什么角色。
- 要写清楚“为什么这样做”，不是只写“做了什么”。

### 2.4 文章里要有“读者能带走什么”

每篇都要尽量回答：

- 我读完之后到底学到了什么。
- 我以后做项目时哪里可以直接照着用。
- 哪些能现在做，哪些要后面做。

不能让内容停留在：

```text
我知道这个项目很厉害。
```

要推进到：

```text
我知道它厉害在哪。
我知道它是怎么做到的。
我知道我自己的项目该先抄哪一步。
```

### 2.5 必须有 Trade-off

优秀文章不会把方案写成银弹。

每篇至少要写清楚一类：

- 成本。
- 风险。
- 不适用场景。
- 为什么不能直接照搬。

因为真正有学习价值的内容，往往来自：

- 为什么要做这个取舍。
- 为什么别的简单做法不够。
- 为什么这个做法在另一个场景可能失效。

## 3. 三类页面的具体写法

### 3.1 项目页

项目页不是项目介绍页，而是：

```text
一个样本为什么值得学
它到底解决了什么
它具体怎么做
它能迁移成什么方法
```

建议结构：

1. 项目一句话。
2. 为什么值得现在读。
3. 它解决的真实问题。
4. 它具体怎么做。
5. 关键步骤与工程边界。
6. 可迁移设计原则。
7. 对当前项目的行动项。

### 3.2 方案页

方案页不是术语页，而是：

```text
某一类问题，成熟系统通常怎么解决
```

建议结构：

1. 问题定义。
2. 为什么普通做法不够。
3. 成熟方案的典型结构。
4. 常见步骤。
5. 常见误区。
6. 证据项目。
7. 我们该怎么做。

### 3.3 痛点页

痛点页不是抱怨页，而是：

```text
行业为什么反复在这里出问题
哪些项目证明它是真的
成熟做法到底是什么
我应该怎么把它转成动作
```

建议结构：

1. 行业痛点定义。
2. 为什么它会反复出现。
3. 证据项目和证据来源。
4. 优秀项目具体怎么解决。
5. 共性做法。
6. 数据信号。
7. 当前项目行动项。

## 4. 平台写作禁忌

### 4.1 禁止只有标题，没有展开

例如只写：

- Agent 如何统一接入外部工具生态？
- 高风险工具如何做权限、安全和审计？

这种只有问题，没有项目做法、没有步骤、没有边界，就不够。

### 4.2 禁止只有功能枚举

例如：

- 有 MCP
- 有 Memory
- 有 Sandbox

这不叫沉淀，只叫记笔记。

### 4.3 禁止只写“很好、很强、很值得”

所有价值判断都尽量往下落：

- 值得在哪里。
- 证据是什么。
- 能迁移什么。

## 5. 当前执行规则

从这次开始：

- 项目页优先补“这个项目具体怎么做”。
- 自动分析不再只截一句话，要尽量保留完整段落。
- 新文档生成时，优先生成“问题 -> 做法 -> 步骤 -> 边界 -> 启发”的结构。
- 后续继续把方案页和痛点页也统一到这套文章骨架。
