## 1. 平台一句话

这个平台的目标不是做一个“看 Markdown 的网页”，而是做一个能持续发现优质项目、把它们沉淀成高质量文档、再进一步抽象成工程方法论的 Agent 工程知识平台。

它最终要回答三件事：

- 哪些外部项目、博客、论文和资料值得学。
- 它们背后的通用问题、行业痛点和工程逻辑是什么。
- 这些学习结果怎样直接反哺我以后做项目时的设计、实现、验证和表达。

## 2. 核心定位

### 2.1 它不是什么

它不是：

- 普通文档站
- 项目链接收藏夹
- 只会展示 Markdown 的前端壳
- 只会总结“这个项目有哪些功能”的目录页

### 2.2 它是什么

它是一条知识转化流水线：

```text
外部资料发现
  -> 项目沉淀
  -> 痛点研究
  -> 方案抽象
  -> 工程逻辑收束
  -> 学习、项目决策、面试表达
```

其中每一层都服务同一个目标：

```text
总结沉淀项目
  -> 让我学习和直接使用
  -> 让我以后做项目时拥有更完整的工程逻辑
```

## 3. 当前是否符合目标

### 3.1 已经具备的能力

当前平台已经有这些基础：

- 稳定路由：`项目 / 方案 / 痛点 / 工程逻辑 / 资料源 / 面经 / 面试官 / 雷达 / 视觉生成`
- 结构化文档体系：`external-projects / patterns / project-radar / source-library / interviews / platform`
- 索引构建：`docs/**/*.md -> knowledge-index.json -> 前端展示`
- 统一搜索：项目、方案、痛点、资料源、面经、工程逻辑可统一检索
- 文档健康检查：`knowledge_lint.py`
- 外部资料入口：GitHub、博客、论文、用户文档已进入同一条知识链路
- 平台化阅读界面：支持长文阅读、检索和路由跳转

### 3.2 还没完全达到的部分

离最终理想状态，还差三类关键能力：

- 自动发现能力还不够强：现在已有 `Project Radar`，但外部资料接入仍以半自动为主。
- 自动进化能力还不够深：结构已经搭起来了，但高质量文档仍需要持续补厚。
- 工程逻辑层刚成型：已经有入口和索引，但还需要更强的阶段化阅读与决策辅助。

## 4. 平台最终目标结构

```text
优质项目 / 博客 / 论文 / 用户资料
  -> 资料源筛选
  -> 单项目沉淀
  -> 行业痛点提炼
  -> 通用方案抽象
  -> 工程逻辑收束
  -> 当前项目行动项
  -> 面试表达与复盘
```

这条链路之所以重要，是因为你的真实需求不是“收集项目”，而是：

- 把外部项目变成自己的设计资产
- 把零散知识变成工程判断
- 把学习材料变成项目实施逻辑
- 把项目实施逻辑再变成复盘和面试表达能力

## 5. 路由规划

### 5.1 路由清单

- `项目`
- `方案`
- `痛点`
- `工程逻辑`
- `资料源`
- `面经`
- `面试官`
- `雷达`
- `视觉生成`

### 5.2 每个路由的职责

#### 项目

看单个优质项目本身：

- 解决什么问题
- 为什么值得学
- 可迁移什么
- 下一步能做什么

#### 方案

看多个项目背后的通用技术框架：

- 问题定义
- 成熟做法
- 常见误区
- 当前项目行动项

#### 痛点

看 Agent / 大模型行业里的共性难题：

- 行业现象
- 项目证据
- 共性解法
- 数据线索
- 当前应对

#### 工程逻辑

看“以后做真实项目时到底该怎么一步步做”：

- 先看什么
- 先设计哪一层
- 主要风险在哪里
- 如何验证
- 文档如何反过来驱动决策

#### 资料源

看外部输入：

- 来源类型
- 证据强度
- 推荐使用方式
- 它能补强哪个项目 / 方案 / 痛点

#### 面经 / 面试官

看学习输出与表达训练：

- 面试题
- 推荐回答
- 项目证据
- 弱点
- 追问链

#### 雷达

看候选池与自动发现能力：

- 哪些项目值得继续沉淀
- 评分是否合理
- 下一批学习对象是什么

#### 视觉生成

看前端视觉工作流：

- 如何用 GPT Image 2 辅助页面目标生成
- 如何把 mockup 落到真实前端工程

## 6. 文档的真实目的

平台里的文档不能只是“说明文档”，它们应承担四种作用：

### 6.1 学习材料

帮助你真正理解项目、方案和痛点，而不只是知道名字。

### 6.2 工程资产

帮助你以后做项目时直接复用设计逻辑、架构判断和方法论。

### 6.3 决策依据

帮助你判断：

- 现在该学哪个项目
- 这个问题该参考什么方案
- 这个痛点有没有成熟做法

### 6.4 表达素材

帮助你以后做：

- 项目汇报
- 技术复盘
- 系统设计
- 项目面试

## 7. 平台当前的主要优势

### 7.1 不是从零开始

现在已经有：

- 旧文档迁移基础
- 新文档体系
- 深度沉淀模板
- 行业痛点结构
- 资料源入口
- 搜索和 lint
- 平台化前端阅读层

### 7.2 结构方向是对的

现在的结构已经不是：

```text
项目列表
  -> 功能总结
```

而是：

```text
项目
  -> 通用问题
  -> 行业痛点
  -> 工程框架
  -> 行动项
```

### 7.3 已经有“自我进化”的雏形

虽然不是全自动，但已经有：

- `Project Radar`
- `source-library`
- `searchIndex`
- `knowledge_lint.py`
- 前端阅读平台

这说明平台已经开始具备“自己发现、自己整理、自己检查”的能力。

## 8. 当前平台的主要短板

### 8.1 内容深度还不均衡

有些文档已经很厚，有些文档仍偏骨架化，还需要继续补证据、补案例、补启发。

### 8.2 自动化更偏结构，内容质量还不够自动

现在自动化能保证：

- 文档被索引
- 文档被分类
- 文档能被搜索
- 文档能被 lint

但还不能稳定保证：

- 每篇文档的思想深度
- 每个痛点的证据厚度
- 每个方案的案例密度

### 8.3 工程逻辑层刚进入产品化阶段

现在已经有“工程逻辑”入口，但还需要继续增强：

- 阶段化阅读
- 标题跳转
- 证据反链
- 导出能力
- 从行动项回流到文档更新

## 9. 行业痛点研究版补充

### 9.1 平台真正对应的行业痛点

这个平台服务的不是“文档展示问题”，而是 Agent / 大模型工程领域里很普遍的断层：

- 好项目很多，但没有被转成可迁移的工程知识。
- 好博客、论文、源码和用户资料分散，没有统一证据链。
- 学习停在功能枚举，不能回答为什么这样设计。
- 文档和未来工程决策脱节，做项目时仍要从头摸索。
- 面经、八股、项目沉淀没有打通，表达和工程理解是割裂的。

### 9.2 我们从现有沉淀里看到的共性

平台里已经逐渐验证出一个共性：

- `项目` 只能提供样本
- `方案` 才能抽象方法
- `痛点` 才能解释为什么重要
- `工程逻辑` 才能把它们真正收束成未来项目的决策链路

所以平台不是一个内容仓库，而是一台知识转化机。

### 9.3 后续最该持续增强的方向

- 自动发现更强
- 自动关联更准
- 痛点证据更厚
- 工程逻辑更集中
- 面经和项目更联动

## 10. 后续阶段规划

### 阶段 A：把现有平台做扎实

目标：

- 让现有路由内容更均衡
- 让资料源、项目、痛点、方案之间关系更清楚
- 收掉 lint 中的内容型缺口

### 阶段 B：增强自动发现与自动沉淀

目标：

- 让平台更少依赖手工找项目

重点：

- 强化 `Project Radar`
- 加入更多 GitHub 搜索策略
- 加入博客 / 论文 intake
- 把新来源自动关联到痛点和方案

### 阶段 C：把工程逻辑层做成主决策页

目标：

- 让“工程逻辑”成为整个平台的收束层

重点：

- 串起发现、沉淀、抽象、诊断、决策、实施、表达
- 让文档输出直接服务未来项目实施

### 阶段 D：做成长期开启就能用的日常工具

目标：

- 让平台更像工作台，而不只是阶段性整理产物

重点：

- 更强搜索
- 版本历史
- block 引用
- 导出
- 更好的阅读跳转与导航

## 11. 验收标准

### 11.1 项目沉淀标准

- 能稳定沉淀高质量外部项目
- 不是只写功能列表
- 每份项目文档都能给出可迁移原则和行动项

### 11.2 学习使用标准

- 你能快速找到某类问题的代表项目
- 能看到成熟做法和错误做法
- 能知道为什么要这样设计

### 11.3 工程逻辑标准

- 平台能把外部知识转成你自己的工程方法论
- 最后能指导你以后做项目时的设计、实现、验证、复盘

### 11.4 进化标准

- 平台能持续吸收新项目和资料
- 能自动更新索引、搜索和质量检查
- 能逐渐把半成品文档推成成熟文档

## 12. 当前结论

当前平台已经明显符合你的方向和主定位：

```text
项目沉淀平台
  -> 学习平台
  -> 工程逻辑平台
```

更准确地说，它现在处于：

```text
学习沉淀平台：已成型
工程逻辑平台：正在成型
自动进化平台：还在加强
```

所以现在最合理的判断不是推翻重做，而是沿着当前结构继续推进，重点补强：

- 工程逻辑层
- 自动发现与自动更新
- 痛点证据厚度
- 长文阅读和知识回流能力
