# 项目沉淀：oil-oil/draw-ui

> 来源：<https://github.com/oil-oil/draw-ui>  
> 沉淀日期：2026-05-04  
> 项目类型：Claude Code Skill、GPT Image 2、UI mockup、Frontend Reconstruction  
> 核心关键词：GPT Image 2、Claude Code Skill、UI Design Mockup、Screenshot Comparison、HTML/CSS Reconstruction、Design Control

## 1. 项目一句话

`draw-ui` 是一个面向 Claude Code / Cursor 等 Agent 工作流的 UI 设计 skill。它用自然语言需求生成 UI mockup，并把生成出来的 UI 截图进一步转成 HTML/CSS 重建任务。

它真正解决的问题不是“画一张好看的图”，而是：

```text
如何让编码 Agent 先获得稳定视觉目标，再按截图对照把前端页面实现出来？
```

## 2. 为什么值得学

在前端开发里，编码 Agent 常见的问题是能写组件，但视觉目标不稳定。你只说“做一个高级 Dashboard”，Agent 很容易直接写出一版能跑但普通的页面。

`draw-ui` 的价值在于把前端生成拆成两步：

```text
先生成视觉稿
  -> 再用浏览器截图对照重建页面
```

这比直接让 Agent 一步到位写 React 页面更稳，因为视觉稿先把布局、密度、导航、色彩、层级和页面气质固定下来。

## 3. 核心场景

### 3.1 从自然语言生成 UI mockup

用户可以提出类似“设计一个 Dashboard 页面”“设计用户资料页”“出图，产品详情页”的需求，skill 会先询问必要信息，再生成视觉稿。

这个流程适合：

- 新页面视觉探索。
- 后台工作台页面。
- 产品详情页。
- 多屏 App 原型。
- 需要先统一视觉方向的前端改版。

### 3.2 多页面导航一致性

项目强调可以用 reference image 锁定 navigation / sidebar 一致性。这个点很重要，因为多页面前端最容易出现的问题不是单页不好看，而是每一页像不同系统。

可迁移做法：

```text
第一张图确定全局导航和页面气质
  -> 后续页面都把它作为 reference
  -> 只变化主内容区，不重复发明整体结构
```

### 3.3 UI 截图到 HTML/CSS 重建

`draw-ui` 不只生成图，还会指导 HTML reconstruction，包括：

- asset strategy。
- browser screenshot comparison。
- logo / illustration 的背景移除规则。
- 根据截图差异继续迭代。

这让它更像一个“视觉稿到代码”的工作流，而不是单纯提示词集合。

## 4. 它解决的通用问题

### 4.1 Agent 生成前端缺少视觉目标

如果没有视觉稿，Agent 只能凭文字描述推断页面，容易出现风格漂移、信息密度不合适、组件层级混乱。

`draw-ui` 的解法是先生成 mockup，把目标从抽象文本变成可对照的视觉样本。

### 4.2 图像模型输出如何进入工程闭环

很多图像生成项目只停在“出图”。`draw-ui` 更值得学的是它把图像输出接到工程执行：

```text
需求
  -> 视觉提示词
  -> GPT Image 2 mockup
  -> 前端实现
  -> 浏览器截图
  -> 与 mockup 对照
  -> 继续修正
```

这个闭环适合直接迁移到我们的知识平台前端迭代。

### 4.3 多屏 UI 如何保持一致性

它用 reference image 锁定导航/侧栏一致性，本质上是在做轻量的视觉上下文注入。

这和我们已有的 `DESIGN.md` 是互补关系：

```text
DESIGN.md 负责文字规则
reference image 负责视觉锚点
```

## 5. 优秀技术和框架

### 5.1 Skill 形式接入 Agent

`draw-ui` 不是独立 SaaS，而是 Claude Code skill。优点是它能直接嵌入编码 Agent 的开发现场：

- Agent 能先生成视觉稿。
- 再打开项目源码。
- 再实现页面。
- 最后用截图对照校准。

这比外部设计工具更贴近“AI 编程工作流”。

### 5.2 GPT Image 2 作为视觉目标生成器

项目 README 明确说明脚本化本地输出时使用 GPT Image 2，并处理 `edit_image` API 的一些执行细节，例如串行执行和重试。

可迁移原则：

```text
图像模型不要直接替代前端工程
图像模型负责生成视觉目标
编码 Agent 负责把目标工程化
```

### 5.3 Prompt 技法分层

项目提到 analogy-style 和 inventory-style prompt 技法。可以理解为两类前端视觉提示词：

- analogy-style：用成熟产品或风格类比来稳定整体气质。
- inventory-style：枚举页面区域、组件、状态、信息密度和视觉约束。

对我们的平台来说，后者更适合工程工作台，因为知识平台需要信息密度和结构稳定，而不是纯审美探索。

### 5.4 截图对照验证

浏览器截图对照是把视觉生成接入前端工程的关键，不然 mockup 和实际页面之间会断开。

成熟流程应该至少包含：

- 生成目标图。
- 实现页面。
- 运行本地页面。
- 截图。
- 对比布局、间距、字体、颜色、内容溢出。
- 修改 CSS / 组件。

## 6. 可迁移设计原则

### 原则一：先出视觉目标，再写页面

对新页面、大改版、视觉不确定的页面，先生成 mockup，再进入代码实现。

### 原则二：reference image 是视觉上下文

多页面系统要把首屏或核心页面作为 reference，避免每个页面重新发明导航、侧栏、卡片、按钮和密度。

### 原则三：图像模型只负责目标，不负责真实 DOM

GPT Image 2 生成的是视觉方向，不是可访问、可维护、可响应式的前端实现。真正的工程质量仍然要靠 React/CSS、组件约束和截图验证。

### 原则四：和 DESIGN.md 配合使用

`DESIGN.md` 提供文字规则，GPT Image 2 mockup 提供视觉锚点，两者结合才适合长期维护。

### 原则五：不要为每个小改动都出图

只有新页面、风格不确定、大改版、多页面一致性校准时才值得使用图像模型。普通按钮、表格、状态文案修改仍然应该直接编码。

## 8. 边界和风险

- 仓库 star 数不高，说明它更像早期工作流样本，需要重点学方法，不要直接当成熟框架依赖。
- 它依赖外部图像生成服务和 API key，落地时要考虑成本、速率、隐私和失败重试。
- 生成图可能存在文字不准、布局细节不稳定、响应式不可见等问题。
- 从截图重建页面仍然需要工程判断，不能把 mockup 当成唯一真相。

## 深度学习版补充

> 学习目标：读完这部分后，不只是知道“项目沉淀：oil-oil/draw-ui 做了什么”，而是能讲清它背后的工程问题、适用边界、常见误区和对当前平台的迁移路径。

### 1. 这件事到底考什么

这里真正考察的不是会不会调用一个 API，而是能不能把 Agent 对外部世界的行动放进可治理的执行管线。

如果只回答功能点，说明还停留在“看过项目”的层面；如果能回答问题来源、工程约束、取舍和行动项，才说明这份沉淀真正进入了自己的方法论。

### 2. 口语版回答

我会把工具调用理解成 Agent Runtime 的行动边界。成熟系统不能只关心函数能不能执行，还要关心输入协议、权限分级、执行隔离、结果压缩、错误恢复和审计回放。否则模型一旦误调工具，风险会直接落到真实文件、浏览器、网络或业务系统上。

这段回答可以直接用于复盘、面试或方案评审。它的结构是：先定义问题，再讲工程边界，最后落到可迁移做法。

### 3. 工程视角拆解

可以按四层来理解：

- 问题层：这个设计到底在解决什么不稳定、不可控或不可复用的问题。
- 机制层：它用了哪些结构、协议、运行时、文档或流程来解决。
- 证据层：有哪些 README、源码、指标、案例或平台行为能证明它不是口号。
- 迁移层：它对 `claude-code-sourcemap`、知识平台、Project Radar 或面试训练有什么可执行启发。

### 4. 常见误区

把 MCP 或 Tool Calling 当成普通 API wrapper，只写 schema，不写权限、结果治理和失败恢复。

另一个常见误区是只把优秀项目当作模板照抄。真正应该学的是它为什么这样拆分，以及这个拆分在自己的场景里是否仍然成立。

### 5. Trade-off 与边界

治理越完整，接入成本越高；但如果工具有副作用，前期省掉治理，后期会以安全事故、上下文爆炸和不可复现的形式还回来。

判断一个方案是否成熟，不是看它有没有更多能力，而是看它有没有明确说明代价、适用场景和不适用场景。

## 行业痛点研究版补充

> 目标：把“项目沉淀：oil-oil/draw-ui”从单篇资料或单个项目笔记，升级成能服务行业痛点研究、优秀做法抽象和当前项目行动的学习资产。

### 1. 它对应的行业痛点

Agent 接入外部工具后，行业共性痛点是权限、结果大小、执行副作用、工具质量和可观测性会同时失控。优秀项目不会把工具当普通函数，而会把它放进 Tool Runtime / MCP Integration 的治理管线。

判断它是不是值得持续沉淀，不看它是否新奇，而看它能不能解释一个反复出现的行业问题，并能不能给当前项目带来可执行改变。

### 2. 可作为证据的来源类型

GitHub 工具型项目、MCP server、旧体系工具文档、源码 README、浏览器自动化案例。

后续如果新增 GitHub、优质博客、论文或你提供的文档，都应该先判断它能否补强这一类证据，而不是直接堆进知识库。

### 3. 优秀项目或资料的共性做法

共性做法是 Tool Registry + Permission Mapping + Result Summary + Artifact Reference + Audit Trail，把调用、权限、结果和追踪拆开治理。

这里真正要学的不是表层功能名，而是成熟项目如何划分边界、控制风险、组织证据、形成可复用流程。

### 4. 数据支撑与判断信号

可观察信号包括工具数量、权限等级覆盖率、单次结果 token 数、artifact 引用比例、失败调用可复现率。

这些信号用于避免主观判断。后续平台应该让痛点页自动展示证据项目数、来源类型、关联方案数和行动项数量。
