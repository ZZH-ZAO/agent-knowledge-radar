# 行业痛点：Tool Result / Context Overload

## 1. 这个问题为什么会在行业里反复出现

很多 Agent 项目一开始都把工具调用理解成一句很简单的话：模型发起调用，工具返回结果，模型继续往下推理。这个理解在 demo 阶段没问题，但一旦工具开始接浏览器、仓库、日志、trace、截图、数据库、搜索结果、网页正文，问题就会立刻暴露出来。

真正的瓶颈往往不是“工具能不能调用成功”，而是“返回结果能不能被系统健康消费”。如果一份工具结果又长、又杂、又没有层次，模型会先被上下文噪声拖慢，用户也会失去对证据链的控制感。更糟的是，团队常常误以为这是上下文窗口不够大，继续堆 token、堆摘要、堆压缩，最后把一个本来应该治理结果结构的问题，误做成了模型成本问题。

所以这个痛点的本质不是大模型太弱，而是 Tool Runtime 没有把“结果治理”当成正式协议。没有结果分层、没有 artifact 引用、没有 follow-up 查询、没有证据回链，系统就会天然走向上下文膨胀。

## 2. 哪些项目给了直接证据

### ChromeDevTools/chrome-devtools-mcp

这是最典型的高结果体量样本。浏览器自动化天然会产出截图、性能分析、网络请求、DOM 结构、trace 等重结果。这个项目值得学的地方，不是它“接进了浏览器”，而是它没有把所有原始结果粗暴塞回模型，而是更强调工具结果的可消费性、后续查询能力和证据引用。

### anthropics/claude-code

Claude Code 的价值在于，它把工具调用放进了正式产品运行时，而不是把工具当成 prompt 里的外挂函数。只要工具真的开始落地到终端、文件、搜索、MCP 和子任务协作，结果治理就一定会变成一等公民，否则整个运行时迟早会被高噪声结果拖垮。

### zzh/pico

`pico` 给我们的启发不是“它工具更多”，而是它已经开始把结构化状态、trace、report、resume 信息分层记录。这说明成熟系统不会让所有执行结果都直接进入同一层上下文，而是会把“当前要继续推理的信息”和“需要保留证据但不必立即注入的信息”拆开。

## 3. 优质项目具体怎么解

成熟项目的做法通常不是减少工具能力，而是重做结果协议。一个健康的 Tool Result 至少会被拆成下面几层：

- `summary`：先告诉模型发生了什么，够不够继续决策
- `structured slice`：只保留当前推理真正需要的字段
- `artifact reference`：把截图、长日志、完整页面、trace 等重结果留在外部引用
- `follow-up action`：告诉模型下一步怎么继续缩小范围，而不是再吞一整坨数据

以浏览器场景为例，成熟系统不会让模型每次都重新读完整页面、完整 trace、完整截图 OCR，而是会先给一层可判断摘要。如果摘要不够，再通过 follow-up query 去追某个节点、某段日志、某个请求、某个截图区域。

换句话说，重点不是“返回更多”，而是“返回更适合继续工作的信息层级”。

## 4. 跨项目能抽出的共性框架

```text
Raw Tool Output
  -> Summary
  -> Structured Slice
  -> Artifact Reference
  -> Follow-up Query
  -> Audit / Evidence Link
```

这个框架最值钱的地方在于，它把“一次性吞完整结果”改成了“逐层展开、逐层追证”。这样模型的上下文压力、用户的复盘成本、系统的失败概率都会一起下降。

进一步一点，结果治理还应该和权限、审计、恢复能力连起来。因为结果一旦被引用而不是被整包注入，后续就会自然带出：

- artifact 的生命周期怎么管
- 结果是否可重放
- 哪些结果只允许用户看，不允许直接注入模型
- 哪些结果需要脱敏、裁剪或摘要化

## 5. 怎么判断这个痛点有没有改善

单靠主观感受是不够的，至少要看下面几类信号：

- 单次 tool result 的平均长度是否持续下降
- artifact reference 的使用比例是否上升
- follow-up query 是否比“重新整页读取”更常见
- 因结果过长导致的中断、截断、答非所问是否减少
- 用户复盘时，是否能快速定位“答案来自哪个结果引用”

如果平台后续要做自动评估，这个痛点也很适合加观测指标，因为它能直接反映系统是不是还停留在“工具能跑”阶段，而没有进入“工具可治理”阶段。

## 6. 常见误区

- 误以为上下文窗口更大，这个问题就自然消失
- 误以为多做几层摘要，就等于完成了结果治理
- 工具结果只追求信息完整，不考虑后续推理成本
- 只有工具 schema，没有结果 schema
- 把所有截图、日志、长文本都塞回模型，最后再怪模型不稳定

## 7. 这对当前平台意味着什么

这个痛点对知识平台的直接启发非常明确：以后我们沉淀工具类、浏览器类、MCP 类项目时，不能只写“有哪些工具”，而要稳定抽出下面这些字段：

- 结果是否分层
- 是否有 artifact reference
- 是否支持 follow-up query
- 是否有统一 result schema
- 是否有结果审计或证据回链

也就是说，平台后续不该只按“Tool Runtime”分类，还应该能按“结果治理成熟度”去比较项目。

## 8. 我们下一步先补什么

- [ ] 在工具类项目沉淀模板里固定抽取 `summary / structured result / artifact refs / follow-up actions`
- [ ] 给 pain-point 聚合结果补一个“结果治理做法”字段，支持跨项目比较
- [ ] 后续在方案页补一篇更完整的 `tool result policy` 文档，把结果协议、artifact、审计和恢复连起来
- [ ] 平台搜索后续支持按 `artifact`, `summary`, `result schema` 这类关键词命中相关项目与痛点
