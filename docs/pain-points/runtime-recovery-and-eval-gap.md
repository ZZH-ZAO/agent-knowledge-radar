# 行业痛点：Runtime Recovery / Eval Gap

## 1. 为什么很多 Agent 能跑，但一中断就露馅

这是行业里特别典型的一种错觉：系统能完成一次 demo，于是团队默认它已经具备长期运行能力。可只要任务被中断、环境变化、工具失败、用户离开、流程切换，系统马上就会暴露出另一个真相：

它会运行，不代表它会恢复；它能产出结果，不代表它能证明结果可靠。

很多 Agent 项目的恢复能力其实停留在“把聊天记录重新喂回去”。这在简单问答里还能勉强工作，但到了编码、工具调用、浏览器操作、长任务执行、后台 session 这些场景就不够了。因为真正需要恢复的，不只是对话文本，而是任务状态、工作区身份、工具执行轨迹、检查点、证据链和当前可信边界。

同样，很多项目会做 benchmark，却没有把真实运行状态和评估体系接起来。结果就是评测是评测，恢复是恢复，线上失败之后无法形成稳定回归闭环。

## 2. 哪些项目已经把这件事做得更像工程

### zzh/pico

`pico` 是这条痛点最扎实的本地样本。它已经把 `TaskState`、`RunStore`、`trace.jsonl`、`report.json`、checkpoint schema、resume validation、metrics、evaluator 这些层串起来了。真正值得学的不是它用了多少文件，而是它已经承认：恢复、状态、追踪、评估本来就是一条链，而不是彼此独立的辅助功能。

### anthropics/claude-code

Claude Code 公开能力里出现 background sessions、subagents、remote control、memory、settings，本身就在说明一件事：正式产品不会把运行过程理解成“一次会话结束就结束”。只要系统进入真实工程环境，恢复协议和状态连续性就一定会成为运行时的一部分。

### 当前平台自身

知识平台后续如果要做“持续沉淀 -> 自动回写 -> 自动进化”，其实也绕不过这条痛点。因为一旦任务中断、回写失败、映射失误、索引构建异常，我们就需要回答：上次做到哪一步、哪些结果可信、哪些应该重跑、哪些可以复用。

## 3. 优秀项目具体怎么解

成熟系统通常不会把恢复理解成“重新开始”，而是把它设计成一套运行合同。

### 3.1 先有任务状态

系统必须知道当前任务处在哪个阶段，已经完成了哪些动作，哪些动作只执行了一半，哪些结果只是中间态。

### 3.2 再有 checkpoint

checkpoint 不是简单存一份文本，而是要能描述：

- 工作区身份
- 当前输入版本
- 已执行步骤
- 可继续的上下文边界
- 需要重新校验的外部依赖

### 3.3 resume 前做 validation

成熟系统不会默认“有 checkpoint 就能续跑”。恢复前至少要校验工作区是否变了、依赖是否变了、关键输入是否过期、工具状态是否还能复现。

### 3.4 trace / report 进入同一条证据链

恢复不是为了“接着跑”，也是为了“解释刚才发生了什么”。所以 trace、report、metrics、error classification 不应该分散在多个互不连通的角落，而要能互相引用。

### 3.5 eval 不脱离真实运行状态

真正有价值的评估不是单独做一套样题，而是让真实运行中暴露出来的失败类型，能回流成可重复的评测样本和回归指标。

## 4. 这条痛点背后的共性框架

```text
Execution
  -> Task State
  -> Checkpoint
  -> Resume Validation
  -> Trace / Report
  -> Metrics / Benchmark
  -> Regression Loop
```

这套结构说明一个成熟 Agent 不只是“会完成任务”，而是“会在任务失败、中断、升级、切换之后，仍然知道自己该如何继续，以及如何证明这次继续是可信的”。

## 5. 用什么信号判断是否改善

- 可恢复任务占比是否上升
- resume 后继续成功率是否提高
- 失败分类是否更完整、更稳定
- trace / report 是否能支撑复盘而不是只记录日志
- benchmark 是否开始覆盖真实失败类型，而不是只覆盖理想流程

如果一个系统每次失败都只能靠人工复盘和手动重试，那它还没有真正进入恢复能力阶段。

## 6. 常见误区

- 把聊天记录当成全部状态
- 有日志就以为有恢复能力
- 只做 checkpoint，不做 resume validation
- 评估体系和真实运行失败完全脱节
- 失败之后只修 prompt，不把失败回流成回归样本

## 7. 这对当前平台意味着什么

知识平台后续做自动回写闭环时，不能只关注“有没有成功生成文档”，还要能回答：

- 哪一步生成成功了
- 哪一步回写成功了
- 哪一步索引更新成功了
- 哪一步失败后可以继续跑，哪一步必须重算

换句话说，我们的平台也需要一套轻量版的 recovery / eval 思路。否则越自动化，越难定位问题。

同时，在沉淀项目时，平台也应该稳定抽取：

- 是否有 task state
- 是否有 checkpoint schema
- 恢复前是否做 validation
- trace / report 怎么组织
- eval 是否和真实运行失败闭环

## 8. 我们下一步先补什么

- [ ] 在项目沉淀模板里固定抽 `task state / checkpoint / resume validation / trace / eval`
- [ ] 给自动回写链路补一层可恢复状态记录，至少知道失败发生在哪个阶段
- [ ] 后续补一篇 `runtime recovery` 方案文档，把恢复协议、证据链和评估闭环讲透
- [ ] 继续深挖 `pico` 的 checkpoint、trace、report 和 evaluator 关系，作为平台重点样板
