# 行业共性痛点总纲

> 这份文档不是“吐槽 Agent 很难做”，而是给平台一个稳定的问题坐标系：以后每沉淀一个项目、资料、博客或论文，都要问它到底补强了哪条行业痛点证据链。

## 1. 痛点到底应该怎么定义

平台里的“痛点”必须满足三个条件：

- 它不是某个项目的私有 bug，而是行业里反复出现的结构性问题。
- 它会直接影响系统长期可用性、可扩展性或用户信任。
- 它值得被多个项目、多个来源、多个证据反复验证。

如果一个问题只是某个仓库今天没配好环境，那不叫行业痛点；如果一个问题在 GitHub 项目、工程博客、论文、面经和你自己的项目里都在反复出现，它才值得进入这里。

## 2. 为什么行业会反复掉进同样的坑

Agent / 大模型工程最容易让人误判的地方是：表面上看起来每个项目都在做不同功能，实际上大家反复撞上的，是同一批底层矛盾。

这些矛盾通常来自五个来源：

- 模型输出天然不稳定
- 工具有真实副作用
- 上下文预算有限
- 用户信任是产品上限
- 很多团队先追功能，再补治理

所以行业痛点之所以会反复出现，不是因为大家都不聪明，而是因为这些问题本来就不是“多写几个 prompt”能解决的。

## 3. 平台应该如何研究痛点

以后每个痛点页，都应该沿着这条研究路径往下写：

```text
行业里为什么反复出这个问题
  -> 哪些项目或资料给了证据
  -> 优秀项目具体怎么处理
  -> 共性做法能抽成什么框架
  -> 有哪些数据信号能判断是否改善
  -> 我们下一步先补哪一层
```

如果一篇痛点文档只有“问题定义 + 建议做法”，那它还只是观点，不算研究资产。

## 4. 当前最值得优先跟踪的行业痛点

## 4.1 Tool Runtime 与权限治理

### 为什么会反复出现

因为几乎所有 Agent 一旦进入真实仓库，都绕不开文件读写、命令执行、网络访问、浏览器自动化、外部系统调用。工具越多，副作用越多，责任边界就越模糊。

### 证据项目

- `anthropics/claude-code`
- `ChromeDevTools/chrome-devtools-mcp`
- `zzh/pico`

### 优秀项目具体怎么做

成熟项目不会把工具当成“可直接调用的函数集合”，而会先做几层治理：

- 工具注册与签名
- 风险等级与确认策略
- 路径或环境边界检查
- 执行前后钩子
- 结果压缩与 artifact 化
- trace / audit 落盘

### 共性做法

```text
Tool Registry
  -> Permission Policy
  -> Execution Guard
  -> Result Policy
  -> Trace / Audit
```

### 数据信号

- 高风险工具覆盖率
- 需要确认的调用占比
- 超大结果被压缩或转 artifact 的比例
- 可复现的失败调用比例

### 当前平台动作

- [ ] 在项目沉淀模板里固定抽取工具权限、结果治理、审计回放。
- [ ] 把项目页里的“这个项目具体怎么做”与 Tool Runtime 痛点页自动关联。

## 4.2 Context / Memory 治理

### 为什么会反复出现

因为模型不是没有上下文，而是很容易被错误上下文拖垮。很多项目一开始只觉得“多给点信息更保险”，最后变成：

- 每轮都重复塞历史
- 老摘要过期了还在用
- tool output 越堆越大
- 当前问题反而被旧信息淹没

### 证据项目

- `zzh/pico`
- `anthropics/claude-code`
- 你现有面经与知识库中关于 long context、memory、resume 的整理

### 优秀项目具体怎么做

真正好的做法不是“做个 memory 开关”，而是把上下文当治理问题：

- 分层记忆
- 最近工作集
- 文件摘要
- durable memory
- freshness / invalidation
- relevance retrieval

`pico` 在源码里已经很清楚地把 `task_summary / recent_files / file_summaries / episodic_notes / durable memory` 分开了，这就是非常强的工程信号。

### 共性做法

```text
Scope
  -> Storage
  -> Retrieval
  -> Freshness
  -> Injection
  -> Eviction
```

### 数据信号

- 平均 prompt 长度变化
- 重复读取次数
- 单任务 tool steps
- 任务完成率或准确率

### 当前平台动作

- [ ] 后续项目页统一增加“上下文治理证据”区块。
- [ ] 痛点页展示来自项目沉淀的 context 指标和案例。

## 4.3 Resume / Recovery / Eval 闭环

### 为什么会反复出现

因为太多项目把“跑通一次”误当成“可以稳定工作”。一旦任务中断、环境变化、工具失败、用户切换工作区，系统就只能重新开始。

### 证据项目

- `zzh/pico`
- `anthropics/claude-code`
- 各类开源 Agent 的 benchmark / report / trace 设计

### 优秀项目具体怎么做

成熟系统不会只恢复聊天历史，而会恢复任务现场：

- task state
- checkpoint
- runtime identity
- workspace fingerprint
- trace / report
- benchmark contract

### 共性做法

```text
Checkpoint
  -> State Validation
  -> Resume Policy
  -> Trace Continuity
  -> Benchmark Feedback
```

### 数据信号

- 可恢复任务比例
- 恢复后继续成功的比例
- 失败分类覆盖率
- benchmark 回归稳定性

### 当前平台动作

- [ ] 面试页增加“你怎么证明这个 Agent 不是 demo”的追问模板。
- [ ] 平台把 checkpoint / report / trace / benchmark 作为高价值能力标签。

## 4.4 扩展生态治理：MCP / Hooks / Plugins / Skills

### 为什么会反复出现

因为所有项目后面都会想开放生态，但一开放就容易乱。工具接口、能力复用、生命周期、权限映射、文档一致性都会一起出问题。

### 证据项目

- `anthropics/claude-code`
- `aaif-goose/goose`
- 你仓库里已有的 MCP、plugin、skill 相关沉淀

### 优秀项目具体怎么做

成熟项目不会只说“支持插件”，而会先区分扩展角色：

- 工具接入
- 工作流扩展
- 任务委派
- 能力包沉淀
- 前后置自动化

### 共性做法

```text
Extension Type
  -> Registration
  -> Capability Contract
  -> Permission Mapping
  -> Lifecycle
  -> Observability
```

### 数据信号

- 扩展类型覆盖度
- 扩展失败可观测性
- 扩展能力复用率
- 权限策略命中率

### 当前平台动作

- [ ] Project Radar 增加对 hooks / MCP / skills / subagents 的独立打标。
- [ ] 方案页增加“扩展角色划分”这类稳定抽象。

## 4.5 从原型到产品化的落差

### 为什么会反复出现

因为很多项目一开始只服务作者本人，等到想做平台或拿去面试时，才发现缺：

- 结构化沉淀
- 证据链
- 状态治理
- 阅读结构
- 搜索与回写链路

### 证据项目

- `anthropics/claude-code`
- `zzh/pico`
- `claude-code-sourcemap` 当前平台自身

### 优秀项目具体怎么做

成熟项目会把“产品化”拆成很多很不性感但很关键的事情：

- 清晰入口
- 配置分层
- 导航清晰
- 文档能读
- 日志能看
- 工件能回放
- 学习资产能回写

### 共性做法

```text
Stable UX
  -> Structured Docs
  -> Searchable Knowledge
  -> Artifact Record
  -> Continuous Writeback
```

### 数据信号

- 文档 section 完整度
- 搜索命中后打开深内容的比例
- 沉淀回写到 patterns / pain-points / interviews 的比例

### 当前平台动作

- [ ] 持续把旧文档迁入新结构，不让平台和文档体系脱节。
- [ ] 每次自动沉淀后同时更新项目页、方案页、痛点页和面试页。

## 5. 优秀项目给我们的共同启发

如果把这些项目横着看，会发现真正值得学的不是谁的功能更多，而是谁更早承认了这些问题是“系统问题”。

共同启发有四条：

- 不要把工具调用当功能，要当治理问题。
- 不要把 memory 当历史，要当上下文预算问题。
- 不要把 resume 当聊天恢复，要当现场恢复问题。
- 不要把平台沉淀当笔记，要当持续回写的问题研究系统。

## 6. 平台怎么利用这份总纲持续进化

以后每新增一个项目、博客、论文或旧文档，都应该做四个动作：

1. 先判断它补强了哪条痛点。
2. 再提取它的具体做法，不许只写功能名。
3. 再补数据信号或证据来源。
4. 最后回写到项目页、方案页、面试页。

只有这样，痛点库才会越来越厚，而不是越来越像一份口号目录。

## 7. 对当前平台的行动项

- [ ] 给每条痛点建立“证据项目 / 共性做法 / 数据信号 / 当前动作”的固定字段。
- [ ] 搜索结果命中痛点时，详情页直接展开深正文，而不是只展示短摘要。
- [ ] 后续自动沉淀链路里，把“补强了哪个行业痛点”设成必填项。
- [ ] 面试页增加“行业为什么反复掉进这个坑”的追问模板，帮助你把项目理解讲出判断力。
