# 行业痛点：Memory / Context Staleness and Bloat

## 1. 为什么这是 Agent 项目最容易反复踩的坑

很多团队第一次给 Agent 加 memory，都会先解决“记不住”的问题，但真正难的从来不是存下来，而是存下来的东西什么时候还可信、什么时候已经过期、什么时候应该重新计算、什么时候根本不该继续注入。

于是系统很容易出现两类问题同时发生：

- 上下文越来越胖，越来越难聚焦当前任务
- 老记忆越来越多，但越来越不可信

这两件事一旦叠在一起，系统就会表现出一种很典型的失控状态：模型看起来“知道很多以前的事”，但越到长流程、恢复流程、跨任务流程，越容易把旧结论当新事实，把过期摘要当稳定前提，把一堆已经偏移的记忆重新塞回当前推理。

所以这个痛点的本质不是“有没有 memory”，而是“memory 有没有生命周期和新鲜度治理”。

## 2. 哪些项目给了强证据

### zzh/pico

`pico` 是这条痛点最有价值的本地样本之一。它的启发不只在于把记忆拆成了多个模块，更在于它已经开始明确区分：

- task summary
- recent files
- file summaries
- episodic notes
- durable memory

更重要的是，它已经把 freshness / invalidation 放进了设计里。这个动作很关键，因为它说明成熟系统不会把“摘要已经生成过”当成结束，而会继续追问“摘要是不是还有效”。

### anthropics/claude-code

Claude Code 把 memory 放进正式产品能力，说明这不是“锦上添花”的增强项，而是长链路协作的基本能力。只要系统希望跨会话、跨任务、跨工作流协作，memory 就一定要从提示词技巧升级成正式运行时组件。

### 当前平台自身

我们的知识平台本身也在经历一个相似问题：项目越来越多、文档越来越长、回写越来越频繁，如果没有稳定的抽取层级、更新规则和失效判断，平台内容很容易从“越积越厚”滑向“越积越乱”。

## 3. 优秀项目具体怎么做

成熟系统不会把 memory 视为一个大文本文件，更不会把所有历史记录一股脑塞回上下文。它们通常至少会做五件事：

### 3.1 先拆 scope

把“什么信息属于哪个层级”讲清楚。比如：

- 当前任务态
- 会话态
- 文件态
- 项目态
- 长期偏好态

scope 不清，后面所有 retrieval 和 injection 都会失控。

### 3.2 再拆 lifecycle

不是所有记忆都应该活一样久。短期任务状态、阶段性摘要、长期偏好、结构化知识，天然就该有不同的过期规则和更新规则。

### 3.3 retrieval 只拿当前真正需要的

很多系统的问题不在“没有记忆”，而在“每次都拿太多”。成熟做法是围绕当前任务、当前文件、当前步骤去做有限检索，而不是把所有相关历史全带上。

### 3.4 injection 有预算

记忆不是“能塞多少塞多少”，而是应该像工具结果一样有预算意识。进入上下文的每一段记忆，都应该回答一个问题：它这次为什么值得占用上下文。

### 3.5 freshness / invalidation 是正式机制

这是最容易被忽略、但决定系统成熟度的一层。只要原始文件变了、用户目标变了、项目结构变了、旧摘要和当前事实对不上，系统就应该允许旧记忆失效，甚至主动淘汰。

## 4. 共性框架可以怎么抽

```text
Memory Source
  -> Scope
  -> Lifecycle
  -> Retrieval
  -> Injection
  -> Freshness / Invalidation
  -> Eviction / Rewrite
```

这个框架最大的价值是把 memory 从“存储能力”拉回“治理能力”。真正值得学的不是谁接了向量库，而是谁把“记忆什么时候该被信任”做成了协议。

## 5. 用什么信号判断问题是否改善

- prompt 中 memory 占比是否可控
- 相同任务是否减少重复读取与重复总结
- stale summary 被识别和淘汰的比例是否上升
- resume 后是否更少出现“旧结论覆盖新事实”
- 长任务里的上下文漂移和目标漂移是否下降

如果后续平台做自动回写和自动进化，这些信号也能反过来帮助我们判断：某篇文档、某条痛点、某个 pattern 是不是已经过期，需要重新抽取。

## 6. 常见误区

- 只关注“记住”，不关注“失效”
- 把 memory 和 context 混成一层
- 所有记忆都长期保留，不淘汰、不重写
- 只做存储，不做 retrieval 排序和注入预算
- 误以为 memory 更多，系统就更聪明

## 7. 对当前平台的直接启发

我们的平台以后沉淀 memory 相关项目时，必须固定抽这几类信息：

- 它的 memory scope 是怎么拆的
- 生命周期和失效规则是什么
- retrieval 按什么条件触发
- injection 有哪些预算或优先级
- stale summary 怎么被发现和重写

否则写出来的内容还是会停留在“这个项目支持 memory”，学习价值很低。

更进一步，平台自己的自动回写体系其实也应该借这条痛点反过来治理自己：旧结论何时过期、旧痛点何时需要重写、旧面试答案何时需要补证据，这本质上都是 memory freshness 问题。
