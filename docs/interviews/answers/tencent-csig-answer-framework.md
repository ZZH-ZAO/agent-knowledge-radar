# Tencent CSIG 面试答案框架

> 目标：这不是题库罗列，而是一套能直接拿来讲项目、接追问、讲 trade-off、把问题拉回工程判断的回答骨架。

## 1. 这份文档到底解决什么问题

很多面试失败，不是因为你项目做得不够，而是因为回答停在“我做了什么功能”。这份框架要解决的是：如何把项目回答从功能枚举，升级成问题定义、工程做法、质量证据、边界取舍和下一步动作。

一句话主线：

> 我不是做了一个会生成内容的 demo，而是围绕真实业务链路，把证据、生成、评估、回流和工程治理组织成了可持续闭环。

## 2. 标准回答骨架

以后讲项目，优先按下面这条线展开：

```text
问题是什么
  -> 为什么这个问题在业务里重要
  -> 我具体怎么做
  -> 怎么验证它不是 demo
  -> 代价和边界是什么
  -> 如果继续做我会补哪里
```

这条线的价值在于，它天然适合接追问，也天然适合把回答拉回工程逻辑。

## 3. 项目介绍版：先把项目讲成闭环，不讲成功能堆

### 3.1 AI 测试用例生成系统的标准讲法

推荐讲法不是“我做了 RAG、Prompt、评估”，而是：

> 这个项目表面上是在做 PRD 自动生成测试用例，但真正难点不是生成文本，而是怎样让模型基于证据生成、减少幻觉、可追溯、可评估，并且能根据 bad case 持续优化。  
> 所以我把它拆成三条链路：第一条是检索链路，负责把 PRD、规范和历史用例变成高密度证据；第二条是结构化生成链路，负责把测试点稳定输出成 JSON；第三条是评估与反馈链路，负责用 AI Critic、人工确认和 bad case 回流形成质量闭环。

这个讲法的关键，是你在第一分钟就把项目从“生成系统”抬到“质量链路系统”。

### 3.2 智慧食安平台的标准讲法

推荐讲法不是“我做了多租户监管平台”，而是：

> 这个项目里我更想强调的不是接口数量，而是复杂业务风险怎么被转成可验证资产。多租户不能串数据，台账状态机不能乱跳，视频证据不能越权访问，报表导出不能拖垮主链路。我在里面做的核心工作，是把这些高风险业务点拆成 API 契约、租户上下文、状态流转规则和回归测试资产。

这个讲法的价值，是把项目回答从“业务系统”拉回“测试开发和工程治理”。

## 4. 深挖版：面试官继续追时怎么往下讲

### 4.1 RAG 不是一句“向量检索”就结束

真正好的回答要讲出链路：

```text
资料加载
  -> 清洗 / 切片 / metadata / embedding
  -> query rewrite
  -> vector + keyword hybrid retrieval
  -> rerank
  -> evidence context
  -> structured generation
  -> AI critic / 人工确认 / bad case 回流
```

你要让面试官听到的是“你知道链路在哪里会坏”，而不是“你用过哪些名词”。

### 4.2 AI Critic 要讲成辅助质检，而不是万能裁判

推荐讲法：

> AI Critic 更像结构化质检员，不是最终裁判。它适合先做覆盖率、一致性、重复项、忠实度这类第一轮筛查，但关键样本仍然需要人工确认。确认后的好样本回流历史库，错误样本进入 bad case 集，用来做后续回归。

这能避免你把系统说得太玄，也更像真实工程。

## 5. Trade-off 版：为什么这样做成立

真正拉开差距的，往往不是你会不会讲流程，而是你会不会讲取舍。

### 5.1 为什么不直接塞整份 PRD

推荐讲法：

> 长上下文解决的是放得下，RAG 解决的是用得好。整份 PRD 里有很多背景、宣传和噪声，模型很容易把低价值内容一起带进生成。我的目标不是给更多字，而是给更高密度证据。

### 5.2 为什么不把 LLM Judge 当绝对真理

推荐讲法：

> LLM Judge 有效率，但不天然稳定。我把它定位成第一轮结构化筛查工具，而不是最终裁判。真正稳的是固定 Rubric、保留评估证据、人工抽检和 bad case 回归。

### 5.3 多租户为什么不能只靠数据库字段隔离

推荐讲法：

> 只靠 tenant_id 字段是远远不够的。请求上下文、业务层资源归属、ORM 默认过滤、缓存 key、导出接口、原生 SQL 都有可能绕过边界，所以我会把它讲成多层隔离，而不是单点字段设计。

## 6. 行业痛点版：把项目回答抬到更高层

如果面试官继续追问“这类系统行业里普遍难在哪”，你可以把回答拉到更强判断层：

- RAG 系统最容易失败的不是检索不到，而是证据密度不够和 rerank 失真。
- AI 生成系统最容易失败的不是写不出来，而是没有忠实度评估和 bad case 闭环。
- 多租户系统最容易失败的不是接口功能少，而是边界穿透和状态失控。
- Agent 系统最容易失败的不是不会调工具，而是权限、结果治理、恢复协议和评估闭环没成形。

这类回答会让你显得不是“记住了自己的项目”，而是真的理解了这类项目为什么难。
