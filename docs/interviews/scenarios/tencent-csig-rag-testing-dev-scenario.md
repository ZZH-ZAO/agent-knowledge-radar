# Tencent CSIG Scenario（RAG + 测试开发模拟面试场景）

> 目标：让 AI 面试官按真实腾讯 CSIG 一面节奏追问，而不是随机抽题。

## 1. 面试官画像

- 关注候选人是否真的做过项目，而不是背 RAG 名词。
- 会连续追问实现细节：切片、检索、重排、指标、评估。
- 会检查项目和测试开发岗位是否匹配。
- 会补基础题和算法题，观察基本功。

## 2. 第一轮：项目主线

1. 请先自我介绍。
2. 介绍一下 AI 测试用例生成系统。
3. 你在项目里主要负责什么？
4. 这个项目和测试开发岗位有什么关系？

判断标准：

- 是否能在 1 分钟内讲清楚质量闭环。
- 是否避免功能罗列。
- 是否把“测试设计”讲成核心，而不只是“调大模型”。

## 3. 第二轮：RAG 深挖

1. RAG 完整流程是什么？
2. 为什么不直接把整份 PRD 塞给模型？
3. 切片策略怎么设计？
4. 如果 chunk 语义不完整怎么办？
5. 为什么要混合检索？
6. rerank 怎么做？
7. 权重怎么定？
8. 你怎么证明 rerank 有效果？
9. 如何区分召回失败和生成失败？

追问原则：

- 如果回答泛泛，继续追具体例子。
- 如果只说向量检索，追问错误码、字段名、失败次数这类精确规则。
- 如果只说指标，追问标注集怎么来、bad case 怎么回归。

## 4. 第三轮：生成、评估、反馈

1. 如何保证 JSON 输出稳定？
2. 评估模块怎么做？
3. LLM Judge 会不会不稳定？
4. 如果 PRD 很短怎么办？
5. 如果 PRD 很长但噪声很多怎么办？
6. 人工反馈怎么回流？
7. 系统有没有长期记忆或自我进化？

评分重点：

- 能否把 AI Critic 讲成辅助质检员。
- 能否强调人工确认和 bad case 回归。
- 能否把 feedback 分成优质用例、驳回原因、规则修正、评估修正。

## 5. 第四轮：Agent / MCP / Skills

1. MCP、Function Calling、Tool Use 有什么区别？
2. Agent 和普通 Function Calling 有什么区别？
3. 你的系统怎么进一步 Agent 化？
4. Skills 放到这个项目里有什么价值？

标准回答核心：

```text
Function Calling 是动作契约
Tool Use 是外部行动能力
MCP 是能力接入协议
Agent 是受控任务推进循环
Skills 是经验资产化
```

## 6. 第五轮：智慧食安项目

1. 介绍一下智慧食安平台。
2. 多租户隔离怎么做？
3. 怎么测多租户越权？
4. 状态机怎么测？
5. 报表导出怎么设计和测试？
6. MySQL / Redis 到底有没有落地？

注意：

- MySQL / Redis 不要夸大。
- 要强调 SQLite 是本地开发和测试默认环境，但模型、迁移、索引、事务边界按正式数据库迁移路径考虑。
- Redis 讲缓存隔离和降级，不要讲成核心依赖。

## 7. 第六轮：基础和算法

1. TCP 三次握手。
2. TCP 四次挥手。
3. TIME_WAIT 作用。
4. 进程、线程、协程区别。
5. 合并两个有序链表。

训练要求：

- 基础题控制在 60 秒内。
- 算法题先说思路，再写模板。
- 复盘时主动说 dummy node、边界和复杂度。

## 8. 评分 Rubric

| 维度 | 高分表现 | 低分表现 |
| --- | --- | --- |
| 项目主线 | 质量闭环清楚 | 功能罗列 |
| RAG | 能讲证据选择和失败定位 | 只说向量库 |
| 评估 | AI Critic + 人工确认 + 回归 | 模型自己评自己 |
| 测开匹配 | 能把风险转成测试资产 | 只讲后端功能 |
| AI 工程 | 能区分 Agent / Tool / MCP / Skill | 概念混用 |
| 基础 | 简洁准确 | 解释绕、边界不清 |
| 算法 | 模板稳定 | 现场卡住无法补救 |

## 行业痛点研究版补充

> 目标：把“Tencent CSIG Scenario（RAG + 测试开发模拟面试场景）”从单篇资料或单个项目笔记，升级成能服务行业痛点研究、优秀做法抽象和当前项目行动的学习资产。

### 1. 它对应的行业痛点

Agent 接入外部工具后，行业共性痛点是权限、结果大小、执行副作用、工具质量和可观测性会同时失控。优秀项目不会把工具当普通函数，而会把它放进 Tool Runtime / MCP Integration 的治理管线。

判断它是不是值得持续沉淀，不看它是否新奇，而看它能不能解释一个反复出现的行业问题，并能不能给当前项目带来可执行改变。

### 2. 可作为证据的来源类型

GitHub 工具型项目、MCP server、旧体系工具文档、源码 README、浏览器自动化案例。

后续如果新增 GitHub、优质博客、论文或你提供的文档，都应该先判断它能否补强这一类证据，而不是直接堆进知识库。

### 3. 优秀项目或资料的共性做法

共性做法是 Tool Registry + Permission Mapping + Result Summary + Artifact Reference + Audit Trail，把调用、权限、结果和追踪拆开治理。

这里真正要学的不是表层功能名，而是成熟项目如何划分边界、控制风险、组织证据、形成可复用流程。

### 4. 数据支撑与判断信号

可观察信号包括工具数量、权限等级覆盖率、单次结果 token 数、artifact 引用比例、失败调用可复现率。

这些信号用于避免主观判断。后续平台应该让痛点页自动展示证据项目数、来源类型、关联方案数和行动项数量。

### 5. 给当前项目的启发

这份文档应该反哺 `claude-code-sourcemap` 的三个位置：

- 项目页：说明它作为样本值得学习什么。
- 痛点页：说明它补强了哪个 Agent / 大模型行业共性问题。
- 方案页：说明它能沉淀成什么可迁移框架。
