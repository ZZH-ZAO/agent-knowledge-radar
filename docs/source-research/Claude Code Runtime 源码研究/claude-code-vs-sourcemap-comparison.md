# Claude Code Sourcemap 与 `D:\claude-code` 对照分析

## 0. 先说明我这份对照是在比什么

这份文档对比的两个对象是：

- 当前仓库：`d:\claude-code-sourcemap`
- 本地另一个仓库：`D:\claude-code`

你原话里写的是 `D:\claude-codex`，但我本地没有找到这个目录，只找到了结构高度对应、明显就是目标对象的 `D:\claude-code`。所以这份文档先基于 `D:\claude-code` 来做。

我这里不是只比较“功能多少”，而是比较更重要的三件事：

1. 两个项目分别把 Agent 当成什么系统来设计。
2. 它们分别强调了哪些工程重点。
3. 如果你以后做自己的 Agent 项目，应该从两边分别学什么。

先给结论：

> `claude-code-sourcemap` 更像“Claude Code 核心 Runtime 的还原版样本”，适合学习底层 Agent 工程主线。
>
> `D:\claude-code` 更像“在这个底座上继续做扩展、产品化和实验化探索的增强版分支”，适合学习如何把 Agent 从核心运行时继续推向复杂产品能力。

这两个项目不是简单的高低关系，而是学习重点不同。

---

## 1. 最大的共同点：它们的底座其实还是同一类 Agent Runtime

从代码结构上看，两个项目共享很多非常关键的主干概念和文件组织方式，比如：

- `QueryEngine.ts`
- `query.ts`
- `buildEffectiveSystemPrompt()`
- `processUserInput()`
- `Tool.ts`
- `toolOrchestration.ts`
- `compactConversation()`
- `extractMemories`
- `runAgent()`
- `coordinatorMode`
- `inProcessRunner`

这说明它们不是两个完全不同思想的系统，而是：

> 同一类 Claude Code 风格 Agent Runtime，在不同阶段和不同目标下的两种呈现。

也就是说，这两个项目都不是那种“聊天界面 + 调工具”的轻量壳子。
它们的核心理解都已经是：

- 有主 query loop
- 有 Prompt 组装层
- 有 Tool Runtime
- 有长会话治理
- 有记忆体系
- 有多 Agent 扩展

所以如果你想学 Agent 工程的底层逻辑，这两个项目都能学。
区别不在“有没有 Agent 工程”，而在“工程重心往哪边继续推”。

## 2. `claude-code-sourcemap` 更像什么：核心机制导向、结构理解导向

这个仓库最大的价值，是它让我们更容易看清 Claude Code 这类系统的主骨架。

### 2.1 它的亮点不是“功能多”，而是“主线清楚”

如果你回头看我们已经写下来的分析文档，你会发现这个项目最强的地方是：

- 主循环很清楚
- Prompt 系统的结构很清楚
- Tool 调度链路很清楚
- compact、memory、多 Agent 这些机制和主链之间的关系很清楚

它特别适合回答这些问题：

- Agent Runtime 到底是什么
- query loop 为什么是系统中心
- Prompt 为什么要拆成系统而不是一整段
- Tool Calling 为什么要做成运行时
- Workflow 为什么要按时间尺度分层
- Memory 为什么不是简单存历史

### 2.2 它更像“内核教材”

如果要给它一个最准确的定位，我会说它像：

- 一个很好的 Runtime 解剖样本
- 一个适合学习 Claude Code 核心架构的内核教材
- 一个帮助你看懂 Agent 基础工程的骨架仓库

它的强项主要在“本质问题”上，而不在“外围产品能力”上。

也就是它更适合学习：

- 内核怎样跑起来
- 模型如何被纳入可控循环
- 状态如何被治理
- 多个机制如何挂回统一主线

### 2.3 它背后的设计理念

我觉得这个仓库体现出来的设计理念是：

> 先把 Agent 的核心运行问题讲清楚，再谈能力扩展。

这种理念非常适合：

- 想理解 Agent 基础架构的人
- 想自己做一个 Claude Code 类系统的人
- 想先把底层设计站稳，再慢慢加能力的人

它不一定是“功能最热闹”的版本，但它很适合建立正确的工程直觉。

## 3. `D:\claude-code` 更像什么：扩展能力导向、产品化导向、实验平台导向

和 Sourcemap 相比，`D:\claude-code` 最明显的差异不是主干变了，而是：

> 它在同一个底座上，明显往“产品能力扩展平台”方向走得更远。

从 `README.md`、`docs/feature-exploration-plan.md`、`docs/features/*` 和源码分布看，它关注的不只是 Claude Code 核心逻辑，而是继续往这些方向推：

- 远程控制
- 多实例通信
- 团队共享记忆
- 主动式 Agent
- 语音输入
- 浏览器 / computer use
- OpenAI 兼容 / 多模型接入
- Feature Flag 驱动的实验体系
- 更重的遥测、监控、运维和发布能力

这意味着它的角色更像：

- 一个 Agent 产品实验场
- 一个多 feature 并行演化平台
- 一个在核心 Runtime 之上继续加企业化和产品化壳层的版本

### 3.1 它最突出的亮点一：Feature Flag 架构非常强

这是两个仓库最明显的气质差异之一。

`D:\claude-code` 对 feature flag 的重视程度非常高，从文档里可以直接看到：

- 它有很系统的 feature 审计文档
- 有探索计划书
- 很多功能明确分为 complete / partial / stub
- 不同 feature 可以组合启用

这代表的设计理念不是“把所有功能一次性做完”，而是：

> 把 Agent 系统做成一个可实验、可分支、可灰度、可组合演化的平台。

这对真正做复杂 Agent 产品特别重要，因为真实世界里很多能力不是一口气做完的，而是：

- 先布线路
- 再做局部实现
- 再灰度验证
- 再决定是否进入主路径

Sourcemap 更适合你学“系统本体”，而 `D:\claude-code` 让你看到“系统如何持续长功能”。

### 3.2 它最突出的亮点二：把 Agent 往“常驻化、后台化、主动化”方向推进

这点非常重要。

Sourcemap 虽然已经有多 Agent、背景任务、memory 整理这些机制，但整体仍然更偏“围绕请求驱动的 Agent Runtime”。

而 `D:\claude-code` 明显在尝试把 Agent 推向更持续存在的形态，比如：

- `KAIROS`
- `PROACTIVE`
- `BG_SESSIONS`
- `/dream`
- bridge / remote control

这里背后的设计理念是：

> Agent 不一定只能在“用户发一句话，我回一句话”这个节奏里存在。

它还可以变成：

- 长驻助手
- 后台持续任务体
- 可远程唤醒的执行体
- 在没有即时用户输入时也能继续推进工作的系统

这是一种更激进、更产品化的 Agent 方向。

### 3.3 它最突出的亮点三：团队协作和分布式场景意识更强

`TEAMMEM`、`pipes`、`LAN pipes`、bridge、remote control 这些能力放在一起看，就能看到一个很强的倾向：

> 这个项目不只把 Agent 当成“单用户本地 CLI”，而是在尝试把它推向多人、多实例、跨端、跨环境协作系统。

尤其 `TEAMMEM` 这块很值得注意。
它不是简单把 memory 文件同步一下，而是已经考虑了：

- 增量同步
- ETag 冲突控制
- secret scanning
- 路径边界校验
- watcher 驱动的自动 push
- GitHub repo 作为团队上下文 scope

这说明它已经不满足于“Agent 记住我”，而是在探索：

> 团队怎样共享被 Agent 沉淀出来的项目知识。

这对未来企业 Agent、团队 Copilot、多人协作型 Agent 都非常有启发。

### 3.4 它最突出的亮点四：外围能力和产品配套明显更重

从 `package.json` 和 `docs` 里还能看出，它比 Sourcemap 更强调这些东西：

- Sentry
- GrowthBook
- OpenTelemetry
- Langfuse
- OAuth / 多平台接入
- 自动更新
- 远程服务器依赖说明
- 自托管 remote control 文档

这背后的理念很明确：

> Agent 产品不是只有模型和工具，还需要监控、发布、灰度、依赖管理、远程控制、账户体系这些“产品外壳”。

这部分在 Sourcemap 里没有那么强的存在感。
所以如果 Sourcemap 更像“Runtime 教材”，`D:\claude-code` 就更像“Runtime + 产品平台”的试验田。

## 4. 两个项目最核心的差异，不是有没有功能，而是设计焦点不同

我觉得可以把它们的差异压缩成一句最关键的话：

> `claude-code-sourcemap` 更强调“把 Agent 运行时讲清楚”。
>
> `D:\claude-code` 更强调“在这个运行时上持续长出更多产品能力和实验 feature”。

下面我把这个差异拆细一点。

### 4.1 Sourcemap 的焦点：核心主线、底层机制、运行本体

它更像在回答：

- Agent Runtime 的标准骨架是什么
- Claude Code 类系统的内核怎么组织
- Prompt、Tool、Workflow、Memory、多 Agent 如何统一到一条主线

所以你会觉得它更适合“学原理”。

### 4.2 `D:\claude-code` 的焦点：能力扩展、实验路线、产品边界

它更像在回答：

- 在这个底座上还能继续长什么
- 哪些能力可以通过 flag 灰度探索
- 怎样把 Agent 推向远程化、主动化、团队化、跨端化
- 怎样让系统越来越接近一个完整产品，而不是单机 CLI 工具

所以它更适合“学演进”。

## 5. 哪些点是 `D:\claude-code` 特别值得单独学习的

这一节我不讲泛泛比较，而是直接讲我认为它最有迁移价值的几个亮点。

### 5.1 Feature Flag 驱动的 Agent 演进方式

这点非常值得学。

很多 Agent 项目最大的问题不是做不出功能，而是：

- 新功能一多，主线开始混乱
- 实验能力直接污染主路径
- 团队不敢做前瞻性尝试，因为收不回来

`D:\claude-code` 的启发是：

- 用 flag 明确能力边界
- 用文档区分 complete / partial / stub
- 允许实验 feature 先布线路，再逐渐落地

这是一种很成熟的“Agent 平台工程”思路。

### 5.2 团队记忆 `TEAMMEM`

这是我觉得它最有特色的设计之一。

为什么它亮眼？

因为它把 Agent memory 从“个人偏好记忆”推到了“团队知识同步”。

它告诉我们：

- 记忆不一定只为当前会话服务
- 也可以成为团队共享知识资产
- 一旦进入团队场景，memory 立刻会遇到同步、冲突、安全、路径边界等工程问题

这比普通“记住用户偏好”要更接近企业级 Agent 场景。

### 5.3 主动模式 / 常驻助手思路

虽然 `PROACTIVE` 在文档里仍有 stub，但它表达出来的方向本身非常值得学。

它不是简单说“我也想做 auto mode”，而是已经在设计：

- tick 驱动
- SleepTool 节律控制
- 用户不输入时也能继续工作
- prompt cache 与节拍控制的关系

也就是说，它在探索一种更接近 autonomous agent 的运行节奏。

哪怕实现尚未完全，这种问题意识本身就很有价值。

### 5.4 pipes / LAN pipes / remote control

这套方向说明它在探索另一种很少被认真做的 Agent 能力：

> Agent 实例之间怎样通信、路由、附着、跨机器协同。

这和普通多 Agent 只在内存里 spawn worker 很不一样。

它意味着系统开始考虑：

- 多实例拓扑
- 本地实例间协作
- 局域网发现
- 外部控制面接入
- control plane 和 data plane 的划分

如果以后要做“Agent 网络”或者“Agent mesh”类系统，这块很值得参考。

## 6. 哪些点是 Sourcemap 反而更适合作为学习起点的

虽然 `D:\claude-code` 更热闹，但不代表它就一定更适合先学。

实际上，对大多数想学 Agent 工程的人来说，Sourcemap 往往更适合作为第一站。

### 6.1 因为它更容易看清主执行链

`D:\claude-code` 的扩展 feature 多了以后，阅读体验会更像：

- 一个不断长功能的真实产品仓库

这种仓库的优点是丰富，缺点是：

- 主线更容易被旁支打散
- 功能 flag 更多，认知负担更重
- 你更容易陷进某个 feature，而忽略核心 Agent Runtime

而 Sourcemap 更适合你先建立：

- Agent Runtime 的骨架认识
- 各层之间的因果关系
- 主 query loop 和周边系统之间的依附关系

### 6.2 因为它更像“通用底层模型”

Sourcemap 里的很多结论更容易迁移到其他 Agent 项目：

- 如何设计 query loop
- 如何拆 Prompt
- 如何组织 Tool Runtime
- 如何分层 Workflow
- 如何理解 Memory
- 如何理解多 Agent 的责任关系

这些是任何 Agent 项目都要面对的问题。

而 `D:\claude-code` 里有些亮点是更偏“特定产品方向”的，比如：

- voice mode
- remote control
- pipes
- teammem
- KAIROS

这些很有启发，但不是每个项目一开始都需要。

## 7. 如果把两个项目的设计理念抽象出来，分别代表什么路线

这一节最重要，因为它决定你以后怎么用这两个项目。

### 7.1 Sourcemap 代表的路线：先把 Agent Runtime 做稳

它代表一种比较“基础设施派”的路线：

- 先有清晰主循环
- 先有上下文治理
- 先有工具治理
- 先有长会话治理
- 先有记忆与多 Agent 的基础骨架

这条路线的好处是：

- 底座稳定
- 容易理解
- 容易迁移
- 容易形成方法论

它更适合：

- 从零做 Agent 内核
- 想做 Claude Code 类核心体验
- 想建立正确 Agent 工程直觉

### 7.2 `D:\claude-code` 代表的路线：把 Agent Runtime 做成可持续扩展的平台

它代表一种更“产品平台派”的路线：

- 内核先站住
- 然后用 feature flag 持续扩能力
- 把 Agent 推向远程化、团队化、常驻化、跨实例化
- 把监控、发布、遥测、集成也纳入设计

这条路线的好处是：

- 能承载更多真实场景
- 更接近产品团队长期演进形态
- 更适合多人协作开发和试验

但代价也很明显：

- 复杂度更高
- 阅读门槛更高
- 一部分 feature 尚未完全落地
- 更容易出现“路线很强，但局部实现还在补”的状态

## 8. 如果你以后自己做 Agent，应该怎么综合吸收两边的优点

这是最实用的一节。

我不建议照搬任意一边，而是建议按阶段吸收。

### 8.1 第一阶段：先学 Sourcemap 的主骨架

先学这些：

- query loop 是中心
- Prompt 要结构化
- Tool 要运行时化
- Workflow 要按时间尺度分层
- Memory 要做多层体系
- 多 Agent 要有责任中心

这一步的目标不是做很多 feature，而是把 Agent 的底层运行方式做对。

### 8.2 第二阶段：再学 `D:\claude-code` 的平台化方法

当底座稳定以后，再考虑学这些：

- feature flag 体系
- 团队共享记忆
- 主动模式
- 远程控制
- 多实例通信
- 更重的 observability 与运维配套

这一步的目标是：

- 让 Agent 从“能跑”走向“能演进”
- 从“单人单机会话”走向“更真实复杂的产品场景”

### 8.3 最好的组合方式

如果让我给一个自己的 Agent 项目提方案，我会建议：

1. 用 Sourcemap 的方式搭内核。
2. 用 `D:\claude-code` 的方式搭演进框架。

也就是：

- 内核参考 Sourcemap
- 产品扩展参考 `D:\claude-code`

这是我觉得最稳的组合。

## 9. 最后总结：这两个项目各自最该学什么

如果把整份对照分析压到最短，我会这样说。

### 9.1 从 `claude-code-sourcemap` 最该学的

- Agent Runtime 的主线
- query loop 的中心地位
- Prompt / Tool / Workflow / Memory / Multi-Agent 的统一理解
- 怎样用一份源码真正看懂 Claude Code 类系统的底层结构

### 9.2 从 `D:\claude-code` 最该学的

- Feature Flag 驱动的 Agent 平台演进方式
- 团队记忆、主动模式、远程控制、多实例通信这些更前沿方向
- 如何把核心 Runtime 往产品化、团队化、常驻化方向推进
- 如何让 Agent 系统具备更强的扩展性和实验能力

### 9.3 一句话结论

`claude-code-sourcemap` 更像“Agent 内核教材”。

`D:\claude-code` 更像“Agent 平台实验场”。

前者更适合学“底层是什么”。
后者更适合学“底层站住以后还能怎么长”。

## 深度学习版补充

> 学习目标：读完这部分后，不只是知道“Claude Code Sourcemap 与 `D:\claude-code` 对照分析 做了什么”，而是能讲清它背后的工程问题、适用边界、常见误区和对当前平台的迁移路径。

### 1. 这件事到底考什么

这里真正考察的不是会不会调用一个 API，而是能不能把 Agent 对外部世界的行动放进可治理的执行管线。

如果只回答功能点，说明还停留在“看过项目”的层面；如果能回答问题来源、工程约束、取舍和行动项，才说明这份沉淀真正进入了自己的方法论。

### 2. 口语版回答

我会把工具调用理解成 Agent Runtime 的行动边界。成熟系统不能只关心函数能不能执行，还要关心输入协议、权限分级、执行隔离、结果压缩、错误恢复和审计回放。否则模型一旦误调工具，风险会直接落到真实文件、浏览器、网络或业务系统上。

这段回答可以直接用于复盘、面试或方案评审。它的结构是：先定义问题，再讲工程边界，最后落到可迁移做法。

### 3. 工程视角拆解

可以按四层来理解：

- 问题层：这个设计到底在解决什么不稳定、不可控或不可复用的问题。
- 机制层：它用了哪些结构、协议、运行时、文档或流程来解决。
- 证据层：有哪些 README、源码、指标、案例或平台行为能证明它不是口号。
- 迁移层：它对 `claude-code-sourcemap`、知识平台、Project Radar 或面试训练有什么可执行启发。

### 4. 常见误区

把 MCP 或 Tool Calling 当成普通 API wrapper，只写 schema，不写权限、结果治理和失败恢复。

另一个常见误区是只把优秀项目当作模板照抄。真正应该学的是它为什么这样拆分，以及这个拆分在自己的场景里是否仍然成立。

### 5. Trade-off 与边界

治理越完整，接入成本越高；但如果工具有副作用，前期省掉治理，后期会以安全事故、上下文爆炸和不可复现的形式还回来。

判断一个方案是否成熟，不是看它有没有更多能力，而是看它有没有明确说明代价、适用场景和不适用场景。

### 7. 面试官追问

**追问：这个项目或方案最值得学习的不是功能，而是什么？**

答：最值得学习的是它如何把一个模糊问题变成可治理的工程结构。功能只是表层，真正可迁移的是它的边界划分、执行流程、证据链和取舍。

**追问：如果迁移到当前平台，第一步应该做什么？**

答：第一步不是照搬实现，而是把它抽象成平台中的一个通用问题，补齐文档、索引、行动项和验证方式，让后续沉淀能自动进入平台展示。

## 行业痛点研究版补充

> 目标：把“Claude Code Sourcemap 与 `D:\claude-code` 对照分析”从单篇资料或单个项目笔记，升级成能服务行业痛点研究、优秀做法抽象和当前项目行动的学习资产。

### 1. 它对应的行业痛点

Agent 接入外部工具后，行业共性痛点是权限、结果大小、执行副作用、工具质量和可观测性会同时失控。优秀项目不会把工具当普通函数，而会把它放进 Tool Runtime / MCP Integration 的治理管线。

判断它是不是值得持续沉淀，不看它是否新奇，而看它能不能解释一个反复出现的行业问题，并能不能给当前项目带来可执行改变。

### 2. 可作为证据的来源类型

GitHub 工具型项目、MCP server、旧体系工具文档、源码 README、浏览器自动化案例。

后续如果新增 GitHub、优质博客、论文或你提供的文档，都应该先判断它能否补强这一类证据，而不是直接堆进知识库。

### 3. 优秀项目或资料的共性做法

共性做法是 Tool Registry + Permission Mapping + Result Summary + Artifact Reference + Audit Trail，把调用、权限、结果和追踪拆开治理。

这里真正要学的不是表层功能名，而是成熟项目如何划分边界、控制风险、组织证据、形成可复用流程。

### 4. 数据支撑与判断信号

可观察信号包括工具数量、权限等级覆盖率、单次结果 token 数、artifact 引用比例、失败调用可复现率。

这些信号用于避免主观判断。后续平台应该让痛点页自动展示证据项目数、来源类型、关联方案数和行动项数量。

### 5. 给当前项目的启发

这份文档应该反哺 `claude-code-sourcemap` 的三个位置：

- 项目页：说明它作为样本值得学习什么。
- 痛点页：说明它补强了哪个 Agent / 大模型行业共性问题。
- 方案页：说明它能沉淀成什么可迁移框架。
