# 通用问题：GPT Image Frontend Generation

> 阅读目标：把 GPT Image 2 在前端工程中的位置讲清楚。它不是“直接生成网页”的银弹，而是前端视觉目标生成器。真正成熟的流程是：先出视觉稿，再由工程实现，最后用浏览器截图校准。

## 1. 这件事在项目里到底考什么

如果有人问“能不能用 GPT Image 2 生成前端页面”，浅层回答是“可以生成 UI mockup”。但这个回答不够。

真正要考的是：

1. 你能不能区分视觉目标和工程实现。
2. 你知不知道图像模型的输出不能直接等价于 DOM、CSS、响应式和可访问性。
3. 你能不能把生成图接入一个可验证、可回写、可复用的前端工程闭环。

比较好的答法是：

> GPT Image 2 更适合做前端视觉目标生成，而不是直接替代前端工程。我的流程是先读取 `DESIGN.md` 和页面 inventory，生成 UI mockup 固定布局、密度和风格；然后由编码 Agent 或工程师实现 React/CSS；实现后用浏览器截图和 mockup 对照，检查间距、字体、信息层级、响应式和内容溢出；最后把反复出现的校准结果回写到 `DESIGN.md`。这样图像模型负责探索和定目标，工程系统负责真实可维护页面。

这段答法能体现工程判断，而不是把图像生成讲成魔法。

## 2. 问题定义

GPT Image Frontend Generation 解决的是：

```text
当前端页面的视觉目标不清楚时，如何先生成一个可对照的 UI 目标图，再把它稳定落到真实页面？
```

它不是：

```text
一句话 -> GPT Image 2 -> 直接得到可上线页面
```

而是：

```text
产品意图
  -> 页面结构
  -> 视觉提示词
  -> UI mockup
  -> React/CSS 实现
  -> 浏览器截图
  -> 差异校准
  -> 设计规则回写
```

## 3. 为什么这件事重要

编码 Agent 写前端时最大的问题，不是不会写 CSS，而是没有稳定的视觉目标。

你说“做一个高级一点的知识平台”，Agent 可能会做出三种完全不同的东西：

- 营销官网式 hero。
- 卡片堆叠式 dashboard。
- 暗色科技感大屏。

这些都可能“看起来还行”，但不一定适合你的产品。

GPT Image 2 的价值在于，它可以先把模糊审美变成一个可讨论的视觉对象。你可以拿着 mockup 判断：

- 信息密度是否合适。
- 中文文本是否有空间。
- 侧边栏是否稳定。
- 列表和详情是否清楚。
- 有没有过度装饰。

但它的边界也很清楚：图像不是前端。

图像不会自动保证：

- DOM 结构合理。
- 移动端可用。
- 文本不溢出。
- 颜色符合对比度。
- 数据为空时仍然好看。
- 后续维护成本可控。

所以必须接工程闭环。

## 4. 口语版回答

如果面试或复盘中被问，可以这样讲：

> 我会把 GPT Image 2 放在前端流程的前半段，用来生成视觉目标，而不是直接生成最终页面。比如我要改知识平台的项目页，我会先把产品定位、信息密度、页面区域和禁用风格写成 prompt，再让模型出一张 mockup。这个 mockup 解决的是“目标长什么样”。之后我仍然要用 React/CSS 实现真实页面，并用 Playwright 或浏览器截图和 mockup 对照。对照出来的差异，比如间距过大、中文标题太拥挤、卡片过多，我会回写到 DESIGN.md。这样它就不是一次性出图，而是设计规则迭代的一部分。

## 5. 和普通 Prompt 生图有什么区别

普通生图 prompt 更像艺术描述：

```text
做一个现代、高级、简洁的后台页面
```

这种写法的问题是不可控。现代、高级、简洁都是情绪词，不是工程约束。

面向前端工程的 prompt 应该像页面规格：

```text
产品类型：中文知识工作台
主要用户：长期学习和项目沉淀的个人开发者
页面目标：浏览项目分类、查看项目详情、追踪行动项
布局：左侧项目列表，右侧详情阅读器，顶部搜索，横向指标条
信息密度：偏高，但不要拥挤
组件：badge、tag、metric、source line、document reader
禁用：营销 hero、大面积渐变、装饰性背景、卡片套卡片
响应式：桌面两栏，移动端单栏
```

这就是从“散文提示词”升级成“Prompt-as-Code”。

## 6. 优秀项目怎么学

### oil-oil/draw-ui

`draw-ui` 值得学的不是“它能出图”，而是它把出图放进 Claude Code skill 工作流。

它的关键链路是：

```text
自然语言页面需求
  -> UI mockup
  -> screenshot reference
  -> HTML/CSS reconstruction
  -> browser screenshot comparison
```

对当前平台来说，这意味着后续大改页面时，可以先生成视觉稿，再改代码，而不是直接凭感觉改 CSS。

### freestylefly/awesome-gpt-image-2

这个项目值得学的是 Prompt-as-Code 思路。

它把零散提示词整理成结构化模板，这对我们很重要。因为平台后续会反复生成：

- 项目页 mockup。
- 方案页 mockup。
- 痛点页 mockup。
- 面试官页 mockup。
- 雷达页 mockup。

如果每次都临时写 prompt，风格一定会漂。

### Desima-AP/autoimage-claude

这个项目的启发是：图像生成可以扫描前端项目上下文。

对当前平台来说，后续可以让系统读取：

- `DESIGN.md`
- `styles.css`
- 当前页面结构
- 已有颜色和组件

再生成更贴合平台气质的视觉稿，而不是凭空生成。

### CookSleep/gpt_image_playground

它适合学产品化界面：参数管理、参考图、遮罩、历史记录、本地存储。

如果以后平台真的加“视觉生成”功能，可以参考它如何管理任务历史和参考图，而不是每次生成完就丢。

## 7. 常见误区

### 误区一：把 GPT Image 2 当代码生成器

图像模型输出的是视觉目标，不是代码。它看起来像一个页面，但没有真实 DOM、状态、交互、响应式和可访问性。

### 误区二：只看生成图，不做截图对照

如果没有实现后的浏览器截图，就不知道真实页面和 mockup 差多少。成熟流程必须包含“实现截图”。

### 误区三：每个页面单独出图

这样很容易导致侧边栏、按钮、密度、字体层级都不一致。

正确做法是：

```text
先确定一个核心参考页面
后续页面都引用它
只变化主内容区
```

### 误区四：忽略中文文本

很多 UI mockup 对英文很友好，但中文标题、长句、路径、标签很容易撑爆。当前平台必须明确写入中文内容优先。

## 8. 工程闭环

成熟流程应该包含八个步骤：

1. 读取 `DESIGN.md`。
2. 写页面 inventory。
3. 生成视觉 prompt。
4. 生成 mockup。
5. 实现 React/CSS。
6. 截图桌面端和移动端。
7. 记录 visual diff。
8. 回写设计规则。

其中最容易被忽略的是第 7 步和第 8 步。

如果只改代码，不沉淀差异，下次还会犯同样的问题。

## 9. 当前平台的可迁移方案

### 第一阶段：只做文档化

先不接 API，只把流程写清楚：

- `DESIGN.md` 增加视觉生成边界。
- `patterns/` 增加 GPT Image 前端生成方法。
- `external-projects/` 沉淀 draw-ui。
- 平台新增“视觉生成工作流”页面。

这一阶段已经基本完成。

### 第二阶段：半自动生成 prompt

平台可以根据当前页面类型生成 prompt：

- 项目页 prompt。
- 方案页 prompt。
- 痛点页 prompt。
- 面试官页 prompt。
- 雷达页 prompt。

人确认后再去调用图像模型。

### 第三阶段：截图校验

前端实现后，用 Playwright 或浏览器截图记录：

- desktop。
- mobile。
- 关键页面状态。

再人工或半自动对照 mockup。

### 第四阶段：规则回写

把反复出现的问题写回：

- `apps/knowledge-platform/DESIGN.md`
- `docs/patterns/前端设计控制/`

这样平台会越改越稳。

## 10. 面试官追问

### 追问一：为什么不直接让模型生成 React？

可以答：

> 因为 React 代码质量不仅取决于视觉，还取决于组件边界、状态管理、响应式、可访问性和后续维护。GPT Image 2 的强项是视觉目标，不是工程结构。所以我会让它先出 mockup，再由编码 Agent 按项目现有组件和 DESIGN.md 实现。

### 追问二：mockup 和真实页面不一致怎么办？

可以答：

> 我会把不一致分成两类。第一类是实现问题，比如间距、字体、颜色没对齐，就改 CSS。第二类是 mockup 不适合真实工程，比如中文太长、移动端不可用，就反过来修 prompt 和 DESIGN.md。这个过程本质是设计规则迭代。

### 追问三：怎么避免每次生成风格都变？

可以答：

> 用固定的 DESIGN.md、页面 inventory 和 reference image。第一张稳定页面作为视觉锚点，后续页面只变化主内容区，不重新发明侧边栏和基础组件。

## 深度学习版补充

> 学习目标：读完这部分后，不只是知道“通用问题：GPT Image Frontend Generation 做了什么”，而是能讲清它背后的工程问题、适用边界、常见误区和对当前平台的迁移路径。

### 1. 这件事到底考什么

这里考察的是能不能把前端审美要求变成可执行的工程规则，而不是只说高级、现代、好看。

如果只回答功能点，说明还停留在“看过项目”的层面；如果能回答问题来源、工程约束、取舍和行动项，才说明这份沉淀真正进入了自己的方法论。

### 2. 口语版回答

我会把前端风格控制理解成设计上下文工程。对知识平台来说，重点不是营销式视觉，而是长期可读、可扫描、可追溯。所以我会用 DESIGN.md 固化规则，用 UI mockup 固定目标，用截图对照校准实现，最后把反复出现的问题回写成设计规范。

这段回答可以直接用于复盘、面试或方案评审。它的结构是：先定义问题，再讲工程边界，最后落到可迁移做法。

### 3. 工程视角拆解

可以按四层来理解：

- 问题层：这个设计到底在解决什么不稳定、不可控或不可复用的问题。
- 机制层：它用了哪些结构、协议、运行时、文档或流程来解决。
- 证据层：有哪些 README、源码、指标、案例或平台行为能证明它不是口号。
- 迁移层：它对 `claude-code-sourcemap`、知识平台、Project Radar 或面试训练有什么可执行启发。

### 4. 常见误区

把所有页面做成卡片堆，或者用 GPT Image 生成一张漂亮图后不做真实页面校验。

另一个常见误区是只把优秀项目当作模板照抄。真正应该学的是它为什么这样拆分，以及这个拆分在自己的场景里是否仍然成立。

### 5. Trade-off 与边界

视觉生成能提升探索效率，但不能替代 React/CSS、响应式、中文长文本和可访问性这些真实工程约束。

判断一个方案是否成熟，不是看它有没有更多能力，而是看它有没有明确说明代价、适用场景和不适用场景。

## 行业痛点研究版补充

> 目标：把“通用问题：GPT Image Frontend Generation”从单篇资料或单个项目笔记，升级成能服务行业痛点研究、优秀做法抽象和当前项目行动的学习资产。

### 1. 它对应的行业痛点

Agent 接入外部工具后，行业共性痛点是权限、结果大小、执行副作用、工具质量和可观测性会同时失控。优秀项目不会把工具当普通函数，而会把它放进 Tool Runtime / MCP Integration 的治理管线。

判断它是不是值得持续沉淀，不看它是否新奇，而看它能不能解释一个反复出现的行业问题，并能不能给当前项目带来可执行改变。

### 2. 可作为证据的来源类型

GitHub 工具型项目、MCP server、旧体系工具文档、源码 README、浏览器自动化案例。

后续如果新增 GitHub、优质博客、论文或你提供的文档，都应该先判断它能否补强这一类证据，而不是直接堆进知识库。

### 3. 优秀项目或资料的共性做法

共性做法是 Tool Registry + Permission Mapping + Result Summary + Artifact Reference + Audit Trail，把调用、权限、结果和追踪拆开治理。

这里真正要学的不是表层功能名，而是成熟项目如何划分边界、控制风险、组织证据、形成可复用流程。

### 4. 数据支撑与判断信号

可观察信号包括工具数量、权限等级覆盖率、单次结果 token 数、artifact 引用比例、失败调用可复现率。

这些信号用于避免主观判断。后续平台应该让痛点页自动展示证据项目数、来源类型、关联方案数和行动项数量。

- 项目页：说明它作为样本值得学习什么。

- 方案页：说明它能沉淀成什么可迁移框架。
